# `src/gnome-shell/` — GNOME Shell extension (JavaScript)

Native shell integration. Provides the panel indicator and quick-access popover, and — only when the opt-in `experimental-meta-daemon` setting is set (read once in `enable()` via `new GPaste.Settings()`) — hosts the in-process daemon (`GPasteDaemonRunner`, see the meta clipboard backend); by default it hosts no daemon and is a pure client of the standalone one. Communicates with the daemon via D-Bus. Lives under the standard GNOME Shell extension layout with `extension.js` as entry point. **The UUID, `GPaste@gnome-shell-extensions.gnome.org`, claims the domain of the official gnome-shell-extensions bundle, which GPaste is not part of** — against extensions.gnome.org's own rules. Renaming it orphans every user's `enabled-extensions` entry, so it stays until there is a migration to ship with it. `metadata.json` carries the integer `version` that site expects, with the string in `version-name`; meson encodes it as `major * 100 + minor`, since e.g.o refuses a re-upload of a number it already has and the major alone would leave every point release in a series unpublishable. A pre-release names its minor instead of numbering it (`51.beta`), so there is nothing to add: meson maps the name to one of the ten numbers just below `major * 100` from a table (`alpha`/`beta`/`rc`, each with an optional `1` or `2`), which keeps every pre-release under each point release of the series it leads to and keeps them in order among themselves. A name not in that table is a configure-time error rather than a shared number: two pre-releases encoding the same integer means e.g.o refusing the second, so the shell keeps the code of the first. `prefs.js` implements `fillPreferencesWindow()` and adds the pages from `g_paste_gtk_preferences_pages_list()`: the default `getPreferencesWidget()` path wraps whatever it is given in an `AdwPreferencesGroup` inside an `AdwPreferencesPage`, which nested GPaste's own switcher inside a single row of the extensions window. `prompt.js` is the extension's **`GPastePrompt` backend** (`GPasteShellPrompt`, `GObject.registerClass({Implements: [GPasteDaemon.Prompt]})` with `vfunc_passphrase`/`vfunc_migration`): `ModalDialog`s built from `St.PasswordEntry`, `CheckBox` and `BarLevel`, which is what lets the in-shell daemon run the storage migration, unlock and re-key in process instead of shelling out. It renders what the C side hands it — the offered backends and their labels, the import/cleanup sensitivity rules, the libpwquality strength rating — so the two prompt backends cannot drift apart. St has no radio button, so the backend choice is a set of `CheckBox`es kept mutually exclusive by hand, and `BarLevel` is normalized to 0..1 so the 0-4 rating is scaled into it. `enable()` creates the indicator and, in the experimental mode, the runner; that runner must survive the screen lock so the clipboard keeps being recorded, so `metadata.json` declares `session-modes: ["user", "unlock-dialog"]` and the extension stays enabled across the lock (`enable`/`disable` are no longer called on lock/unlock). The panel indicator must **not** be reachable from the lock screen, so it is gated on `Main.sessionMode` (`'updated'` signal): created only in `user` mode — and, when the in-shell runner exists, only once `runner.ready` resolves so a fresh start never activates the standalone daemon over D-Bus (without a runner the indicator is added straight away, and that client call is exactly what activates the standalone daemon) — and torn down whenever the mode leaves `user`. `disable()` tears down the indicator and calls `runner.shutdown()` (which flushes, unowns the name, releases the lock); the standalone daemon then resurrects lazily via D-Bus activation if a client calls. **Reporting the extension's state** (the `track-extension-state` key: "stop tracking the clipboard when the extension does", enforced daemon-side in `g_paste_daemon_methods_extension_state_changed`) has to survive an indicator that cannot do it — there is none outside the `user` mode, and one that never reached a daemon has no client to report through. `shutdown(extensionDisabled)` therefore *returns* whether it reported, and `disable()` reports it itself when it did not, so exactly one of the two reports whichever way it went and neither has to guess about the other. **Hosting the daemon ourselves comes before both**, because neither can work there: both are D-Bus calls dispatched a main loop turn later, and `runner.shutdown()` — the next statement — releases the name and drops the daemon they were addressed to, so the policy would silently never be applied on the one setup where we *are* the daemon. `runner.reportExtensionGone()` calls `g_paste_daemon_extension_state_changed (daemon, FALSE)` directly instead (the same `track-extension-state` policy, factored into `g_paste_daemon_methods_extension_state_changed()` so the D-Bus method and the in-process host cannot drift), and reports whether there was a daemon of ours to tell. That fallback (`_reportExtensionGone()`) calls `ReportExtensionState(false)` **straight on the session bus with `DO_NOT_AUTO_START`**, not through a `GPasteClient` (whose proxy is built with `G_DBUS_PROXY_FLAGS_NONE` and would activate a daemon — being disabled must never be what *starts* one) and **never by writing `track-changes` itself**: whether the extension going away should stop tracking is a policy the daemon owns and already implements, and a client second-guessing it duplicates the `track-extension-state` gate. A `G_DBUS_ERROR_SERVICE_UNKNOWN` back means no daemon is running, so nothing is tracking the clipboard and there was nothing to report to; it is swallowed, anything else is logged. The `extensionDisabled` flag is what keeps the lock screen out of it: tearing the indicator down for a non-`user` mode is not the extension going away, and reporting it there would stop recording for the whole locked session — precisely what the `unlock-dialog` session mode exists to prevent.

**History display** (`indicator.js`): the popover history is an `St.ScrollView` (its `max-height` capped at 60% of the monitor work area) wrapping a `PopupMenuSection`, filled lazily. The batch size is computed at runtime to fill the viewport — `_fillBatch()` returns `page_size / average-row-height + 1` (the average derived from the laid-out content, `upper / loaded`), falling back to `_DEFAULT_BATCH` before anything is laid out. `_loadMore()` appends a batch of `GPasteItem` rows, and the scroll view's `vadjustment` drives growth — `changed` keeps appending while the content does not yet overflow the viewport, `notify::value` appends the next batch when the user scrolls to the bottom — so the whole history is reachable by scrolling (no page switcher). St does not recycle actors, so only the scrolled-to depth is ever materialised; `_listing` — one `GCancellable`, replaced by every pass that repopulates the list — is what keeps overlapping reloads apart, and rows are `destroy()`ed on reload. **Cancelling is what stops the work**, not merely the repaint: the search entry asks again on every keystroke, so without it the daemon matched a term per character typed for a list that was only ever going to show the last one. (We deliberately do *not* use `PopupSubMenu`: it is the same `St.ScrollView` primitive but as a click-to-expand "More…" submenu whose scroll is tied to the top menu's max-height, and it holds every item with no virtualisation — so it would force an expander UX and lose the lazy loading.) Because the section is nested in the scroll view (not the menu's item tree), each row's `activate` is wired to `menu.itemActivated()` by hand to close the menu.

**Following the daemon** (`indicator.js`): what says there is one is the `history` property, not the bus name — both daemons own the name *before* building the object that serves it, so a proxy's `GetAll` on a new owner finds nothing at that path and the cache stays empty until the daemon's own `PropertiesChanged` a moment later. `notify::history` carries both edges (the proxy invalidates every cached property when the name loses its owner and fills them again once there is something to fill them from), so the indicator watches that and answers a daemon leaving by clearing the rows, hiding the tracking switch — offered with no daemon there it would either fail unreported or quietly start one — and starting a ladder of probes at 1, 2, 4 … 64 seconds, a little over two minutes, which covers a re-exec, an upgrade or a manual restart. **A scheduled probe never activates the daemon**: a probe is an ordinary method call, which is also what bus-activates one, so it waits for the name to have an owner before it asks — a ladder that activated on its own would put back the daemon the user had just stopped, within a second of their stopping it, with no way to suppress it short of turning the extension off. `report_extension_state()` is such a call too, so it goes out only while there *is* a daemon, and `_onDaemonAppeared()` is what reports it to one that turns up later. Only the latest probe's reply steps the ladder (`_probe`, a cancellable of its own): a retry landing while a scheduled probe is still awaiting its call restarts the ladder, and the overtaken probe stepping it on its way out would walk it twice per click and spend it well before the two minutes it covers. Cancelling the overtaken one un-activates nothing — a daemon is bus-activated by the message having been sent, not by the reply being read. **Past the last rung the placeholder row is the way back**: it becomes sensitive — which is also what makes a menu item reactive and reachable by the keyboard — shows a second label reading "Retry" beside the state's own, and starts the ladder over. **It answers in place**, emitting a `retry` signal of its own rather than the `activate` every `PopupMenuBase` listens for and dismisses on: closing the menu would take away the row that is about to report what the retry did. So the row says "Loading…" the moment the offer is taken — before anything goes out on the bus, and it stops being an offer while that is in flight — and whichever of `_onDaemonAppeared()` and the probe's own tail answers paints the outcome over it. The offer is that separate label rather than a few words on the end of the state text, because the two are not one sentence and a translation of "GPaste daemon not running" stops being one the moment something else is appended to it; and it is a label rather than a button, the row itself being what activates — a second focus target inside it would take over the keyboard navigation a menu item gives for free. Being an offer and being reactive are the same state, so the label follows the sensitivity `_showState()` is already given. That is also the answer for a daemon that owns the name and never exports anything (an export failure, or a passphrase dialog nobody answers): "Loading…" is the honest label while the ladder runs, and a row that only ever says it is not one the user can do anything with, so the spent ladder turns it into the offer whatever the name owner says. `_setup()` guards its own re-entry, `_connect()` retrying for seconds before it assigns `this._client`: a second run started in that window would build a second switch, search row, scroll view and footer into the same menu. That window is a loading state too, and `_connecting` is what says so: there is no proxy yet, hence no name to have an owner, and a row offering a retry there is one `_retry()` would refuse. **A reload whose fetch gives up reconciles the connection state** rather than returning into a menu nothing repaints: `_rebuild()` is the only caller of `_updateVisibility()` on that path, and the reason `_fetchAvailable()` gave up is a daemon that is no longer there to ask, so `_reload()` and `_refresh()` put the question to `_onDaemonStateChanged()` — unless a newer reload has cancelled theirs, in which case it is that one's to answer. Giving up covers a call that *failed* as much as one with nothing to ask: `_fetchAvailable()` catches the size call itself, the bus name having an owner being no promise that the daemon answers, since an exception escaping it would carry straight past the reconciliation to the `.catch(console.error)` at the top. **Those two are not the same repaint**, though, which is why `_onDaemonStateChanged()` answers whether the state actually moved: a daemon that has gone is a change and it repaints the whole menu for one, where a daemon still sitting there that simply did not answer changes nothing to reconcile — so `_reconcileConnection()` clears the rows itself in that case rather than leaving them describing a history the pass could not size, and the next menu opening, `update` or keystroke asks again. It is also guarded on `_destroyed` like every other path resuming after an `await`: a reload, refresh or filter suspended on its call can resume past a teardown, and `_onDaemonGone()` would then set properties on destroyed actors and schedule a reconnect `_cancelReconnect()` has already run past. `_runFilter()` reconciles for itself, the match or the favourites being its own call to lose. Teardown sets `_destroyed` from the `destroy` handler and not only from `shutdown()`, since the actor can be destroyed by other routes and a probe suspended on its call would otherwise resume past it and schedule a timeout nothing is left to cancel. It cancels `_listing` and `_probe` there too: the flag stops the reply from being acted on, where the cancel stops the daemon matching a search for a menu that has gone. **`_connect()`'s own backoff is a tracked source** (`_sleepBeforeRetry()`/`_cancelConnectRetry()`) rather than a `setTimeout`, so a teardown during one has something to remove instead of leaving a timer running against an extension that is gone — and cancelling it *resolves* the promise rather than dropping it, or `_connect()` would hang for good on a source that no longer exists, holding the indicator with it. `GPaste.Client.new()` takes no cancellable, so the attempt itself still runs to its end; `_destroyed`, read the moment the sleep returns, is what stops the ladder.

**The footer** (`actions.js`) is two plain `PopupMenuItem`s — Open GPaste, Preferences — added under a separator. They used to be `St.Button`s in one *non-reactive* `PopupBaseMenuItem`, through which no key event ever bubbled, so the indicator answered Left, Right and Up itself from the menu actor to move a focus the buttons could not move on their own. Menu items navigate themselves; the one step left by hand is Up from the first of them to the last history row, which is not in the menu's item tree. There is no About: a panel menu is not where an application's about dialog belongs. Nor is there Empty History any more: a history's right click in the switcher empties any history, not only the one in use.

**The history switcher** (`historySwitcher.js`) is the row naming the history in use, which expands in place into the chooser: every history with how many items it holds, the current one wearing `Ornament.DOT` — the shell's own mark for one of a mutually exclusive set — and, last, an entry to switch to or create one, stretched across the row as the search entry spans the menu. **Both of the chooser's entries confirm the same way** (`addConfirmMark()`): Enter, or a click on a mark at the entry's end — `go-jump-symbolic` for switching, the graphical tool's own suffix button, and `object-select-symbolic` for a backup, libadwaita's entry-row apply mark — since nothing about a bare entry says Enter is what confirms it. The mark is the St entry's secondary icon, as the search entry's clear icon is, and like that icon it is **only shown while confirming would act**: an entry holding a name that would be held back offers nothing to click in vain. It sits **below the tracking switch and above the search entry**: the switch is global state that belongs to nothing under it, where the history row names what everything under it — the search and the list both — is about, so the menu reads global then scoped instead of the global control splitting the group the other three make. That is also the billing the graphical tool gives the two, its history selector being the sidebar while tracking sits in the hamburger menu. It is a `PopupSubMenuMenuItem`, whose `activate()` toggles the submenu rather than emitting `activate`, so expanding it does not dismiss the menu; **its rows do the same by hand**, emitting a `switch` signal of their own for the reason the placeholder row emits `retry` — `PopupMenuBase` answers `activate` with `itemActivated()`, and the menu is meant to stay open on the history just switched to. Nothing reloads the item list for a switch: `SwitchHistory` writes the `history-name` setting, and the load it sets off ends in `emit_update (REPLACE, ALL)`, which `_update()` already answers. The **label follows `notify::history`** while the **open list is re-asked from `histories-changed`** (and `history-emptied`): a backup creates a history without making it current, which no change of the property can express, and an empty changes a count without changing the set — `history-deleted` needs no listing of its own, the daemon following it with `histories-changed`. **Rebuilding or folding never strands the keyboard**: a destroyed or hidden actor drops the key focus, so `refresh()` hands it back to the row for the same history (or the switcher row when that one is gone), and a switch hands it to the switcher row before folding, as the shell's own Left key does. `ListHistories` answers every name with its size, so the whole submenu costs one round trip; it is asked on each chooser expansion, and **only ever with a daemon there**. File-backed counts parse inactive histories synchronously, so opening the panel alone must not enumerate them. While the chooser is open, set changes re-list it; the current row’s count is the switcher’s own to ask, with `GetHistorySize` (the length of the loaded history, which costs nothing like a listing), on every `update` that can change it — target `ALL`, or `REMOVE` — and after any listing that does not name the history in use, as the `none` storage lists nothing. It is not borrowed from the indicator’s call for the list below: a filtered list asks none, and a filter pass can cancel one in flight. A size and a listing land in the order they were asked, so the last to land is the newer count. Reopening also picks up external file changes — an ordinary method call is also what bus-activates a daemon, so the row is hidden along with the switch while there is none, and `vfunc_hide()` folds the submenu away because that submenu is a child of the menu in its own right rather than of the row, and hiding the row would otherwise leave its list standing with nothing above it. Two things are read off libgpaste rather than restated, a copy being one that drifts from what the daemon enforces: the default history name (`GPaste.DEFAULT_HISTORY` — `G_PASTE_DEFAULT_HISTORY` lives in the installed `gpaste-util.h` rather than being a compiler flag for exactly that reason) and what makes a name valid (`GPaste.util_history_name_is_valid()`, installed beside it while the path builders it guards stay in the uninstalled `gpaste-daemon-util.h`). The second is asked before anything is sent because a panel menu has nowhere to report a refusal in, and the entry keeps what was typed so it can be amended. **A history row deletes its history** the way an item row deletes its item — a bin shown on the row being looked at, and Delete or BackSpace from a binding pool — and **the switcher row deletes the history in use** with the same bin and the same keys, since reaching that history's own row takes expanding the chooser — the bin placed ahead of the shell's arrow, right after the `popup-menu-item-expander` found by the style class the theme knows it by rather than through the shell's private `_triangleBin`; all of them go through a **confirmation**, a shell `ModalDialog` worded as the graphical tool's (so its msgids arrive translated): a history takes everything it holds with it. The dialog closes the panel menu first, since a modal cannot take its grab from under an open one, and nothing is redrawn on a yes: `history-deleted` refreshes the list and deleting the current history switches to the default one. With the menu closed on it, a refusal from the daemon has nowhere to go but the log (`logFailure()`). **The switcher closes a dialog still up when it is hidden or destroyed**: the dialog lives in the shell's modal group, not under the row, so it would otherwise outlive the extension, grab and all, still able to act on the daemon. The bin is the same `GPasteDeleteButton` item rows use, which is only its look — each row answers `clicked` with the call its Delete key makes. On a history row it sits **ahead of the count**, the label being what gives up the room: shown and hidden with the hover, a bin after the count would push it left and back on every row the pointer crosses. It is **not focusable** there and shows on `hover || active`, and a focusable bin would need `item.js`'s stage focus watcher to survive being tabbed into for nothing the Delete key does not already do. **The pointer never takes the key focus on these rows**: `PopupBaseMenuItem` binds `hover` to `active` and grabs the focus when `active` turns on, so crossing a row would take the keyboard from the search entry or a chooser entry, and BackSpace would then delete a history. A history row passes `hover: false`, as `GPasteItem` does (#435); `PopupSubMenuMenuItem` takes no parameters, so the switcher row overrides the `active` accessor to refuse any value that does not match `has_key_focus()`. Only holding back the grab would not do: the pointer would still turn `active` on, and the menu would deactivate the row that does have the keyboard, leaving Delete acting on a row nothing shows. Clutter records the focus before emitting key-focus-in and key-focus-out, so the row's own handlers always get through. **A right click on a history row** (or the menu key, St's `popup-menu`) opens **Empty, Back Up and Delete inline, under that row** (Delete through the same confirmation as the row's bin), rather than a popup menu that would need a grab of its own inside the open one; the same row again folds them away. The right click is a `ClickGesture` on `BUTTON_SECONDARY` recognised on press: a recognising gesture cancels the others on the same points, which is what keeps the row's own click gesture — it takes any button — from switching on the release. It is **one `GPasteHistoryActionsItem`, moved and hidden** rather than one built per click, because what hides it is its own buttons and an actor is not to be destroyed from its child's handler; it is built ahead of the entry, so once the rows are cleared it sits right before the entry and rows added at their own count still land ahead of both — and `refresh()` moves it back below its source row after rebuilding. Refresh preserves the backup draft and its focus while that history exists; disappearance of the source hides and resets it. Empty asks when `empty-history-confirmation` is set, through the same `ModalDialog` as Delete (`GPasteHistoryConfirmationDialog`, worded as the graphical tool's empty confirmation) rather than by starting the graphical tool just to ask — which was all `g_paste_util_empty_with_confirmation()` and the UI's `empty` action behind it were there for, so both are gone; without the setting it empties at once and the menu stays open, and a refusal is logged either way. Back Up swaps the buttons for an entry prefilled `<history>_backup` (the graphical tool's offer), holding back a name `GPaste.util_history_name_is_valid()` refuses as the switching entry does, **and a name the list already holds** (a predicate the switcher hands the actions item, so the mark follows it too): `BackupHistory` refuses a taken name and a panel menu has nowhere to say so, so the entry would otherwise fold away as if the copy had been made (a refusal a stale list lets through is logged). The copy is listed by the `histories-changed` it causes. **Escape swaps the buttons back**, the focus on Back Up, as Cancel answers the graphical tool's dialog. Nothing on the entry can see that key first: the shell's `PopupMenuManager` closes the menu from a `Clutter.KeyController` it adds, in the **capture** phase, to the top menu's actor — the grab actor, so the top of every key's path — so the switcher is handed the top menu and adds its own capture controller to that same actor once, for good. Actions on one actor run in the order they were added, and the manager re-adds its controller on every open, so ours runs first from the next open on; it stops only an Escape while the key focus is in the backup entry. The mark is re-checked when a refresh rebuilds the list, since a taken name can change under unchanged text. Confirmation callbacks also check name ownership.

**Row previews** (`item.js`): a row shows what it holds next to its text — an image thumbnail, a colour swatch, nothing else — in one `St.Bin` slot (an item is never both, and an empty bin takes no room), sitting **between the index and the label**, for the reason `GPasteUiItem`'s does: the label is the row's only expanding child, so it is the one the pin and delete buttons take their width from when they appear, and everything ahead of it keeps its place. The image bytes come from `GetImage`, for the reasons the D-Bus section gives; the colour is read straight off the item, its value being the colour itself. That read gets a cancellable of its own, `_preview`, beside the `_fill` the row's own content read goes out on — St does not recycle actors, but a row *is* refilled in place on reload, and a reply for the item it used to hold must not paint it, nor cost its bytes over the bus on the way. **Two rather than one** — where `GPasteUiItem` needs a single `fill` — because `setImagesPreview()` re-runs `_updatePreview()`: a preview is read again with the row's own binding standing still, so the row's cancellable would not have moved and both reads would think themselves current. A thumbnail is an `St.Icon` over a `Gio.BytesIcon`: `st_icon_theme_lookup_by_gicon_for_scale()` has a `G_IS_LOADABLE_ICON` branch, and the load ends in `gdk_pixbuf_new_from_stream_at_scale (stream, size, size, TRUE)` — scaled into `icon_size` with its aspect ratio kept, so nothing has to be decoded in JS. It is loaded *uncached* (`ST_TEXTURE_CACHE_POLICY_NONE`), because `g_icon_to_string()` cannot serialize a `GBytesIcon` into a cache key — one decode per fill of a row, which is what a handful of image rows costs and the reason not to reach for this for anything bigger. A swatch is an `St.Widget` with an inline `background-color` and an outline spelled out rather than themed: the graphical tool's swatch takes that line from Adwaita's `.frame`, but that class belongs to GTK — the shell stylesheet defines nothing like it, and St's CSS supports neither `currentColor` nor `color-mix()` to rebuild it from. So the two swatches are drawn by different means on purpose, and only the GTK one follows the theme. The shell one interpolates the item's value into an inline style, and that value reached a colour item only because `gdk_rgba_parse()` accepted it — so it is a colour and not arbitrary text. `_showColor()` checks its shape anyway before building the declaration, because what it goes into is a stylesheet and something off the clipboard has no business ending one early. It is outlined in a fixed mid-grey rather than the theme's foreground, which a swatch cannot ask for before it has a theme node, and sized by a constant rather than by `images-preview-size`: turning image previews off must not take the colours with it. The two image-preview settings are watched **once, by the indicator**, which pushes them into every row (`setImagesPreview()`) as it does the element size — one subscription for the menu instead of one per row — and `_createRow()` pushes them into a new row straight away, before its constructor's async fetch can land.

**Row actions** (`item.js`): the pin and delete buttons are laid out and revealed as `GPasteUiItem`'s are — bin first, star **last**, both hidden until the row is the one being looked at, the star staying out on a pinned item because there it is a badge rather than a button, and only the last child of the row keeping its place when the one before it appears. What differs is what "being looked at" means and what hides them. The row is built with `hover: false` (it must not steal key focus from the search entry, Fix #435), so `PopupBaseMenuItem` does not bind hover to `active` and neither property alone covers both input paths: `active` is the row the keyboard is on, `hover` the row the pointer is on, and `_updateActionsVisibility()` watches `notify::` on both. **A button of the row counts as the row.** Both are `St.Button`s and so focusable, and `PopupBaseMenuItem`'s `vfunc_key_focus_out()` clears `active` with no exemption for its own children — so tabbing into the bin would hide the very button the keypress reached, and an unmapped actor is one Clutter drops key focus for, stranding the keyboard on nothing. **Where the keyboard is is therefore asked of the stage**, and answered once the move has settled: `global.stage`'s `notify::key-focus` is emitted after the new focus has been recorded, and `_updateActionsVisibility()` puts `contains()` to the row. The actors' own focus signals cannot answer it — `key-focus-out` on the row and `key-focus-in` on the button both run *mid-move*, the stage still naming the actor being left, so nothing either of them can see tells "leaving this row" from "arriving at one of its buttons". **One connection serves every row.** `focusWatcher` (`item.js`) holds a single `notify::key-focus` handler and a count of the live rows, and updates only the row the focus left and the row it arrived on — both named by the focused actor's own ancestry. A connection per row would instead run a handler, and an ancestor walk, on each of the several dozen rows the menu keeps alive, for every focus move anywhere in the shell. Rows count themselves out on Clutter's `'destroy'` **signal**, never in the `destroy()` method: that is a plain JS method, which a teardown reaching the actor through its parent skips, leaving a stage handler connected for the session and the row alive behind it. The last row out disconnects the stage. `hover` still works despite that constructor argument — `track_hover` follows `reactive`, and `st_widget_leave()` ignores a crossing into a descendant, so moving the pointer onto a button does not un-hover the row under it. And they are hidden by their own `visible` rather than wrapped in the equivalent of a `GtkRevealer`: what a revealer buys there is a row that keeps a button's height while showing none, and here the row's height is its label's either way — a line of menu text is taller than a 16px symbolic icon, and the ornament that would otherwise set a floor is `Ornament.HIDDEN` on these rows.

## JavaScript conventions

The `src/gnome-shell/` extension follows upstream GNOME Shell's JS conventions, enforced by the **same tooling, layout, and configuration** as upstream:

- The npm project lives in `tools/` (`tools/package.json`, `tools/package-lock.json`, `tools/eslint.config.js`), mirroring gnome-shell. The repo-root `eslint.config.js` is a **symlink** to `tools/eslint.config.js`.
- **ESLint** with [`eslint-config-gnome`](https://gitlab.gnome.org/World/javascript/eslint-config-gnome) (`recommended` + `jsdoc` configs) and the [`ci-run-eslint`](https://gitlab.gnome.org/World/javascript/ci-run-eslint) runner, both pinned to the same commits upstream uses. The config mirrors upstream's custom rule overrides (`camelcase`, `consistent-return`, `eqeqeq: smart`, `key-spacing`, `prefer-arrow-callback`, `prefer-const`, jsdoc tweaks). Shell-extension globals (`global`, `_`, `C_`, `N_`, `ngettext`) are declared for `src/gnome-shell/**`.
- Style basics live in `src/gnome-shell/.editorconfig` (LF, UTF-8, trim trailing whitespace, 4-space indent for `*.js`).
- Run it with `tools/run-eslint.sh` — exactly the upstream wrapper. It `npm clean-install`s into `tools/` on first run, symlinks `node_modules` into the repo root for import resolution, then lints `src/gnome-shell`. Pass `--fix` to auto-fix formatting.
- The same script is the single entry point everywhere: the meson `eslint` test (`meson test -C build eslint`, skipped when `npm` is absent) and the GitHub Actions workflow (`.github/workflows/eslint.yml`, runs on pushes/PRs touching the JS or tooling) both invoke it. Code conventions (also following upstream):
- **Don't version-pin core `gi://` imports** — write `gi://GObject`, `gi://GLib`, `gi://Gio`, `gi://Pango`, `gi://Clutter`, `gi://St`. Only pin typelibs that genuinely ship multiple versions: `gi://GPaste?version=3`, `gi://GPasteDaemon?version=1`, `gi://GPasteGtk?version=4`.
- **Manage signal lifecycles with `connectObject`/`disconnectObject`** (owner = `this`) for connections to long-lived non-actor GObjects (settings, the `GPaste.Client`, the daemon runner's bus and daemon), rather than tracking handler ids and disconnecting them by hand. They auto-disconnect when the owner actor is destroyed; an owner that is *not* an actor — `GPasteDaemonRunner`, a plain class — gets no such teardown, so it must still call `disconnectObject(this)` itself (`daemon.js` does, from `_teardownBus()` and `_releaseDaemon()`).
- **Use a standard `constructor()` (calling `super(...)`) in `GObject.registerClass` classes**, not `_init()`/`super._init()`. GJS bridges to the `_init()`-based shell/St/Clutter base classes transparently (positional args like `super(0.0, 'GPaste')` and property dicts like `super({...})` both work).
- **Handle keys with `Clutter.KeyController` or a `ClutterBindingPool`, never `'key-press-event'`/`'key-release-event'` or `vfunc_key_press_event()`.** GNOME 51 finished moving the shell off raw Clutter event signals: `st_focus_manager_navigate_from_event()` is gone, `PopupBaseMenuItem` no longer overrides `vfunc_key_press_event()`, and `PanelMenu.Button._onMenuKeyPress()` now takes no arguments and reads the key from `this._keyController.get_key()`. That last one landed in 51.rc, while 51.beta still connects `'key-press-event'` and calls the method with `(actor, event)` — an override of it therefore forwards `...args` to `super` and reads the key from the event it was handed, falling back to `Clutter.get_current_event()` — which is what upstream reads, but answers `null` outside an event dispatch, so neither spelling may be assumed to have one and an unnameable key simply chains up. Bind a fixed key on an actor with a binding pool (`item.js`); watch the keyboard across a whole subtree — several keys, or the modifier state — with a controller added to the root actor (`indicator.js`, `this._indexKeyController` on `this.menu.actor`). Prefer the controller's `'modifier-change'` signal plus `get_state()` over tracking `Clutter.KEY_Control_L`/`_R` by hand: it also reports latched and locked modifiers.
- **A class that installs a binding pool registers itself in a `static {}` block**, `static { GObject.registerClass(this); const bindingPool = this.get_binding_pool(); … }` (the meta-info object, `Signals` and the like, going first when there is one: `GObject.registerClass({…}, this)`) — the pool is per-class and only exists once the class does. `StWidget` then installs a key controller on every instance whose type chain has a pool, and that controller walks the chain from the instance's own type upward, so a subclass's bindings are consulted before its parent's. Every other class keeps the plain `GObject.registerClass(class … )` form; upstream converted only the classes that needed a pool.

Async / `Gio._promisify` conventions (these bit us — keep them):
- **`Gio._promisify` works on instance methods (`SomeClass.prototype`) but NOT on anything static** — neither a constructor (`SomeClass.new`) nor a namespace-level function (`SomeNamespace.foo_async`) — **inside gnome-shell.** The wrapper assignment silently fails to stick on the class object (it works in standalone `gjs`, so it is easy to miss), and the *raw* introspected `new` then throws *"At least 1 argument required, but only 0 passed"* when awaited with no args. Even where the assignment does stick, the wrapper's body reads `this[originalFuncName]`, which is a `TypeError` when the wrapper is called unbound — which is what calling it off a plain value in a strict-mode ES module does. Promise-wrap the raw `_async` + `_finish` pair by hand instead — see `_connect` in `indicator.js` and `callStorageConcern` in `daemon.js`. `dependencies.js` promisifies only the instance methods.
- **Pass the cancellable, not a trailing `null`.** `GPaste.Client`'s async methods are `(…args, cancellable, callback, user_data)`, so a promisified call ends at the cancellable: `await client.get_history_size(cancellable)`. One `null` there is legal and means "no cancellable"; a *second* trailing `null` lands in the callback slot and defeats `Gio._promisify` (the call hangs or returns `undefined`), which is also what one `null` does on a method taking no cancellable at all — `GPaste.Client.new`, and the `GPasteDaemon.storage_*_async` concerns. Every awaited read in the extension has one: `dependencies.js` exports `replaceCancellable()` (cancel the request in flight, hand back the one its successor goes out on) and `awaitReply()` (await the reply and say whether it is still wanted), and they sit beside the `_promisify` calls because they are the same subject. **Both halves of `awaitReply()` are needed**: cancelling fails the call, arriving as a rejection of `G_IO_ERROR_CANCELLED`, but it does not unqueue a reply already on its way, so the question is also put to the cancellable *the request went out on* — an `async` function's own local, where the C rows need callback data to carry it.
- **`GLib.idle_add_once` / `GLib.timeout_add_once` take `(priority, func)`**, not `(func)`. Passing only the callback makes GJS treat the callback as the priority and dispatch with no function → *"callback is not a function"*. Always pass an explicit priority (e.g. `GLib.PRIORITY_DEFAULT_IDLE`) and keep the `GLib.Source.set_name_by_id(...)` wrapper.
- **Keep the id of every source you add, and remove it on teardown.** A source outlives the object that scheduled it, so an idle or timeout left behind runs against a destroyed actor or a disabled extension — the id is the only handle there is. `daemon.js` is the model (`_reconnectId`, and `_pending` for the deferred jobs, all removed in `shutdown()`); `indicator.js` has `_reconnectId`, `_connectRetryId` and `_selectSearchId`, each with its own `_cancel*()` called from `_onDestroy()`. A `*_once` source must clear its own id from inside its callback, or the cancel would remove an id that has already fired. Do not reach for `setTimeout` to skip this: it is a GLib source too, just one with no id to hold.
