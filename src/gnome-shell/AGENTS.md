# `src/gnome-shell/` — GNOME Shell extension (JavaScript)

The panel indicator and its menu, a client of the daemon over D-Bus — and, only when the opt-in `experimental-meta-daemon` setting is set (read once in `enable()`), the host of the in-process daemon (`GPasteDaemonRunner`, `daemon.js`, see [`src/libgpaste/gpaste-daemon/AGENTS.md`](../libgpaste/gpaste-daemon/AGENTS.md)). The standard extension layout, `extension.js` as entry point. The files are commented throughout; this is the map and what spans them.

## Packaging

- **The UUID, `GPaste@gnome-shell-extensions.gnome.org`, claims the domain of the official gnome-shell-extensions bundle**, which GPaste is not part of, against extensions.gnome.org's rules. Renaming it orphans every user's `enabled-extensions` entry, so it stays until there is a migration to ship with it.
- **`metadata.json` carries an integer `version`** for extensions.gnome.org and the string in `version-name`. `meson.build` encodes it as `major * 100 + minor`, a pre-release (`51.beta`) taking one of the ten numbers just below `major * 100` from a table (`alpha`/`beta`/`rc`, each with an optional `1` or `2`); a name not in the table is a configure-time error. Its comment says why.
- **`prefs.js` implements `fillPreferencesWindow()`** with the pages from `g_paste_gtk_preferences_pages_list()`, so the extensions window switches between them itself.
- **`prompt.js` is the `GPastePrompt` backend** (`GPasteShellPrompt`, `GObject.registerClass({Implements: [GPasteDaemon.Prompt]})`, `vfunc_passphrase`/`vfunc_migration`): `ModalDialog`s of `St.PasswordEntry`, `CheckBox` and `BarLevel`, rendering what the C side hands it. St has no radio button, so the backends are `CheckBox`es kept exclusive by hand, and the 0-4 rating is scaled into `BarLevel`'s 0..1.

## Enabling, the lock screen and the extension's state

- `enable()` creates the indicator and, in the experimental mode, the runner, which must keep recording through the lock: `metadata.json` declares `session-modes: ["user", "unlock-dialog"]`, so lock and unlock never reach `enable()`/`disable()`. **The indicator must not be reachable from the lock screen**: `Main.sessionMode`'s `updated` creates it only in `user` mode — with a runner, only once `runner.ready` resolves, so a fresh start never activates the standalone daemon (without one, adding the indicator is exactly what activates it) — and tears it down whenever the mode leaves `user`.
- `disable()` tears down the indicator and calls `runner.shutdown()` (flush, unown the name, release the lock); the standalone daemon comes back through D-Bus activation when a client calls.
- **Reporting the extension's state** (`track-extension-state`, enforced daemon-side in `g_paste_daemon_methods_extension_state_changed()`) happens exactly once, in `extension.js`, whose comments give the reasons: the runner's daemon is told directly first (`runner.reportExtensionGone()` → `g_paste_daemon_extension_state_changed (daemon, FALSE)`), since a D-Bus call would reach it after `shutdown()`; otherwise the indicator's `shutdown(extensionDisabled)` reports and says whether it did; otherwise `_reportExtensionGone()` calls `ReportExtensionState(false)` on the bus with `DO_NOT_AUTO_START`, never through a `GPasteClient` (whose proxy would activate a daemon) and never by writing `track-changes`. `G_DBUS_ERROR_SERVICE_UNKNOWN` is swallowed, anything else logged. `extensionDisabled` keeps the lock screen out of it: dropping the indicator for a non-`user` mode is not the extension going away.

## The indicator (`indicator.js`)

- **The history is an `St.ScrollView`** (`max-height` 60% of the monitor work area) around a `PopupMenuSection`, filled lazily: `_fillBatch()` is `page_size / average-row-height + 1` (the average being `upper / loaded`, `_DEFAULT_BATCH` before layout), `_loadMore()` appends a batch, and the `vadjustment`'s `changed` (until the content overflows) and `notify::value` (at the bottom) drive growth. St does not recycle actors, so only the scrolled-to depth exists; rows are `destroy()`ed on reload. **`_listing`**, one `GCancellable` replaced by every pass repopulating the list, keeps overlapping reloads apart and stops the daemon matching a search per keystroke. `PopupSubMenu` is deliberately not used: the same primitive as a click-to-expand submenu, scrolling with the top menu's max-height and holding every item, which would cost the lazy loading. The section being outside the menu's item tree, each row's `activate` is wired to `menu.itemActivated()` by hand.
- **Following the daemon**: the `history` property, not the bus name, says there is one (both daemons own the name before serving it), and `notify::history` carries both edges. A daemon leaving clears the rows, hides the tracking switch and the history switcher (a call there would bus-activate one), and starts a probe ladder at 1, 2, 4 … 64 s. **A probe never activates the daemon**: it waits for the name to have an owner, and `report_extension_state()` likewise goes out only to a daemon that is there (`_onDaemonAppeared()` reports to one turning up later). Only the latest probe (`_probe`, its own cancellable) steps the ladder.
- **Past the last rung the placeholder row offers a retry**: it turns sensitive (hence reactive and keyboard-reachable), shows a separate "Retry" label beside the state text (the two are not one sentence to translate, and a label rather than a button keeps the menu item's own navigation), and emits a `retry` signal of its own rather than `activate`, which would close the menu. It reads "Loading…" as soon as the offer is taken, and the spent ladder makes it the offer whatever the name owner says, covering a daemon that owns the name and never exports anything.
- **Re-entry and teardown**: `_setup()` guards its own re-entry while `_connect()` retries (`_connecting` being a loading state with no proxy yet, where a retry offer would be refused). A reload or refresh whose fetch gives up — `_fetchAvailable()` catching a failed size call too — asks `_onDaemonStateChanged()`, unless a newer reload cancelled it; that answers whether the state moved, and when it did not `_reconcileConnection()` clears the rows itself. `_runFilter()` reconciles for itself. Every path resuming after an `await` checks `_destroyed`, set from the `destroy` handler (not only `shutdown()`), which also cancels `_listing` and `_probe`. `_connect()`'s backoff is a tracked source (`_sleepBeforeRetry()`/`_cancelConnectRetry()`) whose cancel resolves the promise; `GPaste.Client.new()` takes no cancellable, so `_destroyed` is read when the sleep returns.
- **The footer** (`actions.js`) is two `PopupMenuItem`s under a separator — Open GPaste, Preferences — which navigate themselves; the one step by hand is Up from the first to the last history row, outside the menu's item tree. There is no About (not a panel menu's place) and no Empty History (a history's right click in the switcher empties any history).

## The history switcher (`historySwitcher.js`)

The row naming the history in use, a `PopupSubMenuMenuItem` expanding in place into every history with its count, the current one wearing `Ornament.DOT`, and last an entry to switch to or create one. Its comments carry the reasons; the shape:

- **It sits below the tracking switch and above the search entry**: global state first, then the history everything below is about — the billing the graphical tool gives the two.
- **Both chooser entries confirm alike** (`addConfirmMark()`): Enter, or the entry's secondary icon — `go-jump-symbolic` to switch, `object-select-symbolic` for a backup — shown only while confirming would act.
- **Rows switch without closing the menu**, emitting a `switch` signal of their own. Nothing reloads the item list: `SwitchHistory` ends in `emit_update (REPLACE, ALL)`, which `_update()` answers. The label follows `notify::history`; the open list is re-asked on `histories-changed` and `history-emptied`.
- **Rebuilding or folding never strands the keyboard**: `refresh()` hands the focus to the same history's row (or the switcher row), and a switch hands it to the switcher row before folding.
- **Listing**: `ListHistories` costs one round trip, asked on each expansion and **only with a daemon there**, since file-backed counts parse inactive histories synchronously. The current row's count is asked with `GetHistorySize` on every `update` that can change it (`ALL` or `REMOVE`) and after a listing not naming the history in use (the `none` storage lists nothing), never borrowed from the indicator's call, and replies land in the order asked. With no daemon the row is hidden, and `vfunc_hide()` folds the submenu, which is a child of the menu rather than of the row.
- **Read off libgpaste, never restated**: `GPaste.DEFAULT_HISTORY` and `GPaste.util_history_name_is_valid()`, the latter asked before sending anything, the entry keeping what was typed.
- **Deleting**: a history row's bin (`GPasteDeleteButton`, only a look; each row answers `clicked` with its Delete key's call) and Delete/BackSpace from a binding pool delete that history; the switcher row does the same for the history in use, its bin placed right after the `popup-menu-item-expander` found by style class. On a history row the bin is ahead of the count, not focusable, shown on `hover || active`. Every delete goes through a confirmation `ModalDialog` worded as the graphical tool's; it closes the panel menu first, redraws nothing on a yes, logs a refusal (`logFailure()`), and is closed if the switcher is hidden or destroyed.
- **The pointer never takes the key focus**: history rows pass `hover: false` (#435), and the switcher row overrides the `active` accessor to refuse any value not matching `has_key_focus()`.
- **A right click** (a `ClickGesture` on `BUTTON_SECONDARY` recognised on press, or the menu key, St's `popup-menu`) opens Empty, Back Up and Delete inline under the row, as one `GPasteHistoryActionsItem` moved and hidden rather than rebuilt (built ahead of the entry; `refresh()` moves it back under its row, preserving a backup draft and its focus while that history exists). Empty confirms when `empty-history-confirmation` is set (`GPasteHistoryConfirmationDialog`). Back Up offers an entry prefilled `<history>_backup`, holding back an invalid name and one the list already holds (a predicate handed in by the switcher), the mark following it and being re-checked on refresh. **Escape swaps the buttons back**, through a capture `Clutter.KeyController` the switcher adds once to the top menu's actor — the grab actor, where the shell's `PopupMenuManager` closes the menu — acting only while the backup entry has the focus: nothing on the entry sees the key first, and since actions on one actor run in the order they were added and the manager re-adds its controller on every open, ours runs first from the next open on. Confirmation callbacks also check name ownership.

## Rows (`item.js`)

- **Previews** — an image thumbnail or a colour swatch — share one `St.Bin` **between the index and the label**, as in the graphical tool. Their read has its own cancellable, `_preview`, beside the row's `_fill`, since `setImagesPreview()` re-reads a preview with the row's binding unchanged. A thumbnail is an `St.Icon` over a `Gio.BytesIcon` of `GetImage`'s bytes — `st_icon_theme_lookup_by_gicon_for_scale()` loads a `G_IS_LOADABLE_ICON` through `gdk_pixbuf_new_from_stream_at_scale()`, aspect kept, so nothing is decoded in JS — loaded uncached (`g_icon_to_string()` cannot key a `GBytesIcon`) — one decode per fill, fine for a handful of rows. A swatch is an `St.Widget` with an inline `background-color`, its shape checked by `_showColor()` before it goes into a stylesheet, outlined in a fixed mid-grey (St has no `.frame`, `currentColor` or `color-mix()`), and sized by a constant. The indicator watches the two image-preview settings once and pushes them into every row (`setImagesPreview()`), `_createRow()` doing so before a row's first fetch can land.
- **Pin and delete** are laid out as `GPasteUiItem`'s — bin first, star last, a pinned star always shown as a badge — but shown when the row is `active` (keyboard) or `hover` (pointer), the row being built with `hover: false` (#435); `hover` still works since `track_hover` follows `reactive` and `st_widget_leave()` ignores crossing into a descendant. **A button counts as the row**: where the keyboard is is asked of `global.stage`'s `notify::key-focus`, once the move has settled, by **one shared `focusWatcher`** updating only the rows the focus left and reached, rows counting themselves out on Clutter's `'destroy'` signal (never the `destroy()` method, which a teardown through the parent skips). They are hidden by `visible` rather than a revealer, a line of menu text being taller than a 16px icon and the ornament `Ornament.HIDDEN`.

## JavaScript conventions

The `src/gnome-shell/` extension follows upstream GNOME Shell's JS conventions, enforced by the **same tooling, layout, and configuration** as upstream:

- The npm project lives in `tools/` (`tools/package.json`, `tools/package-lock.json`, `tools/eslint.config.js`), mirroring gnome-shell. The repo-root `eslint.config.js` is a **symlink** to `tools/eslint.config.js`.
- **ESLint** with [`eslint-config-gnome`](https://gitlab.gnome.org/World/javascript/eslint-config-gnome) (`recommended` + `jsdoc` configs) and the [`ci-run-eslint`](https://gitlab.gnome.org/World/javascript/ci-run-eslint) runner, both pinned to the same commits upstream uses. The config mirrors upstream's custom rule overrides (`camelcase`, `consistent-return`, `eqeqeq: smart`, `key-spacing`, `prefer-arrow-callback`, `prefer-const`, jsdoc tweaks). Shell-extension globals (`global`, `_`, `C_`, `N_`, `ngettext`) are declared for `src/gnome-shell/**`.
- Style basics live in `src/gnome-shell/.editorconfig` (LF, UTF-8, trim trailing whitespace, 4-space indent for `*.js`).
- Run it with `tools/run-eslint.sh` — exactly the upstream wrapper. It `npm clean-install`s into `tools/` on first run, symlinks `node_modules` into the repo root for import resolution, then lints `src/gnome-shell`. Pass `--fix` to auto-fix formatting.
- The same script is the single entry point everywhere: the meson `eslint` test (`meson test -C build eslint`, skipped when `npm` is absent) and the GitHub Actions workflow (`.github/workflows/eslint.yml`, runs on pushes/PRs touching the JS or tooling) both invoke it. Upstream runs lint from GitLab CI; GPaste runs it from GitHub Actions, but the toolchain, config, layout, and `run-eslint.sh` are otherwise identical.
- This tooling applies **only** to the JavaScript code; it does not affect the C/meson sources.

Code conventions (also following upstream):
- **Don't version-pin core `gi://` imports** — write `gi://GObject`, `gi://GLib`, `gi://Gio`, `gi://Pango`, `gi://Clutter`, `gi://St`. Only pin typelibs that genuinely ship multiple versions: `gi://GPaste?version=3`, `gi://GPasteDaemon?version=1`, `gi://GPasteGtk?version=4`.
- **Manage signal lifecycles with `connectObject`/`disconnectObject`** (owner = `this`) for connections to long-lived non-actor GObjects (settings, the `GPaste.Client`, the daemon runner's bus and daemon), rather than tracking handler ids and disconnecting them by hand. They auto-disconnect when the owner actor is destroyed; an owner that is *not* an actor — `GPasteDaemonRunner`, a plain class — gets no such teardown, so it must still call `disconnectObject(this)` itself (`daemon.js` does, from `_teardownBus()` and `_releaseDaemon()`).
- **Use a standard `constructor()` (calling `super(...)`) in `GObject.registerClass` classes**, not `_init()`/`super._init()`. GJS bridges to the `_init()`-based shell/St/Clutter base classes transparently (positional args like `super(0.0, 'GPaste')` and property dicts like `super({...})` both work).
- **Handle keys with `Clutter.KeyController` or a `ClutterBindingPool`, never `'key-press-event'`/`'key-release-event'` or `vfunc_key_press_event()`.** GNOME 51 finished moving the shell off raw Clutter event signals: `st_focus_manager_navigate_from_event()` is gone, `PopupBaseMenuItem` no longer overrides `vfunc_key_press_event()`, and `PanelMenu.Button._onMenuKeyPress()` now takes no arguments and reads the key from `this._keyController.get_key()`. That last one landed in 51.rc, while 51.beta still connects `'key-press-event'` and calls the method with `(actor, event)` — an override of it therefore forwards `...args` to `super` and reads the key from the event it was handed, falling back to `Clutter.get_current_event()` — which is what upstream reads, but answers `null` outside an event dispatch, so neither spelling may be assumed to have one and an unnameable key simply chains up. Bind a fixed key on an actor with a binding pool (`item.js`); watch the keyboard across a whole subtree — several keys, or the modifier state — with a controller added to the root actor (`indicator.js`, `this._indexKeyController` on `this.menu.actor`). Prefer the controller's `'modifier-change'` signal plus `get_state()` over tracking `Clutter.KEY_Control_L`/`_R` by hand: it also reports latched and locked modifiers.
- **A class that installs a binding pool registers itself in a `static {}` block**, `static { GObject.registerClass(this); const bindingPool = this.get_binding_pool(); … }` (the meta-info object, `Signals` and the like, going first when there is one: `GObject.registerClass({…}, this)`) — the pool is per-class and only exists once the class does. `StWidget` then installs a key controller on every instance whose type chain has a pool, and that controller walks the chain from the instance's own type upward, so a subclass's bindings are consulted before its parent's. Every other class keeps the plain `GObject.registerClass(class … )` form; upstream converted only the classes that needed a pool.

Async / `Gio._promisify` conventions (these bit us — keep them):
- **`Gio._promisify` works on instance methods (`SomeClass.prototype`) but NOT on anything static** — neither a constructor (`SomeClass.new`) nor a namespace-level function (`SomeNamespace.foo_async`) — **inside gnome-shell.** The wrapper assignment silently fails to stick on the class object (it works in standalone `gjs`, so it is easy to miss), and the *raw* introspected `new` then throws *"At least 1 argument required, but only 0 passed"* when awaited with no args. Even where the assignment does stick, the wrapper's body reads `this[originalFuncName]`, which is a `TypeError` when the wrapper is called unbound — which is what calling it off a plain value in a strict-mode ES module does. Promise-wrap the raw `_async` + `_finish` pair by hand instead — see `_connect` in `indicator.js` and `callStorageConcern` in `daemon.js`. `dependencies.js` promisifies only the instance methods.
- **Pass the cancellable, not a trailing `null`.** `GPaste.Client`'s async methods are `(…args, cancellable, callback, user_data)`, so a promisified call ends at the cancellable: `await client.get_history_size(cancellable)`. One `null` there is legal and means "no cancellable"; a *second* trailing `null` lands in the callback slot and defeats `Gio._promisify` (the call hangs or returns `undefined`), which is also what one `null` does on a method taking no cancellable at all — `GPaste.Client.new`, and the `GPasteDaemon.storage_*_async` concerns. Every awaited read in the extension has one: `dependencies.js` exports `replaceCancellable()` (cancel the request in flight, hand back the one its successor goes out on) and `awaitReply()` (await the reply and say whether it is still wanted), and they sit beside the `_promisify` calls because they are the same subject. **Both halves of `awaitReply()` are needed**: cancelling fails the call, arriving as a rejection of `G_IO_ERROR_CANCELLED`, but it does not unqueue a reply already on its way, so the question is also put to the cancellable *the request went out on* — an `async` function's own local, where the C rows need callback data to carry it.
- **`GLib.idle_add_once` / `GLib.timeout_add_once` take `(priority, func)`**, not `(func)`. Passing only the callback makes GJS treat the callback as the priority and dispatch with no function → *"callback is not a function"*. Always pass an explicit priority (e.g. `GLib.PRIORITY_DEFAULT_IDLE`) and keep the `GLib.Source.set_name_by_id(...)` wrapper.
- **Keep the id of every source you add, and remove it on teardown.** A source outlives the object that scheduled it, so an idle or timeout left behind runs against a destroyed actor or a disabled extension — the id is the only handle there is. `daemon.js` is the model (`_reconnectId`, and `_pending` for the deferred jobs, all removed in `shutdown()`); `indicator.js` has `_reconnectId`, `_connectRetryId` and `_selectSearchId`, each with its own `_cancel*()` called from `_onDestroy()`. A `*_once` source must clear its own id from inside its callback, or the cancel would remove an id that has already fired. Do not reach for `setTimeout` to skip this: it is a GLib source too, just one with no id to hold.
