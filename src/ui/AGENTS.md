# `src/ui/` — `gpaste-ui` (GTK4 + libadwaita)

The main graphical history browser. Launched via `gpaste-client ui`. Contains widgets for the history list, item actions, search, and settings panel. Uses libadwaita widgets extensively:

- `AdwApplicationWindow` (via `G_PASTE_GTK_INIT_APPLICATION` which uses `AdwApplication`)
- `AdwHeaderBar` with `AdwWindowTitle` (current history name shown as subtitle), one per `AdwNavigationPage`
- `AdwShortcutsDialog` / `AdwShortcutsSection` / `AdwShortcutsItem` (keyboard shortcut help). The dialog is a snapshot of the settings it was built from and can neither drop a section nor update an accelerator, so `GPasteUiWindow` closes the one it presented on `notify::keybindings-enabled` and on `rebind`, and builds a new one on the next request. The close is **coalesced on the same 250 ms delay the daemon rebinds over**, and for the same reason: `rebind` comes one write per keystroke, and closing on the first of them takes the dialog out from under an edit that has not settled. Closing drops the weak pointer itself rather than waiting for the close transition to unparent the dialog and clear it: a present in between would raise the very snapshot being retired. A request for the dialog with a close still pending **retires whatever is up first** (`retire_shortcuts()`) and builds a fresh one: the pending close says what is up has gone out of date, and the user asking for the dialog is asking for one that tells the truth — raising the stale snapshot and letting the close shut it 250 ms later reads as the accelerator dismissing the dialog. The same call is what cancels a close armed for a dialog the user shut themselves before any further `rebind` arrived, which would otherwise shut the fresh snapshot that is everything that close was making room for; a `rebind` that does arrive with nothing up disarms it there instead, so a source is armed only for a dialog that is up. The dialog constructor returns a **floating** reference, and the caller sinks it into a `g_autoptr` for the length of the present rather than leaving `adw_dialog_present()` to: a present that does not take the dialog would leak it and leave a weak pointer that never clears, and every later request would then re-present a dialog that is not up. The master switch being off is said in the **title of every section the global shortcuts are listed under**, and it can be said nowhere else: an `AdwShortcutsItem` with an empty accelerator renders a "No Shortcut" chip next to its text, one with no accelerator at all is not rendered, and a section with no items is outside libadwaita's contract — so a notice of its own has nowhere to go, and whichever section the reader is looking at has to say it.
- `AdwToastOverlay` (wraps main content; every failed call reports through it)
- `AdwBanner` (shown on daemon connection failure)
- `AdwNavigationSplitView` (responsive split: history selector panel + history list), collapsed by an `AdwBreakpoint` below 600px
- `AdwStatusPage` (shown when history is empty or search has no results)
- `AdwEntryRow` (panel's "Switch or Create" entry, in a one-row `boxed-list` `GtkListBox` in the sidebar's `suffix` slot)
- `AdwSidebar` / `AdwSidebarSection` / `AdwSidebarItem` (history selector list in the panel sidebar)
- `AdwAboutDialog` (about dialog)

**Subclassing notes:** GTK4 made many widget classes final (`G_DECLARE_FINAL_TYPE`), preventing subclassing. Libadwaita re-enables subclassing for its own derivable types. Within the ui, internal widgets subclass derivable types: `GtkBox` (for `GPasteUiPanel`, `GPasteUiHistory`, `GPasteUiItem`), `AdwApplicationWindow` (for `GPasteUiWindow`), `AdwSidebarItem` (for `GPasteUiPanelHistory` — a GObject, not a widget), etc. `GtkStack` is final in GTK4 and cannot be subclassed — use `GtkBox` with manual visibility toggling instead. **`AdwHeaderBar` is final too**, which is why the window's header bar is a plain one carrying its buttons as qdata rather than a `GPasteUiHeader` type: with no type of its own, `ADW_IS_HEADER_BAR()` cannot tell it from anyone else's, so its accessors check that the qdata is there instead of assuming it.

**The header bar and the window's actions.** Everything the header carries drives a `win.` action installed on `GPasteUiWindow` (a `GActionMap`), so a button, a menu item and an accelerator can all ask for the same thing and the window owns the state. The bar holds what acts on the history — New at the start, Search, Pinned and Select at the end — and one `GtkMenuButton` (`open-menu-symbolic`) for what acts on the application: Track Clipboard Changes (a stateful boolean, so it renders as a check), Restart Daemon, Preferences, Keyboard Shortcuts, About GPaste. **The tracking check follows the daemon**: activating it *asks* (`SetActive`, with a confirmation on the way down) and sets nothing; the client's `tracking` signal is what moves it, so it can never sit somewhere the daemon is not. It used to be a `GtkSwitch` whose confirmation hung off a capture-phase `GtkGestureClick` — which meant the keyboard bypassed the confirmation *and* the D-Bus call entirely. Icon-only buttons set both a tooltip and `GTK_ACCESSIBLE_PROPERTY_LABEL`: GTK feeds a tooltip in as the accessible *description*, and an icon gives the button no name. **New is an `AdwSplitButton`**, not a button and not a menu button: clicking it adds a text item, which is what it is for nearly every time, and its arrow drops a menu naming that alongside New Password — a primary action with a small number of related alternatives, which is the case the HIG names for a split button. Two header buttons would give a rare action equal billing in a bar that already carries five controls, and a plain menu button would charge the common case a second click.

**Adaptive layout** (`GPasteUiWindow`): the window is an `AdwToastOverlay` over a `GtkBox` of an `AdwBanner` and an `AdwNavigationSplitView`, and nothing else — there is no window-level `AdwToolbarView`, because every bar belongs to one page or the other. Each `AdwNavigationPage` wraps its content in an `AdwToolbarView` with its own `AdwHeaderBar` (the sidebar's is bare, so it shows its page title; the content's is `g_paste_ui_header_new ()`, with the search bar as a second top bar and the merge `GtkActionBar` at the bottom). That is what gives a collapsed window a back button. An `AdwBreakpoint` added with `adw_application_window_add_breakpoint()` collapses the split view below 600px, and `on_history_changed` shows the content page when it is collapsed, so picking a history navigates to it. The minimum size is 360x294, the narrowest the HIG asks a window to survive.

**Reporting failures.** Client calls the user set off are finished, not discarded: a failed one says so in a toast (`g_paste_gtk_util_toast`, which takes any widget and finds the toast overlay from it) as well as in a `g_warning`. Two callbacks cover calls that report through the window, because a `GPasteClient` `_finish ()` comes in two shapes — one answering nothing and one answering the uuid it created (which nothing in the UI wants; the item arrives as an `update`). Pair `g_paste_ui_report_void_cb` with what `g_paste_ui_report_void (origin, finish, message)` returns, or the `_string` pair; `origin` is any widget in the window, and the message is a translated literal kept by pointer. An `AdwSidebarItem` is a `GObject` with no widget to find a window from, so `g_paste_ui_panel_history_activate()` is handed one.

**Dialogs** (`gpaste-gtk4/gpaste-gtk-util.c`) are shared with the daemon's prompts. `g_paste_gtk_util_confirm_dialog()` takes a **heading** (the question — never the application's name and version, which asks nothing), a body (what confirming does), the confirm label and an `AdwResponseAppearance`: destructive is for what is actually lost, so restarting the daemon and pausing the clipboard are not. `g_paste_gtk_util_form_dialog()` is the shell every composer puts up — an `AdwDialog` with an `AdwHeaderBar` offering to cancel or to confirm, not an alert with a form in its extra child — built around whatever content widget the caller hands it and answering the confirm button, which is the caller's to follow: insensitive while the form is incomplete, and insensitive again once pressed, since `adw_dialog_close()` is asynchronous and the button stays live until it happens. `g_paste_gtk_util_text_dialog()` is that shell around a text view, the composer both New Item and Edit put up, and it hands the caller what was written (`NULL` when cancelled) rather than a buffer to read; `gpaste-ui-password-dialog.c` is the same shell around an `AdwPreferencesPage` of boxed-list rows — a name and a timeout, plus a password and its strength on the one path that composes a password rather than naming one the history already holds. The password composer waits for the daemon before closing: while a call is pending its fields and confirm button are insensitive, but Cancel remains available. A failure preserves the entries and reports the problem above them; a name conflict asks for another name. The reply holds only a weak reference to the dialog and always finishes the call, including after cancellation. `g_paste_gtk_util_password_strength_row_new()` / `_rate()` are shared for the same reason the dialogs are: the passphrase prompt and the graphical tool both rate what is being typed, and one row means they cannot come to rate the same string two ways. Its `unavailable` text — what a build without libpwquality says in place of a rating — is nullable and defaults to the row's own wording: that a build cannot rate is a fact about the build, not about the form asking, so a caller passes its own string only to say it differently (the prompt, to spell it “passphrase”) and never to repeat it. The meter is kept on the row as qdata — `AdwActionRow` is final, and a caller that only rates has no use for the widget — and a build without libpwquality gets a row that says so and goes insensitive rather than no row at all. **`_rate()` does not rate inside the call**: libpwquality's check is a dictionary lookup off the disk, tens of milliseconds of it on a cold cache, and it runs on the thread that asks — which for both forms is the one drawing them, on every keystroke. So the row keeps the *entry* — never what was typed into it, which would be a second copy of the cleartext for this library to hold for the row’s lifetime and to free without wiping, where the entry’s own buffer is a copy that exists either way — and rates what it holds at most once every `G_PASTE_UTIL_STRENGTH_RATING_DELAY` (200ms), rate-limited rather than restarted on each keystroke: the meter is never further behind than that however long the typing goes on, where a timer restarted per keystroke would say nothing at all until it stopped. **The extension's own prompt rates on the same delay**, and for a sharper reason — the thread it would block is the compositor's — so the number is `gpaste-util.h`'s rather than each form's, re-spelled as `G_PASTE_PROMPT_STRENGTH_RATING_DELAY` for the extension to read off the typelib (g-ir-scanner carries a `#define` over only when it is a literal) and pinned to the original by a `G_STATIC_ASSERT`, exactly as `G_PASTE_PROMPT_STRENGTH_MAX` is. `prompt.js` arms one `GLib` timeout and lets a keystroke arriving while it is pending do nothing, and drops it when the dialog goes. What is waiting is dropped with the row, on `::destroy` rather than at finalization, that being the moment before the meter it would set is unparented — and the meter is dropped with it, which is what makes every later `_rate()` a no-op: dropping the rating alone would leave a call arriving during that same dispose arming a fresh one on a row about to be finalized.

**Image previews** in `GPasteUiItem` rows are a small inline `GtkPicture` thumbnail (sized by `images-preview-size`, toggled by `images-preview`), in a slot that sits **between the index and the label** rather than after it: the label is the row's only expanding child, so it is the one the pin and delete buttons take their width from when they appear under the pointer, and everything ahead of it keeps its place — with the preview after the label, hovering a row slid the preview left. Hovering it shows a larger detail preview via a custom `query-tooltip` (`gtk_tooltip_set_custom`), capped and aspect-preserved. The inline thumbnail is kept deliberately (glanceable, keyboard/touch-friendly); the tooltip only enlarges it on demand.

**Colour swatches** give colour items the same glanceable preview, in that same slot (an item is either an image or a colour, never both). The colour costs no call of its own, unlike an image's bytes: a colour item's value *is* its colour, the `[Color]` in front of it on the row being the client's own decoration (see the D-Bus section), so the swatch parses what the row already holds. A value `gdk_rgba_parse()` cannot read back costs the swatch and nothing else. The swatch itself (`gpaste-ui-color-swatch.{c,h}`) draws nothing and styles nothing: it is a `GtkPicture` showing a **one-pixel `GdkMemoryTexture`** of the colour, stretched over the widget with `GTK_CONTENT_FIT_FILL`, wearing Adwaita's **`.frame`** style class — *"1px solid currentColor at the border opacity"*, which is exactly what a hand-drawn outline has to work out for itself, except that the theme keeps it right when the theme changes — and `GTK_OVERFLOW_HIDDEN`, so the colour stays inside that frame whatever radius a theme gives it. No graphene, no GSK, no cairo, and no snapshot to rebuild per binding: setting a colour builds four bytes. The two alternatives both cost more than they give. **CSS** cannot do it at all: GTK4 has no supported way to give *one* widget its own colour — providers are per-display, and the per-widget pair (`gtk_widget_get_style_context()` + `gtk_style_context_add_provider()`) has been deprecated since 4.10, which the project's `GDK_VERSION_MAX_ALLOWED` gating would flag. **Drawing it** (a `GtkSnapshot` with a rounded clip and a border) works, but then the outline colour is ours to keep in step with the theme by hand. Its size is a constant, deliberately not `images-preview-size`: turning image previews off must not take the colours with it.

**Row actions** (`GPasteUiItem`): every per-item action is a `GSimpleAction` in a `GSimpleActionGroup` inserted on the row under the `item.` prefix — `edit`, `make-password`, `strip-rich-text`, `upload`, `pin` (stateful boolean, so the menu shows a check) and `delete`. **What a row can do follows its kind**, which it stores as the `GPasteItemKind` the item arrived with rather than as a boolean per action derived from it: one fact, so no two copies can drift. It is reset to `INVALID` on every (re)binding, in `_g_paste_ui_item_set_index()` — the search-row path writes the new uuid before the item's reply lands, so a kind left standing would steer the actions at the row's *previous* item while the uuid already names the new one, and `edit`, which opens one composer or the other, would hand a text item to the password composer. `upload`, `make-password` and `strip-rich-text` want a text item, `edit` a text item *or* a password — on a password `edit` opens the password composer (`gpaste-ui-password-dialog.{c,h}`) rather than the text editor, since its name and its timeout are the only things about it that can be written, and its value is not something any client can read back. That is also why `make-password` is offered on a text row alone: on a password row it would open the very dialog `edit` already does. Both go through `MakePassword`, which takes a password as readily as a text item, so there is one call and one dialog for the two. The inline buttons and the context menu are both named after them, so there is one implementation of each and one place that says whether the row can perform it: `g_paste_ui_item_update_actions()` disables the lot when the row has no uuid, which is what a row waiting for its content — or one the list view has just recycled — has. That replaced handing every button its own copy of the uuid and disarming them one at a time. Only **pin and delete** are inline, flat, and revealed on hover (a `GtkEventControllerMotion` on the row); a *pinned* row shows its star always, because there it is a badge rather than a button. The star is the **last** child of the row, after the bin, precisely because of that: only the last child keeps its place when the one before it is revealed, so a badge put ahead of the bin slid a button's width left the moment the pointer arrived. What hides them is a **`GtkRevealer` around each**, not their own visibility: a button is taller than the text beside it, so a row that stops measuring one is as tall as its text without the buttons and as tall as a button with them, and every row below it moved as the pointer went by. A revealer with a **horizontal** transition (`SLIDE_LEFT`, duration 0 — an animation the eye can follow would re-ellipsize the label all the way through it) still measures its child's *height* while collapsing its *width* to nothing, so the row's height is a button's whether it is showing one or not and no width is reserved at the end of a row that shows none. Fading the buttons out instead keeps them allocated, which leaves that width dangling on every row. Everything is in a `GtkPopoverMenu` parented to the row with `gtk_widget_set_parent()` — safe inside a `GtkBox`, since `GtkPopover` is a `GtkNative` and layout managers skip those — opened by a secondary-button `GtkGestureClick`, a touch `GtkGestureLongPress`, or `Menu`/`Shift+F10`. Those two keys are a `GtkShortcutController` on the **list view**, not on the row: what takes the focus is the `GtkListItem` above the row, so a controller on the row would never see them.

**Label widgets in list rows** use `GtkInscription` (not `GtkLabel`) for the main text display. `GtkInscription` is optimised for list-item cells and avoids overhead from markup/accessibility features not needed there. Set overflow explicitly with `gtk_inscription_set_text_overflow(GTK_INSCRIPTION_OVERFLOW_ELLIPSIZE_END)` — the default is `CLIP`. To display bold text, use `pango_parse_markup` to convert a markup string into `PangoAttrList` and pass it to `gtk_inscription_set_attributes`; call `gtk_inscription_set_attributes(NULL)` before `set_text` when switching back to plain text.

**Property-driven CSS classes** use `adw_bind_property_to_css_class()` rather than paired `gtk_widget_add_css_class`/`remove_css_class` calls: promote the state to a GObject property and bind the class to it (`GPasteGtkShortcutRow:capturing` → `accent`). Only worth it for a class that actually toggles — classes set once at construction stay plain `gtk_widget_add_css_class` calls, and a state that is not a property on some object (or has no object at all) is not a candidate.

**AdwSidebar** is used in `GPasteUiPanel` to list available histories. Its `suffix` slot holds the "Switch or Create" `AdwEntryRow` — inside a one-row `boxed-list` `GtkListBox`, because an `AdwEntryRow` warns when it is put anywhere else and the slot itself is an `AdwBin`. `GPasteUiPanelHistory` subclasses `AdwSidebarItem` (a `GObject`, not a widget) to represent each history entry. The right-click context menu (backup/empty/delete) is driven by a `GMenuModel` set on the sidebar, with `GSimpleAction`s installed on the panel widget under the `panel.` prefix.

**The history list** (`GPasteUiHistory`) is a `GtkListView` over `GPasteUiHistoryModel`, a `GListModel` of `GPasteUiHistoryItem` rows, driven by a `GtkSignalListItemFactory`. A row carries no history index of its own: in the positional view its index *is* its position, read from `gtk_list_item_get_position()` at bind time, so there is no second copy to go stale; in a uuid-driven view (a search, and later the favourites filter) it carries the uuid it displays instead — which is the model's `by_uuid` mode, entered through `g_paste_ui_history_model_set_uuids()`. `setup` builds one empty `GPasteUiItem`, `bind` points it at its model item (kicking off the async fetch of its content), `unbind` clears it. Because the view recycles a small pool of row widgets, `GPasteUiItem` carries a `GCancellable` for the reads filling it — cancelled and replaced on every (re)binding and on `refresh`, and handed to each of `GetItem`, `GetItemAtIndex` and `GetImage`. **Cancelling is what stops the read**, which for `GetImage` is the image's bytes over the bus for a row that has scrolled away; dropping the reply is the other half of the job, a cancel not unqueueing one already on its way — so every step of the fill chain asks `g_paste_ui_item_still_wants()`, which puts the question to the cancellable *that read went out on*, held by the callback data rather than read back off a row that has replaced it since. That check is made **before** the matching `_finish()` and also covers a cleared `client`: the callback data's ref keeps a disposed row allocated, not alive, and `dispose` cancels and then drops the very client the call was issued on. `unbind` also drops the row's uuid, so a recycled row can be neither activated nor picked as the item it used to display. **The list itself carries one too** (`self->display`): a refresh and a search are two ways of listing the same rows — `GetHistorySize` by position, `Search`/`GetFavourites` by uuid — so whichever went out last is the one that may land, and allocating a listing's callback data (`display_callback_data_new()`) is what cancels and replaces the one before it. Each reply asks the cancellable *it* went out on, held by that data, before it touches the result. A refresh that finds no history name to report sends nothing, so it cancels without allocating a successor. Model updates map to `g_list_model_items_changed()`: the tail on a resize (`set_size`), one row on an in-place replace (`item_replaced`), and the rows that kept their positions but not their contents on a refresh (`invalidate` — history entries shift as one is added or removed). `invalidate` **replaces the `GPasteUiHistoryItem`s** in the range as well as emitting the signal: `GtkListView` pairs each released row widget with the item pointer it was bound to, so handing the same pointers back makes it reuse the widget as-is and run neither `unbind` nor `bind` — the rows would go on showing what they showed. Since only realised rows are bound, an activation may find no widget to ask: a search row's uuid is in the model, and a positional row is at the index it sits at, one `GetItemAtIndex` away.

**Lazy history loading** (`GPasteUiHistory`): the display count is computed at runtime to fill the window — there is no `max-displayed-history-size` setting. `self->limit` is the count of items currently allowed on screen; `self->size` (= number of rows in the model) is `MIN (available, limit)`. The batch size (`g_paste_ui_history_batch()`) is one viewport's worth of items — `page_size / row-height + 1` — falling back to `G_PASTE_UI_HISTORY_DEFAULT_BATCH` until the viewport is allocated. The list view owns the rows, so the row height is not measured but derived from the laid-out content (`upper / size`, as the shell extension does) rather than from a widget we do not hold. The view grows `limit` by one batch on demand, driven by the scrolled window: the vertical adjustment's `changed` signal keeps loading batches while the content does not yet overflow the viewport (so the window always fills), and `GtkScrolledWindow::edge-reached` (`GTK_POS_BOTTOM`) loads the next batch each time the user scrolls to the bottom — lazily pulling in the whole history. A `self->loading` flag guards against re-entrant growth while a refresh is in flight. When the history shrinks, `limit` is clamped back down (`MIN (limit, MAX (batch, available))`) so lazy growth restarts from a single batch rather than eagerly reloading the old depth. There is no libadwaita lazy-scroll helper; `edge-reached` is the idiomatic GTK primitive for the bottom trigger (preferred over hand-computing the adjustment's value/page/upper). Growth applies to the positional view only: a search lists every match, since the view realises just the rows on screen and each fetches its own content on demand.

**Window state** (`GPasteUiWindow`) is left to GTK: there is no geometry GSettings key and none is needed. `GtkApplication` saves and restores it on its own — from its shutdown unless the app was forgotten, and on a timer while the app is focused. GPaste used to prompt a save right after a resize settled, through `gtk_application_save()`, but GTK added that API (22e45968e2) and then hid it again (eabaa008d5) before 4.24, so it is private and the call, along with the timeout that coalesced the per-frame resize notifications, is gone. `gtk_window_set_default_size (800, 600)` (plus a 400x300 minimum) is what `init` sets, as the fallback for a session with nothing saved. Should the API come back, the thing to restore is the coalescing: geometry notifications arrive on every frame of a drag-resize, and the default size must be applied *before* any `notify::default-width`/`-height`/`maximized`/`fullscreened` handler is connected, or every launch would save our own hardcoded default over the geometry the session was about to restore — the window is only presented from the async client callback.

**Window shortcuts** (`GPasteUiWindow`) go through a bubble-phase `GtkShortcutController`, not a hand-written `GtkEventControllerKey` handler: Ctrl+0-9 activates the item at that index, Escape leaves selection mode or closes. Build the digit triggers with `gtk_shortcut_trigger_create_with_aliases()` — GTK knows `KP_0`-`KP_9` are aliases of `0`-`9`, so one trigger covers the keypad twin and there is no second range to spell out. The index is passed as the shortcut's `GVariant` arguments rather than recovered from the keyval. A `gtk_callback_action_new()` callback returning `FALSE` propagates, which is how Escape defers to the search bar when it is open. Note `question` has *no* aliases, so `win.show-help-overlay` stays on `gtk_application_set_accels_for_action()` — an alias trigger would buy it nothing. The rest of the window's accelerators are registered the same way in `add_window_actions()`: `Ctrl+F` search, `Ctrl+N` new item, `Ctrl+Shift+N` new password, `Ctrl+,` preferences, `Ctrl+W` on GTK's own `window.close`.

**The initial focus** (`GPasteUiHistory`) is taken by the history list, from the list view's own `map`. Left to GTK it goes to the first focusable widget in the window, which is the sidebar's "Switch to history" `AdwEntryRow` — an editable, and the search bar captures keys in the *bubble* phase (`gtk_search_bar_set_key_capture_widget()` is only named "capture"), so whatever the user typed went into that entry instead of starting a search. `map` rather than the moment the list is revealed because a widget can only take the focus once it is mapped, and the list is hidden until there is something to list; the handler disconnects itself, so the grab happens once and no later refresh can pull the focus out of what the user is doing. A history that is empty on open therefore still leaves the focus in the entry — there is no list to map, and nothing to search either.

**Merge selection mode** (`GPasteUiHistory` + `GPasteUiHeader` + `GPasteUiWindow`): the header's "merge" button puts the list into a multi-selection mode to merge several entries into one. Selectability belongs to the selection model rather than to the rows, so `g_paste_ui_history_set_selection_mode()` swaps the one installed on the `GtkListView`: a `GtkMultiSelection` to pick with, a `GtkNoSelection` the rest of the time (and `single-click-activate` off while picking, so clicks select instead of pasting). Nothing has to be applied per row, which is what makes rows loaded lazily — or recycled — need no treatment of their own. A capture-phase `GtkGestureClick` added to each row in the factory's `setup` implements click-to-toggle (plain multi-select would need Ctrl/Shift), claiming the press and calling `select_item`/`unselect_item` at the row's current position, which it reads from the borrowed `GtkListItem`. The native row highlight is the only selection cue. Selection *order* is tracked in a `GArray` of **positions**, mirrored from the selection model's `selection-changed` (a `GtkBitset` cannot express order), so the merge keeps the order the user picked them, not the list order. Positions rather than uuids because an unrealised row has no widget to read a uuid off, and select-all over a lazily loaded history picks plenty of those — skipping them would silently merge only the on-screen subset. `g_paste_ui_history_get_selected_uuids()` resolves them at merge time: a search row carries its uuid in the model, and positional ones are looked up in the history (one `GetHistory`, on the first row that needs it, since a position *is* a history index). The list emits `selection-changed(count)`; the window updates the header count (`g_paste_ui_header_set_selection_count`) and the "Merge" button's sensitivity (needs ≥2). The header swaps to a selection look by *emptying itself*: everything that does not belong to picking is hidden, Cancel replaces the merge button and the title shows "N selected". There is no style class for it — libadwaita defines `.selection-mode` for `checkbutton` alone, so the one the header used to add styled nothing. The rows' own actions are hidden with them, through `GPasteUiItem:selection-mode` bound to `GPasteUiHistory:selection-mode` at factory `setup`. The merge controls live in a bottom `GtkActionBar` (`adw_toolbar_view_add_bottom_bar`) revealed with the mode; "Merge" is a `GtkMenuButton` whose popover offers separator presets plus a custom-separator entry — choosing one collects the ordered uuids (`g_paste_ui_history_get_selected_uuids`) and calls `g_paste_client_merge()` (empty decoration), then leaves the mode. Escape and the cancel button also leave it.
