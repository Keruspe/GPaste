# `src/libgpaste/` — shared libraries

The core libraries used by all other components. Two sub-modules:

- `gpaste-3/` → **libgpaste** — daemon-agnostic types: `GPasteClient` (D-Bus client), `GPasteClientItem` (the lightweight item representation transferred over D-Bus), `GPasteSettings` (GSettings wrapper), enums, utilities.
- `gpaste-gtk4/` → **libgpaste-gtk4** — GTK4 + Adwaita helpers (the preferences widgets).

**All three libraries split their headers into an installed half and an internal one**, and the internal half is what a new header joins unless something outside the library names it. libgpaste-gtk4 installs exactly two types — the preferences dialog and the preferences widget `prefs.js` embeds — while the groups, the shortcut row and the four pages it is built from stay in; its GIR is generated from `libgpaste_gtk4_public_sources` alone, so an internal symbol cannot leak into it. The four pages are plain functions returning an `AdwPreferencesPage`, not types: they carry no state, and both callers build them from one list (`g_paste_gtk_preferences_pages_new()`) so they cannot drift apart.

**The core library's directory carries `apiversion`, so it is renamed on every major bump** (`gpaste-2/` → `gpaste-3/` for this release), and its includes are spelled `<gpaste-3/gpaste-macros.h>`. That is not decoration: the installed headers live at `$prefix/include/gpaste/gpaste-3/` with `-I …/include/gpaste`, and the *same* include text has to resolve both in-tree and against the install prefix, since these are the same files. In-tree it resolves through `include_directories('.')` = `src/libgpaste`. Keeping the two spellings identical is what makes a broken installed header a build failure here rather than a downstream bug report. `gpaste-gtk4/` and `gpaste-daemon/` are named for their library rather than for a version, so they never move.

The installed layout is one shared directory, with each library owning a subdirectory of it:

```
include/gpaste/{gpaste.h, gpaste-gtk4.h, gpaste-daemon.h}   <- the three umbrellas
include/gpaste/{gpaste-3/, gpaste-gtk4/, gpaste-daemon/}    <- per-library headers
```

All three `.pc` files therefore declare `Cflags: -I${includedir}/gpaste` (meson `subdirs: 'gpaste'`) — that line is what puts the include path on a consumer's command line, so it is the one to check when the layout changes. `libgpaste` is versioned all the way through (`libgpaste-3.so`, `gpaste-3.pc`, `GPaste-3` typelib, `gpaste-3.vapi`, all derived from `apiversion`); `libgpaste-gtk4`'s `4` is GTK's version and `GPasteDaemon-1`'s is its own, so neither tracks the GPaste major.

**Each library ships a `.pc`**: `gpaste-3`, `gpaste-gtk4` and `gpaste-daemon`. What goes in `requires:` is the set a *consumer* must also satisfy — i.e. what the **installed** headers name, not what the library links. `gpaste-daemon` therefore requires only `gpaste-3`: no public daemon header names a GTK, GDK or GCR type, so those stay in the `Requires.private:` meson derives from the library's own `dependencies:`, alongside the optional ones (libsodium, sqlite3, libsecret-1, libmutter; `pwquality` is on `gpaste-3`, which is where the rating lives). Use `requires:`, not `libraries:` — the latter means "put this in `Libs:`".

**Observing a setting: use `notify::<key>`.** Every setting is a GObject property named exactly like its GSettings key, so `notify::track-changes` *is* the change notification — there is no separate `changed` signal, and `g_object_bind_property()` works directly. `GPasteSettings` emits exactly one signal of its own, **`rebind::<key>`**, and it is not a duplicate: a rebind is an action to take (re-register a keybinding), not a value that changed, and only the keybinding settings carry it. Prefer the detailed form; `notify` undetailed fires for all twenty-nine keys. Note the callback takes a `GParamSpec *`, not the key string.

A third library, **libgpaste-daemon**, lives under `src/libgpaste/gpaste-daemon/` and holds the rich clipboard item hierarchy along with the rest of the daemon objects, plus the utility helpers nothing outside it calls: `gpaste-daemon-util.h` has the history-path helpers and the file backend's XML escaping (though not `g_paste_util_history_name_is_valid()`, which a client asks too before sending a name, and which is installed in `gpaste-3/gpaste-util.h` with `G_PASTE_DEFAULT_HISTORY` for that reason), which is why `gpaste-3/gpaste-util.h` no longer declares them (nor includes `gpaste-client.h`). Each library exports the symbols marked `G_PASTE_VISIBLE` (built with hidden default visibility), and GIR + Vala bindings are generated from it.

**Favourites are pinned against both caps.** `g_paste_item_set_favourite()` marks an item and `g_paste_history_set_favourite()` is what a caller uses, because everything that follows from the flag is the history's business. `private_check_size()` walks the tail dropping only non-favourites, and `elect_new_biggest()` never elects one, so the memory cap's loop stops on its own once nothing is electable — a history with nothing else in it therefore grows past `max-history-size` rather than let one go. Both skip index 0 as well: that is the item just added or selected, and evicting it would mean a clipboard that keeps nothing at all once the rest is pinned. Un-pinning is not symmetric with pinning: pinning shrinks the electable set, so only a full re-election can name the runner-up (and only when the item was the elected one), while un-pinning grows it by one and needs a single comparison — then both caps re-run, and may well evict the very item that was just let go. When they do, the change is persisted as a full rewrite: a replace carries no snapshot for an incremental backend to reconcile against, unlike an add, which is the one operation that expects to displace anything. **The pin belongs to the entry, not to the object holding its contents.** Whenever one item takes another's place — `_g_paste_history_replace()` behind `Replace`/`MakePassword`, and the growing-line and dedup branches of `_g_paste_history_add()` — the flag is carried over: editing a pinned item, retyping it, or turning it into a password is not the user letting go of it, and silently un-pinning there would make what they asked to keep evictable again by nothing more than using it.

**The history model is a `GPtrArray` plus a uuid `GHashTable`**, newest first. The array owns a ref per item; the index borrows both halves from it (the key is the item's own uuid string, the value the item the array owns), so the two are always updated together — `g_paste_history_private_remove()` drops the index entry *before* stealing the array's ref, since the key belongs to the item. That is only sound because a uuid never changes once its item is in the history: `g_paste_item_set_uuid()` is called while loading and when preparing the plain replacement for a rich-text strip, before either object joins the history. Positions are *not* indexed — adding prepends, which shifts every position, so a uuid→position map would have to be rewritten on every add; `g_paste_history_private_get_indexed_by_uuid()` scans for it instead, comparing pointers. **`GList` remains the storage layer's interchange type**: `read_history_file`/`write_history_file`, the saver's snapshots and the migration code all still take one, because persisting is a one-shot bulk operation where a list costs nothing. `g_paste_history_snapshot()` and `g_paste_history_private_set_from_list()` are the two conversion points. Note the three ways items leave the history and how they differ: `private_remove(…, TRUE)` disposes of the item *and its backing file*, `private_clear()` swaps a history out with a plain unref (files kept, since the items are only being put away), and `dispose` destroys the containers themselves.

**libgpaste-daemon has a public/internal header split.** `meson.build` keeps two lists, and the distinction is real rather than cosmetic:

- `gpaste_daemon_public_headers` — installed, introspected, and included by the `gpaste-daemon.h` umbrella. Seven of them exist because the gnome-shell extension drives them (`GPasteBus`, `GPasteDaemon`, `GPasteSearchProvider`, `GPastePrompt` — which `prompt.js` *implements* — `GPastePassphrase`, `GPasteStorageMigration`, and `GPasteStorageBackend` for its static passphrase helpers). The other eight are there only because those headers pull them in: `gpaste-daemon.h` declares `g_paste_daemon_new()`, hence the clipboard provider, hence the history, hence the item hierarchy they hand around.
- `gpaste_daemon_internal_headers` — compiled into the library but **never installed and never introspected**. In-tree consumers (`src/daemon/`, `src/ui/`, `tests/`) reach them through `gpaste_daemon_headers_dep`'s `include_directories`, never the install prefix. The optional features (libsodium, SQLite, libsecret, mutter) append to the union lists, so their headers are internal by construction and the GIR does not change shape with the feature set.

**A new header goes in the internal list unless the extension needs it.** Two rules follow from the split: the umbrella must only include installed headers (an installed umbrella pulling an uninstalled header is a broken install), and adding a header to the public list means committing to it in the GIR.

**GObject type macros** — use these in `.c` files:

| Macro | Use when |
|---|---|
| `G_PASTE_DEFINE_TYPE` | Concrete type — this is the normal case |
| `G_PASTE_DEFINE_TYPE_WITH_INTERFACE` | Concrete type implementing an interface |
| `G_PASTE_DEFINE_TYPE_WITH_PRIVATE` | **Derivable** type with a `Private` struct |
| `G_PASTE_DEFINE_ABSTRACT_TYPE_WITH_PRIVATE` | Abstract base class with private data |

**A final type puts its fields straight in `struct _GPasteX`, with no `Private` struct.** `G_DECLARE_FINAL_TYPE` already keeps that struct in the `.c` file, where nothing outside can reach it, so a private struct adds only an offset lookup per access and a `priv = …` line in every function. Access the fields as `self->field`. Private structs are for the **derivable and abstract** types (`GPasteItem`, `GPasteStorageBackend`, `GPasteBusObject`, …), whose instance struct *is* public and so cannot carry them — those keep `G_PASTE_DEFINE_TYPE_WITH_PRIVATE` and the `_g_paste_x_get_instance_private()` const shim it emits.

The daemon library, `gpaste-daemon/`, is documented in [`gpaste-daemon/AGENTS.md`](gpaste-daemon/AGENTS.md).

## D-Bus

Every interface GPaste speaks is described by an XML file that `gdbus-codegen` turns into both halves of the wire. No method hand-marshals a `GVariant` any more. One place still does: `g_paste_client_g_signal()` unpacks the incoming signals by hand, because `GPasteClient` implements the interface rather than deriving from the generated proxy (below) and so never gets the proxy's own demarshalling.

- **The XML is the source of truth.** `data/dbus/org.gnome.GPaste3.xml` is the daemon's own interface; it is installed to `$datadir/dbus-1/interfaces` (path from `dbus-1.pc`'s `interfaces_dir`, overridable with `-Ddbus-interfaces-dir`) so anything can read the contract without building GPaste. `src/libgpaste/gpaste-daemon/org.gnome.Shell.SearchProvider2.xml` is gnome-shell's interface, kept only to feed codegen and deliberately **not** installed — gnome-shell ships the authoritative copy.
- **The generated code is internal.** It is produced by `gnome.gdbus_codegen()` from `src/libgpaste/gpaste-3/meson.build` and `src/libgpaste/gpaste-daemon/meson.build`, which exist only so the output lands in those subdirectories and the `<gpaste-3/…>` include style keeps working. It is never installed and never introspected: `GPasteClient` is the whole public story and is hand-written. Confirm with `grep -c Daemon3 build/src/libgpaste/GPaste-3.gir` — it must stay `0`.
- **`org.gnome.GPaste3` is generated into libgpaste**, the lowest library, because a GType may only be registered once per process and gnome-shell loads libgpaste and libgpaste-daemon together. libgpaste-daemon uses the skeleton half, so the generated declarations carry `G_PASTE_VISIBLE` via `--symbol-decorator`; without it, hidden visibility would leave them unlinkable.
- **A `declare_dependency()` passes the generated *header*, never the whole codegen output.** `gnome.gdbus_codegen()` returns `[source, header]`, and `sources:` on a dependency is inherited by every target that uses it — handing over the list would compile `gpaste-daemon3.c` into each of them, which is precisely the one-registration-per-process rule above being broken, once per dependent. Only the library named in `link_with:` builds the source. Same for `gpaste-shell-search-provider2.c` in `gpaste_daemon_headers_dep`. Check with `nm -D --defined-only build/src/libgpaste/libgpaste-gtk4.so.* | grep -c g_paste_daemon3_` — it must stay `0`, and `153` for `libgpaste-3.so.0.0.0` alone (name the file, not the glob: `.so.*` matches the symlink too and doubles the count).
- **Naming.** The `org.gtk.GDBus.C.Name` annotation maps the interface to `PasteDaemon3`, so the generated symbols are `g_paste_daemon3_*` and never collide with the `g_paste_daemon_*` of the `GPasteDaemon` object that implements it. The `3` is the interface version, bumped for the 51.0 break; the bus name and object path are not versioned and did not move.
- **`GPasteClient` implements `GPasteDaemon3` rather than deriving from the generated proxy.** Deriving would drag the generated class struct into the installed `gpaste-client.h`; implementing the interface is what makes `g_paste_daemon3_call_*()` usable while the public header, the GIR and the VAPI stay exactly as they were. It therefore overrides the interface's `Active`, `History` and `Version` properties (`g_paste_daemon3_override_properties`) and keeps its own `g_signal`/`g_properties_changed` handlers, which turn the wire signals into GPaste's richer ones.
- **An item travels as one struct, `(ssubas)`**: uuid, value, kind, favourite, notes. The kind rides along because every client drawing a row wanted it and had to ask separately — `GetElementKind` is gone. `GetItem`, `GetItemAtIndex`, `GetItems`, `GetHistory`, `GetFavourites` and `Search` all answer it, `Search` included so a search view needs no follow-up call. **`GetFavourites` is a listing of its own** rather than a flag on `GetHistory`: the pinned items are typically a handful out of a history that is not, and the flag lives daemon-side, so a favourites view that pulled the whole history across the bus to keep three rows would be paying for the filter twice. A client wanting the pinned *matches of a search* still sifts those itself, the matches being the narrow set already. The type is spelled in one place in C, in `gpaste-3/gpaste-client-item.h` next to the `GPasteClientItem` it builds, and the daemon's builder and the client's parser both go through it. It takes **two macros** rather than one: `G_PASTE_ITEM_VARIANT_STRING` is the type, for `G_VARIANT_TYPE`, and `G_PASTE_ITEM_VARIANT_FORMAT` is the same shape as a `g_variant_new()`/`g_variant_get()` format string, where the array is `^as` — `as` plus the convenience conversion to and from a `GStrv`. `^` is not part of any type string, so `G_VARIANT_TYPE` will not take the second; and without it the first would mean handing `g_variant_new()` a builder and `g_variant_get()` an iterator for a field that is always empty. They sit on adjacent lines so that changing the shape means changing both. `gpaste-3/gpaste-client-history.h` is the same arrangement one size down, for the `(st)` a history travels as and the `GPasteClientHistory` `ListHistories` hands back. **One value per item**, the one a user is shown: the `GetRaw*` twins that answered `g_paste_item_get_value()` instead are gone, since for plain text — nearly all of a history — the two strings are equal, and neither was ever a password's real value. That is what leaves `g_paste_daemon_methods_item_variant()` with nothing to choose between; `g_paste_item_get_value()` itself stays, for the in-daemon callers (the image loader, `GetImage`, `Merge`, the growing-line test, the search regex, both storage backends) that never went near the wire.
- **The current history is what every item call acts on.** Reading items (`GetHistory`, `GetItem`, `GetItemAtIndex`, `GetItems`, `GetFavourites`, `GetImage`, `GetUris`, `GetPasswordTimeout`, `Search`, `GetHistorySize`) and changing them (`Add*`, `Merge`, `Replace`, `MakePassword`, `Select`, `SetFavourite`, `DeleteItem`, `DeletePassword`) never name a history; the calls that do — `ListHistories`, `BackupHistory`, `EmptyHistory`, `DeleteHistory`, `SwitchHistory` — are the ones treating histories as objects rather than as a place to put items. Inspecting another history means switching to it. `GetHistorySize` used to be the one exception, and paid for it: sizing a history that is not the current one meant building a `GPasteHistory` and loading it *synchronously*, and `GPasteUiPanel` did that once per row. **`ListHistories` answers `a(st)` instead** — name and size together, in the store's own order — so a sidebar of them costs one call. The size comes from `g_paste_storage_backend_count_history()`, which every backend overrides so that no listing has to materialize a history: `GPasteSqliteBackend` answers a `COUNT (*)` over the very predicate `read_history_file` selects on — cap, favourites and, when images are turned off, the image rows a read would drop — on a short-lived read-only connection of its own, since counting needs no content and so no key, and borrowing the cached one would evict the current history's connection and its derived key once per history listed. `GPasteFileBackend` has no cheaper question to ask than parsing, so it walks the document through the same parser, version gate and cap as a read, in a counting mode that builds no item and touches no image side file. The default — read and count — is what a backend with neither gets. Only a read creates the placeholder file for a history that is not there; counting must not bring one into existence.
- **`notes` is a reservation, not a feature.** The array is always empty: nothing in the tree attaches a note to an item, no method writes or reads one, and `g_paste_client_item_get_notes()` answers an empty `GStrv` for every item there is. It is on the wire because of what a note *is* — something a row draws — which is the same test that keeps `kind` and `favourite` in the struct and `GetPasswordTimeout` out of it. A field every client redraws for cannot be added later without breaking every client, so the break is spent here, on the release that is breaking the interface anyway, rather than a second time for #254. It is empty rather than absent for the same reason `g_paste_client_item_get_notes()` answers an empty array rather than `NULL`: a client that draws whatever it finds needs no version check now and no change then. Do not give it a meaning it does not have — a note is a note, and until one exists this field says only that there are none.
- **Every mutation answers what it did.** The `Add*` calls, `Merge`, `Replace` and `MakePassword` all return the uuid of the item that landed. Policy can refuse an add outright — `min-text-item-size`, `max-text-item-size`, `trim-items`, an item over `max-memory-usage` — and that is **`.Error.Rejected`** (`G_PASTE_ERROR_REJECTED`), which says the request was well formed and nothing went wrong: the daemon simply kept nothing. Without it a caller could not tell an add that worked from one that quietly did not, short of racing the asynchronous `Update`. Content the current selection already says is *not* a refusal: the history keeps what it has and the add answers the uuid it already holds it under, so the same value added twice in a row succeeds twice. It is still handed to `g_paste_history_add()` rather than dropped there, since what the arriving item carries beyond the value it matched on is the head's to take (`private_merge_into_head()`, in [`gpaste-daemon/AGENTS.md`](gpaste-daemon/AGENTS.md)): an `AddPassword` for the value already at the head would otherwise lose the timeout it came with, and answer that call one way here and another when the very same password arrives off a selection. `Replace` and `MakePassword` matter most: both mint a *new* uuid and report `target == ALL`, so before this the new item's uuid existed nowhere a caller could reach. **`MakePassword` is the exception to its own rule**, being the one method that takes an item of the kind it produces: handed a password rather than a text item it updates that one in place -- its name and its `timeout`, never its value -- so it answers the uuid it was given and reports `ITEM`, since nothing was replaced and a view listing the item can repaint one row. The name is part of what the item weighs, so that update moves `GPasteHistory`'s own memory total with it — the bookkeeping `_g_paste_history_replace()` does around the object it swaps in, for an item that stays where it is; left out, the difference is subtracted a second time when the item eventually goes, and that total is unsigned. A total that moved is a cap that may have given way, so the rename re-runs `private_check_memory_usage()` itself — only that one, the item count being unchanged — and, exactly as in `set_favourite()`, persists a full rewrite when evictions rode along, since the renamed item may be among them. Left to whatever is added next, the eviction would be blamed on that instead. That is also what retired `RenamePassword`, which did the strictly smaller half of it and had already drifted where it mattered: it checked no collision at all, so it could put two passwords under one name, after which `GetPassword` answered whichever it reached first and `DeletePassword` destroyed an arbitrary one. Renaming now needs the password's uuid, which a listing carries. The collision check exempts the item itself, and exempts `G_PASTE_PASSWORD_ITEM_NO_NAME` (`"******"`) outright: that is what a password with no name of its own reads as rather than a name anybody picked, so it is the one name a history may hold several entries under — the make-password keyboard shortcut, which has no name to hand over, is what makes them. That shortcut acts on a **text item alone**: a password is one already, and a shortcut carries neither a name nor a timeout, so there is nothing about one it could change. **The `timeout` both it and `AddPassword` take is in seconds**, `0` for none: it is how long the password may stay on the clipboard once it is the active item, after which the daemon takes it off every selection still carrying it (`GPasteClipboardsManager`, in [`gpaste-daemon/AGENTS.md`](gpaste-daemon/AGENTS.md)). The wire type is `u` and the item holds a `guint`, but the range is `G_PASTE_PASSWORD_TIMEOUT_MAX` — 65535, the `password-timeout` key's own `<range>`, which the preferences row and the Make/Edit Password composer both offer and `g_paste_password_item_set_timeout()` caps everything down to, both storage backends reading one back included. Past it a countdown outlives every session it could run in, which reads as expiring and never does. `gpaste-client --timeout` **refuses** a value above it rather than let the item cap it: a number silently becoming a smaller one is a password expiring at a time nobody asked for. **`MakePassword` also takes `G_PASTE_PASSWORD_TIMEOUT_UNCHANGED`** (`G_MAXUINT`, above the range so it collides with no real timeout), which writes no timeout at all: a password keeps the one it carries — and the countdown running for it — while a text item becoming one takes the `password-timeout` default, `g_paste_history_make_password()` resolving the sentinel in the one place. That is what a caller changing only the *name* sends, and it is why the sentinel exists at all: `0` is a timeout of its own, so a client with no timeout to write had to read the current one back with `GetPasswordTimeout` and echo it, and any that forgot — `gpaste-client make-password` did — cancelled a running countdown by sending the setting's default over it. `NULL` and the sentinel are the same story for the two writable fields, rather than one having it and the other not. **Updating a password publishes nothing**: what a password is put on a selection as is `g_paste_item_get_real_value()`, which neither branch of `MakePassword` touches, and the item at the front is not necessarily what a selection holds — selecting it would be writing a password's cleartext over whatever the user has copied since. The new timeout still has to reach the running countdowns, and that is `g_paste_clipboards_manager_rearm_password()`, which the D-Bus method and the make-password shortcut both call: it re-arms each selection that currently carries the item, and leaves the countdown of one that has moved on alone — that selection is watching an exposure of its own. A selection whose *duration* did not actually move keeps the countdown it is running: `arm_password()` compares the item **and** the seconds it was armed for, so a rename is no reason to hand the password more time on the clipboard. A `NULL` `@name` leaves a password's own name alone rather than writing the placeholder over it — only a text item becoming a password takes `G_PASTE_PASSWORD_ITEM_NO_NAME` from one. **`GetPasswordTimeout` reads it back**, and is a method rather than another field on the item struct for the reason `GetImage` and `GetUris` are ones: nothing drawing a row wants it, only the client putting up a dialog to change it, so as a field it would be a number every item of every kind carried for the password's sake.
- **`Upload` waits for the upload.** It answers the url, and an upload that failed fails the call — not a reply the moment the tool has been spawned, with the failure going to a `g_warning` and the url into the history behind the caller's back. Adding it to the history is the *keyboard shortcut's* behaviour, which has nobody to answer to, and lives in `on_keybinding_upload_done()`; the method adds nothing. An empty `uuid` means the current item, since that is what the shortcut uploads and a D-Bus string is never absent. Because the reply waits on a network round trip, it is the one call `GPasteClient` gives a timeout of its own (`G_PASTE_CLIENT_TIMEOUT_UPLOAD`) instead of the `GDBusProxy` default of 25 seconds — otherwise a large paste or a slow service fails on the caller's side while succeeding on the daemon's. **What runs is the `upload-command` setting**, not a tool named in the source: a command line, parsed as a shell would (`g_shell_parse_argv()`) so it can carry arguments, but spawned as an argv rather than through a shell — a clipboard item reaching a shell as anything but stdin buys nothing and costs a quoting bug. The contract is the one `wgetpaste` had and every alternative shares: the item on stdin, the url alone on stdout. That last word is load-bearing now that the command is the user's: a tool that is out of date, misconfigured, or not a pastebin client at all answers with its usage or with an HTTP error body on that same stream, so the reply is checked before it can be handed back as an address: a successful exit, and a scheme of `http` or `https`. `g_uri_is_valid()` alone would not do it -- a scheme and a colon is all a valid uri takes, which every `Usage:` and `Error: 429 Too Many Requests` has — and `on_keybinding_upload_done()` would otherwise put it in the history and on the clipboard as one. **Neither refusal quotes what the command wrote**: the item's own text goes in on its standard input, so a tool that hands its input back — a misconfigured `cat`, a curl given an error page that quotes the request body — would put what the user copied into an error that reaches the caller over the bus and the journal behind it. The exit status (or the signal that killed it), and the bare fact that the answer was not a url, are what get reported; what the command wrote is the user's to look at by running their own command line. **And the command is given a deadline** (`G_PASTE_DAEMON_UPLOAD_TIMEOUT`, nine minutes, comfortably inside the ten `G_PASTE_CLIENT_TIMEOUT_UPLOAD` allows so the caller is told which one ran out): nothing about a command line the user wrote promises it exits, and one that does not held the task, the child and the pipes the daemon opened for it for the life of the process. Nothing secret waits with them: `Upload` is a text item's action, and the value it hands the command is `g_paste_item_get_value()`, which a password answers with `G_PASTE_PASSWORD_ITEM_NO_NAME` rather than what it holds. The deadline cancels *and* kills, in that order: cancelling `g_subprocess_communicate_utf8_async()` abandons the read without touching the child, which would then outlive the daemon holding the pipes it was writing to, while killing alone would let the read come back with whatever was written so far and be reported as a command that exited badly. So the cancel is what labels the failure, and `G_IO_ERROR_CANCELLED` — the only cancellation there is on this path — is turned into the timeout it actually was. **Any other failure kills the child as well**: `communicate()` answers once the child has exited, so one that fails any other way — an I/O error on the pipes — leaves it running, and the deadline that would have killed it is gone with the answer that arrived.
- **`ShowAbout` is not the daemon's business.** `ShowHistory` is a signal, because only the extension can act on it; an about dialog is the UI app's own `about` action, which any client reaches with `g_paste_util_activate_ui ("about", NULL)`. The daemon's method did no more than make that same call, so `gpaste-client about` makes it itself and the method is gone — which is also what lets `gpaste-client about` work with no daemon running: the window registers `about` and `preferences` (`add_daemonless_window_actions()`) whichever way the connection concluded, and holds neither back when it failed. The extension offers no About at all: a panel menu is not where an application's about dialog belongs.
- **Errors mean the same thing everywhere.** `NOT_FOUND` for any uuid or name that matches nothing, `INVALID_INDEX` only for `GetItemAtIndex` (its sole user), `INVALID_ARGUMENT` for an argument missing, empty, or not something the method can act on — a history name that is a path is the second kind, refused by `g_paste_util_history_name_is_valid()` because the name goes straight into the file the history is stored in and into the images directory it owns, `ALREADY_EXISTS` for a name already taken — `AddPassword`'s (which leaves the existing password and clipboard untouched), `MakePassword`'s, and `BackupHistory`'s, which refuses rather than overwrite an existing history, since a backup silently destroying an older one of the same name is a loss noticed far too late. `DeletePassword` reports `NOT_FOUND` rather than succeeding at nothing, and `EmptyHistory` can fail at all. `MakePassword`'s `ALREADY_EXISTS` is about *another* password: a password keeping the name it already carries has collided with nothing, which is the ordinary case now that changing only a timeout goes through the same method.
- **`Update` names the item it is about.** `Update(u action, u target, s uuid, t index)`: a position means nothing to a view listing something other than positions, which both a search and the favourites filter are, so the uuid is what lets them apply a change instead of re-running their query. The favourites view is the one that cannot take that shortcut: whether a row still belongs in a list of pinned items is exactly what a pin/un-pin changes, and the update names the item rather than what became of its flag, so it re-queries (`GetFavourites`, which is cheap for it). `target == ALL` carries neither. A replace that mints a *new* uuid (editing a text item, turning one into a password, a growing line standing where the shorter one it grew from stood) reports `ALL` rather than `ITEM`, because one uuid cannot say both which item went and which arrived.
- **The current history is a property, not a signal.** `History` replaces `GetHistoryName()` and the `SwitchHistory` *signal* (the method stays), so `GPasteClient` reads it off the proxy's cache with no round trip and clients follow `notify::history`. What a switch cannot express is a history appearing *beside* the current one, which is what a backup does — hence **`HistoriesChanged`**, a signal of its own. `BackupHistory` used to emit `SwitchHistory` three times running to force GUIs to re-list; that hack is what the new signal replaces. **It fires for every change to the set**, not just a backup: a `DeleteHistory`, an `EmptyHistory` naming a history there was none of, and a `SwitchHistory` that had to create its target. `HistoryDeleted`/`HistoryEmptied` still carry the name beside it, so a sidebar can update one row instead of re-listing; a client that only lists needs `HistoriesChanged` alone.
- **`ReportExtensionState`, not `SetExtensionState`.** The extension reports a fact about itself; whether that should stop the tracking is the daemon's `track-extension-state` policy, and a client does not second-guess it.
- **The interface's signals carry `Raw*` C names.** That is not decoration: without it the generated `update`, `history-deleted`, … would collide with the identically named signals `GPasteClient` declares itself. The daemon emits them with `g_paste_daemon3_emit_raw_*()`.
- **No signal shares a name with a method.** `HistoryEmptied` and `HistoryDeleted` are named for what happened, not for the `EmptyHistory`/`DeleteHistory` that did it. D-Bus allows the collision, but most language bindings map an interface's methods and signals onto members of one class, where the second of a pair has nowhere to go.
- **The numbers on the wire are documented in the XML itself.** `(ssubas)`'s kind and `Update`'s action/target travel as bare `GPasteItemKind`/`GPasteUpdateAction`/`GPasteUpdateTarget` values, which is nothing a client outside this tree can read off the signature. The mappings are carried in annotations — `org.gnome.GPaste3.ItemKind` on the interface, `org.gnome.GPaste3.UpdateAction`/`.UpdateTarget` on `Update`'s two arguments — rather than only in the XML comments, because an annotation comes back from `Introspect()` over the bus where a comment does not. **Under a name of GPaste's own, never `org.gtk.GDBus.DocString`**: gdbus-codegen treats everything in its own namespace as an instruction to itself and emits none of it into the `GDBusInterfaceInfo` the skeleton answers `Introspect()` from, which is the one place these have to reach. Check with `grep -c org.gnome.GPaste3.ItemKind build/src/libgpaste/gpaste-3/gpaste-daemon3.c`.
- **`StripRichText` keeps the item.** Rich text is what a copy out of a browser or an office suite carries beyond its text — the `text/html` and `text/xml` payloads `GPasteSpecialMime` names, fetched into the item's special values and served back from them — so it is an alternative *representation* of the very string the item already shows. Dropping it changes nothing a listing displays, which is why the item stays in place under the uuid it had and the `Update` reports `ITEM`, where `Replace` has to report `ALL`. It is also why the method answers nothing: there is no new uuid for it to name — a uuid that matched nothing still answers `NotFound`, and one whose item stopped being a text item under the strip's own lock still answers `WrongItemKind` — which is what the strip's `found` out-parameter is for, the two refusals being indistinguishable in its return value, and the unlocked lookup the kind check needs being one the item can be evicted or replaced between. `g_paste_history_strip_rich_text()` creates a plain text object under the same uuid, using `_g_paste_history_replace()` to carry over the pin, memory bookkeeping and biggest-item election. **The rich object stays intact for saving workers**: a save snapshot holds references to live items, and the file and sqlite writers borrow their special-value lists, so freeing that list in place would race those readers. A replacement preserving its uuid reports `ITEM`; one minting a new uuid reports `ALL`. **An item with no rich text is stripped successfully**, and saves nothing. **The D-Bus handler refreshes only selections still carrying the text**, through `g_paste_clipboards_manager_refresh_text()`, regardless of the item's position. The model emits no `selected` signal for a strip: the history head may differ from the clipboard while tracking is paused, and the clipboard and primary selection may differ from each other. **A text item is the only kind it takes**: a uris item carries special values too, but they are how a file list is handed over (`x-special/gnome-copied-files`) rather than another spelling of what the item shows, so dropping them would leave a file manager nothing to paste — anything but a text item answers `WrongItemKind`. Editing an item and turning one into a password already drop the same thing, both minting an item that never had any; a password never acquires one in the first place, `GPasteClipboardUpdate` skipping the special mimes for a sensitive read.
- **`Merge` has to be daemon-side.** What it joins is each item's *real* value, and the only string an item travels with here is the one a user is shown, so a client holding a listing cannot do it itself. That is the reason the method exists at all now that the `GetRaw*` twins are gone.
- **`ay` needs `org.gtk.GDBus.C.ForceGVariant`.** The default mapping for a byte array is a C bytestring, which stops at the first NUL — that would truncate every PNG `GetImage` returns. The annotation is load-bearing; do not drop it.
- **Handler signatures are not checked by the compiler.** `g_signal_connect_swapped (skeleton, "handle-x", G_CALLBACK (…), self)` erases the prototype, so a handler whose arguments do not match the generated `handle_x` vfunc is undefined behaviour at runtime, not a build error. When adding or changing a method, compare the handler against `struct _GPasteDaemon3Iface` in the generated header by hand. The `G_PASTE_DAEMON_HANDLER*` macros in `gpaste-daemon.c` are what keep that to four places instead of thirty-one.
- **The three flavours of a client method are generated, and so are the handlers.** A method reaches the daemon as `g_paste_client_x_sync()`, `g_paste_client_x()` and `g_paste_client_x_finish()`, and comes back through one handler; both ends are written from macros — `G_PASTE_CLIENT_METHOD*` in `gpaste-client.c`, `G_PASTE_DAEMON_HANDLER*` in `gpaste-daemon.c` — with the signature and the forwarded arguments passed as parenthesized lists and `ARGLIST` supplying the comma that vanishes for a method with no arguments of its own. **The gtk-doc block goes above the invocation**: g-ir-scanner matches a block to a symbol by the name on its first line, not by what follows it, which is the same trick `gpaste-settings.c` uses for its accessors. Add a method by adding an invocation; only reach for a hand-written body when there is genuinely one (a relative path to resolve, two out parameters, a precondition of its own).
