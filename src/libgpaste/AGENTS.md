# `src/libgpaste/` — shared libraries

Three libraries, each exporting what is marked `G_PASTE_VISIBLE` (hidden default visibility) and each with GIR and Vala bindings:

- `gpaste-3/` → **libgpaste**: the daemon-agnostic types — `GPasteClient` (the D-Bus client), `GPasteClientItem` (an item as it travels over D-Bus), `GPasteSettings` (the GSettings wrapper), enums and utilities.
- `gpaste-gtk4/` → **libgpaste-gtk4**: GTK4 + Adwaita helpers, the preferences widgets.
- `gpaste-daemon/` → **libgpaste-daemon**: the daemon's objects, documented in [`gpaste-daemon/AGENTS.md`](gpaste-daemon/AGENTS.md).

## Headers, layout and pkg-config

- **Every library splits its headers into an installed half and an internal one**, and a new header joins the internal half unless something outside the library names it. libgpaste-gtk4 installs exactly two types — the preferences dialog, and the preferences widget `prefs.js` embeds — while its groups, shortcut row and pages stay internal; its GIR is generated from `libgpaste_gtk4_public_sources` alone. The four pages are plain functions returning an `AdwPreferencesPage`, not types: they carry no state, and both callers build them from one list (`g_paste_gtk_preferences_pages_new()`). libgpaste's own lists are in `src/libgpaste/meson.build`, and libgpaste-daemon's split is described in its own `AGENTS.md`.
- **The core library's directory carries `apiversion`**, so it is renamed on every major bump (`gpaste-2/` → `gpaste-3/` for 51.0), and its includes are spelled `<gpaste-3/gpaste-macros.h>`. The same include text resolves in-tree (through `include_directories('.')` = `src/libgpaste`) and against the install prefix, which is what makes a broken installed header a build failure here rather than downstream. `gpaste-gtk4/` and `gpaste-daemon/` are named for their library and never move.
- **The installed layout** is one shared directory:

  ```
  include/gpaste/{gpaste.h, gpaste-gtk4.h, gpaste-daemon.h}   <- the three umbrellas
  include/gpaste/{gpaste-3/, gpaste-gtk4/, gpaste-daemon/}    <- per-library headers
  ```

  so all three `.pc` files declare `Cflags: -I${includedir}/gpaste` (meson `subdirs: 'gpaste'`), the line to check when the layout changes. `libgpaste` is versioned all the way through from `apiversion` (`libgpaste-3.so`, `gpaste-3.pc`, `GPaste-3`, `gpaste-3.vapi`); `libgpaste-gtk4`'s `4` is GTK's and `GPasteDaemon-1`'s is its own, so neither tracks the GPaste major.
- **Each library ships a `.pc`** (`gpaste-3`, `gpaste-gtk4`, `gpaste-daemon`). `requires:` is what a *consumer* must also satisfy — what the installed headers name, not what the library links — so `gpaste-daemon` requires only `gpaste-3`: no public daemon header names a GTK, GDK or GCR type, and those stay in the `Requires.private:` meson derives from `dependencies:`, with the optional libsodium, sqlite3, libsecret-1 and libmutter (`pwquality` is on `gpaste-3`, where the rating lives). Use `requires:`, never `libraries:`, which means `Libs:`.

## Settings

**Observe a setting with `notify::<key>`.** Every setting is a GObject property named exactly like its GSettings key, so there is no separate `changed` signal and `g_object_bind_property()` works directly; the callback takes a `GParamSpec *`, not the key. Prefer the detailed form: undetailed `notify` fires for all twenty-nine keys. `GPasteSettings`' one signal of its own, **`rebind::<key>`**, is an action to take (re-register a keybinding), carried only by the keybinding settings.

## D-Bus

Every interface GPaste speaks is described by an XML file that `gdbus-codegen` turns into both halves of the wire. **`data/dbus/org.gnome.GPaste3.xml` is the contract**: its comments document every method, signal and property, and are the first thing to read and to update when the interface changes. What follows is how the tree is built around it.

- **The XML is the source of truth**, installed to `$datadir/dbus-1/interfaces` (`dbus-1.pc`'s `interfaces_dir`, overridable with `-Ddbus-interfaces-dir`). `src/libgpaste/gpaste-daemon/org.gnome.Shell.SearchProvider2.xml` is gnome-shell's interface, kept only to feed codegen and deliberately **not** installed.
- **The generated code is internal**: produced by `gnome.gdbus_codegen()` from `src/libgpaste/gpaste-3/meson.build` and `src/libgpaste/gpaste-daemon/meson.build` (which exist so the output lands where the `<gpaste-3/…>` include style works), never installed, never introspected. `GPasteClient` is the whole public story. `grep -c Daemon3 build/src/libgpaste/GPaste-3.gir` must stay `0`.
- **`org.gnome.GPaste3` is generated into libgpaste**, the lowest library, because a GType registers once per process and gnome-shell loads libgpaste and libgpaste-daemon together. libgpaste-daemon uses the skeleton, so the declarations carry `G_PASTE_VISIBLE` through `--symbol-decorator`.
- **A `declare_dependency()` passes the generated *header*, never the whole codegen output**: `sources:` on a dependency is inherited by every dependent, which would compile `gpaste-daemon3.c` into each of them — the one-registration rule broken once per dependent. Only the library in `link_with:` builds the source; the same holds for `gpaste-shell-search-provider2.c` in `gpaste_daemon_headers_dep`. `nm -D --defined-only build/src/libgpaste/libgpaste-gtk4.so.* | grep -c g_paste_daemon3_` must stay `0`, and `153` for `libgpaste-3.so.0.0.0` alone (name the file: `.so.*` also matches the symlink and doubles the count).
- **Naming**: `org.gtk.GDBus.C.Name` maps the interface to `PasteDaemon3`, so generated symbols are `g_paste_daemon3_*` and never collide with the `GPasteDaemon` object implementing it. The `3` is the interface version, bumped for the 51.0 break; the bus name and object path are not versioned.
- **`GPasteClient` implements `GPasteDaemon3` rather than deriving from the generated proxy**, which would drag the generated class struct into the installed `gpaste-client.h`; the header, GIR and VAPI stay exactly as they are. It overrides the interface's `Active`, `History` and `Version` properties (`g_paste_daemon3_override_properties`) and keeps its own `g_signal`/`g_properties_changed` handlers, turning the wire signals into richer ones — which is why `g_paste_client_g_signal()` is the one place unpacking a `GVariant` by hand.
- **An item travels as `(ssubas)`**: uuid, value, kind, favourite, notes, answered by `GetItem`, `GetItemAtIndex`, `GetItems`, `GetHistory`, `GetFavourites` and `Search`. The type is spelled once in C, in `gpaste-3/gpaste-client-item.h`, as **two macros on adjacent lines** — `G_PASTE_ITEM_VARIANT_STRING` for `G_VARIANT_TYPE`, and `G_PASTE_ITEM_VARIANT_FORMAT` with `^as` for `g_variant_new()`/`g_variant_get()` — and the daemon's builder and the client's parser both go through them. `gpaste-3/gpaste-client-history.h` does the same for a history's `(st)` and `GPasteClientHistory`. `notes` is a reservation: always empty, never given a meaning until notes exist (#254), and empty rather than absent so a client needs no version check. **One value per item**, the one a user is shown; `g_paste_item_get_value()` stays for the in-daemon callers that never go near the wire (the image loader, `GetImage`, `Merge`, the growing-line test, the search regex, both storage backends).
- **`ListHistories` answers `a(st)`**, name and size together in the store's order, so a sidebar costs one call. The size comes from `g_paste_storage_backend_count_history()`, which every backend overrides so no listing materializes a history: SQLite counts over its read predicate on a short-lived read-only connection of its own (needing no key, and leaving the cached connection and derived key alone), the file backend walks the document in a counting mode building nothing. Only a read creates the placeholder file of a history that is not there; counting never does.
- **Every mutation answers what it did**: the `Add*` calls, `Merge`, `Replace` and `MakePassword` return the uuid that landed. Policy refusing an add (`min-text-item-size`, `max-text-item-size`, `trim-items`, `max-memory-usage`) is **`.Error.Rejected`** (`G_PASTE_ERROR_REJECTED`). Content the current selection already holds is not a refusal: it still goes through `g_paste_history_add()` (see `private_merge_into_head()`) and answers the uuid the history already has.
- **`MakePassword`** (documented in the XML and on `g_paste_history_make_password()`): `timeout` is in seconds, `u` on the wire and `guint` in the item, capped at `G_PASTE_PASSWORD_TIMEOUT_MAX` (65535, the `password-timeout` key's `<range>`) by `g_paste_password_item_set_timeout()`, both storage backends included — past it a countdown outlives every session it could run in, reading as expiring and never doing so. `gpaste-client --timeout` **refuses** a larger value rather than let it be capped, a number silently becoming a smaller one being a password expiring when nobody asked. `G_PASTE_PASSWORD_TIMEOUT_UNCHANGED` (`G_MAXUINT`) writes none, and a `NULL` name keeps a password's own; `gpaste-client make-password` uses both. Updating a password in place moves `GPasteHistory`'s memory total with its name (an unsigned total that would otherwise be subtracted twice), re-runs `private_check_memory_usage()` alone, and persists a full rewrite when evictions rode along, as `set_favourite()` does. Names are unique, since `DeletePassword` addresses a password by name: the check exempts the item itself and `G_PASTE_PASSWORD_ITEM_NO_NAME` (`"******"`, what a nameless password reads as, which the make-password shortcut creates). Renaming goes through `MakePassword` with the uuid a listing carries; there is no separate `RenamePassword` to drift from it. The make-password keyboard shortcut acts on a text item alone. Nothing is published, and running countdowns are updated by `g_paste_clipboards_manager_rearm_password()`, called by both the method and the shortcut. **`GetPasswordTimeout`** reads the timeout back.
- **`Upload` waits for the upload** and answers the url; adding it to the history is the keyboard shortcut's behaviour (`on_keybinding_upload_done()`). It is the one call `GPasteClient` gives a timeout of its own (`G_PASTE_CLIENT_TIMEOUT_UPLOAD`, ten minutes, beyond the `GDBusProxy` default of 25 s). What runs is the **`upload-command` setting** (default `curl -sS --data-binary @- https://paste.rs`, also named in the schema and `README.md`, and checked at release time), parsed with `g_shell_parse_argv()` and spawned as an argv: the item on stdin, the url alone on stdout. The daemon (`g_paste_daemon_upload()` and the comments around it) checks for a successful exit and an `http`/`https` url, never quotes what the command wrote, kills a command still running at `G_PASTE_DAEMON_UPLOAD_TIMEOUT` (nine minutes), and kills the child on any other failure too.
- **`ShowAbout` does not exist**: `ShowHistory` is a signal because only the extension can act on it, while an about dialog is the UI's own `about` action, which `gpaste-client about` activates with `g_paste_util_activate_ui ("about", NULL)` — working with no daemon, since the window registers `about` and `preferences` (`add_daemonless_window_actions()`) however the connection concluded. The extension offers no About.
- **Errors mean the same thing everywhere**: `NOT_FOUND` for a uuid or name matching nothing (`DeletePassword` included), `INVALID_INDEX` only for `GetItemAtIndex`, `INVALID_ARGUMENT` for an argument missing, empty or unusable — a history name that is a path is refused by `g_paste_util_history_name_is_valid()` — and `ALREADY_EXISTS` for a name taken (`AddPassword`, `MakePassword` naming *another* password, `BackupHistory`). `EmptyHistory` can fail. A new code goes in the enum and the `GDBusErrorEntry` table (see the daemon's `AGENTS.md`).
- **`Update(u action, u target, s uuid, t index)` names its item**, so a search or the favourites view can apply a change without re-running its query; the favourites view still re-queries on a pin change, the update naming the item rather than its flag. `target == ALL` carries neither. A replace minting a new uuid (an edit, a text item becoming a password, a growing line) reports `ALL`.
- **The current history is the `History` property**, read off the proxy cache and followed with `notify::history`. **`HistoriesChanged`** fires for every change to the set (backup, delete, an empty or switch naming a history that did not exist); `HistoryDeleted`/`HistoryEmptied` still carry the name, so a sidebar can update one row.
- **`ReportExtensionState`, not `SetExtensionState`**: the extension reports a fact, and `track-extension-state` decides.
- **Signals carry `Raw*` C names**, or the generated `update`, `history-deleted`… would collide with `GPasteClient`'s own; the daemon emits them with `g_paste_daemon3_emit_raw_*()`. **No signal shares a name with a method** (except `ShowHistory`, as the XML explains), since bindings map both onto one class.
- **Numbers on the wire are documented as annotations** (`org.gnome.GPaste3.ItemKind`, `.UpdateAction`, `.UpdateTarget`) so they come back from `Introspect()` — under GPaste's own names, never `org.gtk.GDBus.DocString`, which gdbus-codegen consumes. `grep -c org.gnome.GPaste3.ItemKind build/src/libgpaste/gpaste-3/gpaste-daemon3.c` checks it.
- **`StripRichText` keeps the item** (the XML and `g_paste_history_strip_rich_text()` explain the rest): the `text/html`/`text/xml` payloads `GPasteSpecialMime` names go, a plain text object replaces the rich one under the same uuid through `_g_paste_history_replace()` (carrying the pin, memory bookkeeping and biggest-item election), and the rich object stays intact for save workers borrowing its special values. The method answers nothing; its `found` out-parameter tells `NotFound` from `WrongItemKind` under the history's lock. The D-Bus handler refreshes only selections still carrying the text, through `g_paste_clipboards_manager_refresh_text()`, and the model emits no `selected`. A password never acquires rich text, `GPasteClipboardUpdate` skipping special mimes for a sensitive read.
- **`Merge` has to be daemon-side**, joining each item's *real* value.
- **`ay` needs `org.gtk.GDBus.C.ForceGVariant`**, or every PNG `GetImage` returns is truncated at its first NUL.
- **Handler signatures are not checked by the compiler**: `g_signal_connect_swapped (skeleton, "handle-x", …)` erases the prototype, so compare a new or changed handler with `struct _GPasteDaemon3Iface` by hand.
- **Client methods and daemon handlers are generated by macros** — `G_PASTE_CLIENT_METHOD*` in `gpaste-client.c`, `G_PASTE_DAEMON_HANDLER*` in `gpaste-daemon.c`, each explained where it is defined — giving `g_paste_client_x_sync()`, `g_paste_client_x()` and `g_paste_client_x_finish()`. **The gtk-doc block goes above the invocation**, g-ir-scanner matching a block by the name on its first line (as `gpaste-settings.c` does for its accessors). Add a method by adding an invocation; write a body by hand only for a real reason (a relative path to resolve, two out parameters, a precondition, `Reexecute`'s missing reply).
