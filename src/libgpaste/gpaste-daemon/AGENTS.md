# `src/daemon/` — `gpaste-daemon` + **libgpaste-daemon**

This file covers both the library under `src/libgpaste/gpaste-daemon/` and the executable under `src/daemon/`. The D-Bus interface rules it implements are in [`src/libgpaste/AGENTS.md`](../AGENTS.md).

The background service. Owns the clipboard history and exposes it over D-Bus (`org.gnome.GPaste`). Almost all of its objects live in the installed, introspectable **libgpaste-daemon** library (sources under `src/libgpaste/gpaste-daemon/`, umbrella header `src/libgpaste/gpaste-daemon.h`, `GPasteDaemon-1` GIR/typelib); `src/daemon/gpaste-daemon.c` is the thin executable entry point that links it. What stays in `src/daemon/` is what only that executable uses: the **GDK clipboard backend** (`gpaste-clipboard-gdk.{c,h}` and its `gpaste-text-content-provider.{c,h}`), which is why `gtk4-x11` is a dependency of the executable and not of the library. They are compiled straight into the binary, include each other with quoted local includes, and carry no `G_PASTE_VISIBLE` — nothing exports them. Its types keep the `GPaste`/`g_paste_` prefix, so the GIR passes an explicit `identifier_prefix: 'GPaste'` / `symbol_prefix: 'g_paste'` to place them in the `GPasteDaemon` namespace. Handles:

- Clipboard watching (primary + clipboard selections), through the backend-agnostic `GPasteClipboardProvider` interface
- The rich clipboard item type hierarchy: the abstract `GPasteItem` base and the five kinds deriving from it directly — `GPasteTextItem`, `GPastePasswordItem`, `GPasteColorItem`, `GPasteImageItem`, `GPasteUrisItem` — plus the `GPasteSpecialMime`/`GPasteBinaryData` helpers (the UI/client instead use libgpaste's lightweight `GPasteClientItem`). **The hierarchy is flat on purpose.** Uris and password items used to derive from `GPasteTextItem` while inheriting nothing from it, which is what forced `g_paste_item_equals()` to dispatch in both directions and made `G_PASTE_IS_TEXT_ITEM()` true for things that were not text. The base's `equals` compares kind and value, which is symmetric, so one dispatch does; only the image (checksum) and the password (a named one never matches, a nameless one matches by value) override it.
- Keybinding registration through the XDG GlobalShortcuts portal (`GPasteGlobalShortcutClient`, used directly by the keybinder); if the portal is unavailable, keyboard shortcuts are simply disabled
- The `keybindings-enabled` setting is a master switch: `GPasteKeybinder` gates `g_paste_keybinder_activate_all()` on it, caches in `self->enabled` the value it last applied (not whether the client ended up holding anything — a grab can fail on the far side), and rebinds on `changed::keybindings-enabled` only when the setting no longer matches it (GSettings emits `changed` for any write, including one that re-sets the value it already holds). `self->enabled` is seeded from the setting in `g_paste_keybinder_new()`, before anything can notify about it: zero-initialised it reads as off while the setting defaults to on, and a change landing before `activate_all()` would compare against that. A switch flipped and flipped back inside the debounce window leaves the rebind the first write armed standing, and it costs nothing: the set it hands over is the one the client already holds, and it recognises it and stays put. That is the general fix for a redundant rebind — an accelerator written back to the value it already had is the same waste — and it is why the keybinder has no special case of its own for the switch
- Rebinds are **debounced** on a 250 ms timeout (`keybinder_rebind_all()`): an accelerator typed into the preferences writes its GSettings key on every keystroke, and each write would otherwise cost a full ungrab and grab — a D-Bus round trip each — and reopen the window with nothing grabbed in between. A pending timeout is re-armed rather than left alone, so the delay is measured from the *last* write of the burst; throttling instead would fire mid-edit and cost a rebind per 250 ms. The source holds the keybinder **weakly**, `dispose()` being what cancels it
- `g_paste_keybinder_activate_all()` deactivates every keybinding before it activates them, and that pair is load-bearing: `g_paste_keybinding_activate()` caches the parsed keycodes and `_keybinding_activate()` skips a binding that is already active, so without the deactivate an edited accelerator would never be parsed anew. It deactivates the *keybindings* only — the `_keybinding_deactivate()` walk it opens with — not the client's grabs, and it does so whatever the master switch says. The client is then handed the new set in one `grab_all()` — an empty one when the switch is off, which is how a rebind that turns the shortcuts off releases them — and one asked to ungrab first would have nothing left to tell a set that has not changed from a new one. `grab_all()` replaces whatever the client holds, so the ungrab was only ever redundant — which is why there is no public `deactivate_all()` counterpart to `g_paste_keybinder_activate_all()`: nothing was left calling it once the rebind path stopped, and it was the one place that moved `self->enabled` without a grab to match
- History persistence to disk: `GPasteHistory` owns the in-memory model and dedup/size policy, but delegates the asynchronous I/O to `GPasteHistorySaver`. Each mutation records an operation (`g_paste_history_saver_record` with a `GPasteHistorySaveOp` — add/remove/replace/clear/full — plus the item/uuid involved and, when the backend will consume it, a snapshot of the items: incremental backends only get one on *add*, where it is reconciled against; the other operations pass NULL). An incremental backend (see below) applies the queued operations in order; a non-incremental one rewrites the whole snapshot, so the saver collapses the queue down to the latest snapshot (the previous coalescing behaviour). Loads carry a `save_after` flag so a snapshot-rewriting backend persists its read-time normalization after a history switch; the saver drops it for incremental backends (they normalize on open): a load reads at most `max-history-size` rows, and the next add reconciles the store down to the loaded snapshot, so rows beyond the cap survive only until then. The saver never touches the live list, so it shares no locking with the model; it hands load results back through a callback. The model itself is guarded by a **non-recursive** `GMutex` taken through two macros: `G_PASTE_DO_LOCK_HISTORY` just locks for the rest of the scope, while `G_PASTE_LOCK_HISTORY` — what public entry points use — additionally declares a `g_auto` scope guard *before* the locker, so its cleanup runs after the unlock. That guard is what emits the `SELECTED` signal: `g_paste_history_selected()` only records the item in `priv->pending_selection`, because emitting inline would drive the clipboards manager (hence GTK's clipboard and the X11 selection machinery) with the lock held, queueing every other caller — all the D-Bus methods included — behind it, and a handler calling back into us (`g_paste_history_remove()` when an item turns out to be invalid) would deadlock outright. The signal is still emitted before the caller regains control, so ordering towards clients is unchanged. Any new code path emitting a signal that can re-enter the history must go through the same mechanism.

**Bus-name ownership & handover.** Both daemons — the standalone `gpaste-daemon` and the one hosted in the gnome-shell extension (`daemon.js`) — own the single well-known name `org.gnome.GPaste`, and a clean handover between them is done through D-Bus name replacement rather than any stop/proxy protocol. `GPasteBus` always owns the name with `G_BUS_NAME_OWNER_FLAGS_ALLOW_REPLACEMENT`; `g_paste_bus_own_name_full (self, replace)` — the only entry point, there is no plain `own_name()` — adds `G_BUS_NAME_OWNER_FLAGS_REPLACE` when `replace` is set. The extension **always** replaces (hosting the daemon in-shell is the future-proof path since GTK will drop X11); the standalone daemon replaces **only** when started with `--replace` (a bare argv flag stripped before GApplication sees it) — never from D-Bus activation or the systemd unit, so those automated paths can't ping-pong with the extension. Both daemons are **own-first**: `main()` (and `daemon.js`) create the bus and own the name *before* building the daemon, then do the storage work and build the `GPasteDaemon` from the `name-acquired` signal. Owning first fails fast (`name-lost` with `was_owned == FALSE`) when another daemon already holds the name and refused replacement, without popping a migration/passphrase dialog first. On a takeover the evicted daemon gets `name-lost` with `was_owned == TRUE`: it flushes the history, releases the storage lock and exits `0` (so the systemd unit doesn't land in `failed`). `was_owned` distinguishes a real takeover from a startup failure only. Failing to *export* an object is neither, so it gets its own **`export-failed`** signal (the bus warns about the cause itself; the listener decides what to do) rather than riding on `name-lost`: it is detected *after* the name was acquired (both daemons own the name first and add their objects from `name-acquired`), and reporting it as a lost name would have a listener blame a conflict with another daemon that never happened. Both daemons treat it as fatal — a name we own but cannot serve is worse than not owning it, since it also stops D-Bus from activating a daemon that would work: the standalone one flushes, unlocks and exits `EXIT_FAILURE`, and the in-shell runner stands down (releasing the name) exactly as it does on a takeover. The in-shell runner tells a deliberate takeover from the session bus connection simply dropping with `g_paste_bus_is_connected()`: with a live connection it stands down for good, otherwise it tears the bus down and re-owns the name on a fresh connection a second later (`g_bus_own_name()` does not survive its connection closing; a retry that still cannot acquire lands in `name-lost` with `was_owned == FALSE` and gives up, so a flapping bus can't spin). **`g_paste_bus_unown_name()` also unexports every object it registered** (`g_paste_bus_object_unregister_on_connection()`): a `GDBusInterfaceSkeleton` stays exported, and its path stays taken, until it is explicitly unexported — on gnome-shell's *shared, process-lifetime* session-bus connection that would make the next `enable()` fail to export and stand the runner down for good. The objects stay in the bus' list, so re-owning the name re-exports them. The GApplication singleton (`org.gnome.GPaste.Daemon`, distinct from the owned bus name) still dedups two standalone daemons, so `--replace` only ever targets the in-shell one. The activation/desktop/systemd files remain the fallback for non-GNOME or GNOME-on-X11 sessions without the extension. The daemon's unit is **`Type=exec`, with no `BusName=`**: re-executing releases the well-known name for as long as it takes the successor to ask for it back, and a `Type=dbus` unit is stopped the moment its `BusName=` goes away -- which killed that successor before it could, leaving the session with no daemon at all. Activation does not depend on the type: the bus starts the unit named by `SystemdService=` and waits for the name to appear either way. What it *did* depend on is the ordering `Type=dbus` implied — systemd gives such a unit `Requires=`/`After=dbus.socket` for free — so the unit spells those out: a daemon whose whole job is owning a name on the session bus has no business being started before the bus is there, and `After=graphical-session.target` only happens to be past it. The two `--gapplication-service` units (Ui, Preferences) stay `Type=dbus`; neither re-executes, and there the readiness handshake is worth having.

**History flush & the storage lock.** Handover is race-free because history *loads* are gated on a process-wide advisory lock (`g_paste_storage_backend_lock`/`_unlock`, a `flock` on `<history-dir>/lock`) acquired inside the saver's load worker thread before the first read and held for the process lifetime; the successor blocks on it until the previous owner releases it, so it never loads a stale history mid-flush (the kernel drops the lock if the holder crashes). That wait deliberately happens *outside* the global mutex guarding the lock fd — it can last as long as the previous daemon takes to finish writing, and `_unlock()` runs on the **main** thread of every exit path, so holding the mutex across it would block (in the gnome-shell host, freeze) the compositor for that whole time; `_unlock()` instead raises a flag the waiter polls, so a teardown while still waiting gives up rather than installing a lock nobody wants. **Neither way out of that wait holds the lock**, so the load task asks the cancellable again the moment it returns and reads nothing at all: opening the store — which on the sqlite backend creates it and migrates its schema — is the very thing the lock keeps out of a flush still running, and a read that never happened answers **unreadable** for the same reason a cancelled one does. **The load's `GCancellable` is polled in that same loop, and answers a different question**: the flag says *this process* has let go of the lock and wants none, where the cancellable says *this load* has been given up on — superseded by a newer one, abandoned by the owner (`g_paste_history_saver_abandon_load`), or belonging to a saver the owner has replaced (`_detach`). It is the load's, so it goes on down into `g_paste_storage_backend_read_history()` as well: the file backend asks it once, before the call that reads and decrypts the whole document (neither that nor the parse after it stops halfway, so there is nowhere else the check would save work), and the sqlite backend asks it before its first step and then per row, where each one is a decryption and possibly an image — before the first step because a store with no rows to walk would otherwise report a cancelled read as a complete, empty history. Either way a read a cancel got in front of answers **unreadable**, exactly as a corrupt row does — a partial history is one nothing may persist over, which is what `readable` is for. That cancel is also why the load task sets `g_task_set_check_cancellable (task, FALSE)`: whether the read completed is the *result's* to say and whether anyone still wants it is the generation's, so GTask turning a cancelled load into an error of its own on top would only be a second answer to both. Every exit/handover path first calls `g_paste_daemon_flush` → `g_paste_history_flush`, which sets a `stopped` flag (no further changes are recorded) and `g_paste_history_saver_drain`s the saver: it waits for the in-flight worker write via a `GMutex`/`GCond` handshake (it can't spin the main loop, which is where the write-done callback runs) then applies any queued writes synchronously. So after `flush()` returns the on-disk history is complete *without* pumping the main loop, and the lock is released only afterwards. `drain()` deliberately leaves `write_in_progress` set: the drained task's completion callback is still queued on the main context and will clear it (and pick up anything recorded meanwhile), whereas clearing it in `drain()` would let a `record()` made after a *resumed* handover start a second worker while that callback starts a third — two threads rewriting the same history at once. **`DeleteHistory` is ordered against all of this**, since a delete that loses its race silently resurrects everything the user asked to destroy: `g_paste_history_delete` refuses outright while `stopped` (the store belongs to the successor daemon, or to a migration rewriting it — the D-Bus method turns that `G_IO_ERROR_BUSY` into the reply and skips the deleted/switch signals), and for the *current* history it first `g_paste_history_saver_abandon_load`s (a load in flight is reading the very file being unlinked; its result would be installed right after, and the next clipboard change would write the whole pre-delete history back), then empties, then `drain`s before unlinking — the emptying records a write for this very history, which both backends would otherwise apply *after* the file is gone, re-creating it on open. The standalone daemon flushes+unlocks on `SIGTERM`/`SIGINT` and on a takeover (`name-lost` with `was_owned`). **Re-exec** is a special exit that must not lose the daemon: `reexec()` first synchronously flushes GApplication's shared session D-Bus connection (so mutation replies queued before the restart idle reach the socket), then flushes history (so the successor loads the final state) but does **not** quit or explicitly unlock, then `execl`s — first the installed `PKGLIBEXECDIR/gpaste-daemon` (correct after an upgrade: same path, new inode), then `/proc/self/exe` as a fallback (so a daemon run uninstalled from the build tree still re-execs itself). `execl` only returns on failure, and quitting *before* it (the historical bug) meant a missing/failed target left **no daemon at all**; instead, on a successful exec the process is replaced (its `O_CLOEXEC` storage-lock fd releasing automatically), and if every exec fails the daemon logs a warning and `g_paste_daemon_resume`s (clearing the `stopped` flag `flush()` set) so it keeps running rather than exiting.

**Prompts.** Everything the storage layer needs to ask the user goes through `GPastePrompt` (`gpaste-prompt.{c,h}`), a GObject *interface* in the same spirit as `GPasteClipboardProvider`: **no toolkit type appears in any signature**, so the migration/unlock/re-key logic lives in one place while its UI does not. Two concerns — `passphrase` (one entry, or two plus a strength meter when `confirm`) and `migration` (pick a backend, import, cleanup) — plus `report`, which is not one: `g_paste_prompt_report (title, message)` takes no request and has no `_finish`, because it asks nothing. It tells the user that something they set in motion did not happen (a passphrase that did not change, old data that was not deleted) where a log line would leave them believing it did; its **default implementation is that log line**, so a backend that skips it loses the dialog, not the report. Callers get the usual `_async`/`_finish` pair, but the **vfuncs take a `GPastePromptRequest` rather than a `GAsyncReadyCallback`**: GJS refuses to implement a vfunc that accepts a callback (*"VFunc … accepts another callback as a parameter. This is not supported"*), and being implementable from GJS is the entire point — the gnome-shell-hosted daemon can run neither `gtk_init` nor `adw_init`. A backend shows its UI, keeps the request, and answers it with `reply_passphrase()`/`reply_migration()`/`dismiss()` whenever the user gets round to it; the first answer wins and later ones are no-ops, so a dialog that both replies and then reports its own destruction is harmless. **Every way of losing the window must answer**, since the whole daemon startup is waiting on that answer — and it must answer from the window's **`destroy`** (dispose-time), never from a `g_object_set_data_full()` destroy notify alone: qdata is cleared in `finalize`, so anything still holding a reference (an animation, an a11y peer, a queued frame callback) would defer the answer for as long as it holds it. Both backends hook `destroy`; the Adwaita one keeps the destroy notify only to free the dialog struct, once the widgets carrying it are gone. The **default vfuncs dismiss**, which is the safe answer everywhere: nothing is migrated, and no passphrase is set, so an encrypted history stays locked rather than being loaded empty and overwritten. Anything both backends would otherwise duplicate is exported next to the interface — including `g_paste_prompt_passphrase_is_complete()` (what counts as an answer) and `G_PASTE_PROMPT_STRENGTH_MAX` (the scale a meter is built against, a literal repeating `G_PASTE_UTIL_STRENGTH_MAX` under a `G_STATIC_ASSERT`, since g-ir-scanner only carries a `#define` over to the typelib when it is one), so neither prompt can come to disagree with the other about them — `g_paste_prompt_list_storage_backends()` (the offered flavors, keeping the feature `#ifdef` ladder in one place) with `g_paste_prompt_storage_label()`, the live sensitivity rules `g_paste_prompt_can_import()` / `g_paste_prompt_backend_changes()`, and `g_paste_prompt_passphrase_strength()` (libpwquality, which is not introspectable, so this is the only way a JS prompt can show the same rating; it forwards to `g_paste_util_password_strength()`, since a passphrase and a password item are rated by the same rules and the graphical tool rates the latter without linking this library). `passphrase_finish()` hands back a **`GPastePassphrase`** (`gpaste-passphrase.{c,h}`), an opaque boxed type holding the cleartext in gcr secure memory (non-pageable, wiped on free) — never a `gchar *`: the whole point of the boxed type is that it carries its own free function, so `g_autoptr()` enforces `g_paste_passphrase_free()` at compile time and introspected callers cannot `g_free()` gcr memory. Build one with `g_paste_passphrase_new()` (%NULL and the empty string both give %NULL — an empty passphrase is no passphrase), read it with `g_paste_passphrase_peek()`. The libadwaita backend is `GPastePromptAdw` (`src/daemon/gpaste-prompt-adw.{c,h}`) — executable-only, like the GDK clipboard, since only the standalone daemon builds one. It is also why **libgpaste-daemon links neither libadwaita nor libgpaste-gtk4** (nor carries `Adw-1` or `GPasteGtk-4` in its GIR): the storage dialogs were the last thing in it that built one, and the single function it still wanted from libgpaste-gtk4 — an image checksum, pure GDK — moved to `g_paste_image_item_compute_checksum()`. `gtk4` itself stays, for `GdkTexture`, `GdkRGBA` and `gtk_accelerator_parse`; the widget stack does not, which is what matters for a library gnome-shell hosts and can initialise neither of.

**Storage backends & migration.** *Where* the history is persisted is abstracted behind `GPasteStorageBackend` (`gpaste-storage-backend.{c,h}`), a derivable GObject with `read_history_file`/`write_history_file`/`get_kind` plus optional `delete_history`/`list_histories` vfuncs, and optional incremental `add_item`/`remove_item`/`replace_item`/`clear_history` vfuncs (a backend that implements **all** of them reports `g_paste_storage_backend_is_incremental () == TRUE`; a partial implementation counts as non-incremental and the public wrappers fall back to a full `write_history`, which is what the file backend relies on). `read_history_file` returns a `gboolean`: **%FALSE means the history is on disk but could not be read back** (failed decryption, parse or I/O error — **a read that stopped short of the end counts**, which is why the SQLite read only answers `TRUE` once its final `sqlite3_step()` has come back `SQLITE_DONE` and the file backend's only once its parse reached the `END` state: the rows a cut-short read did reach are not the history, and handing them back as one is exactly what has the caller write that truncation over the rest — **and a row the read did reach and could not make anything of counts the same way**: a value that does not decrypt or that its kind's constructor refuses, a password's name that does not decrypt — a password is always written with one, `G_PASTE_PASSWORD_ITEM_NO_NAME` standing in for the ones the user gave none, so a `NULL` read back can only be a failed decryption, and building the nameless password out of it would have the next save write that placeholder over the name — a kind this build does not know, an image whose stored blob does not decrypt or that no texture can be made of — that blob being the whole of such a row, so there is nothing to fall back to: a row storing its image as a blob stores the checksum as its value, which names no file — is a record the store has and the model would not, so `g_paste_sqlite_backend_read_item()` says through an `unreadable` out-parameter which of its `NULL`s is that and which is a row dropped on purpose, an image read with `images-support` off, one with no date, or one whose row holds no blob to build it from, and only the first refuses the read. That last one is a drop and not a refusal because the blob is the whole of such a row: an image that is not in it is nowhere, and a row names no file — its value is the checksum — so nothing on disk is left behind for a dropped row either. That is stricter than the file backend, which warns about an `<item>` it cannot make sense of and reads the history around it, and the difference is deliberate: a row here is one the store still holds intact and only this build could not turn back into an item — a kind a newer GPaste wrote, an image whose loader is no longer installed — so handing back the rest as a complete history is what has the next save delete it, where refusing costs a session an empty history and costs the store nothing. A *special value* the read could make nothing of does **not** count the same way — an unknown mime (one a newer GPaste wrote), a value that does not decrypt: the item itself came back, and what it is missing is one of the several spellings of a value it still holds, so `g_paste_sqlite_backend_read_special_values()` drops that row and reads the item around it, exactly as the file backend reads an unknown mime and as the write path already skips one. It answers `FALSE` for a scan of its own that stopped short, and for nothing else), as opposed to a genuinely empty or absent one — an empty file, which is the placeholder the file backend creates for a never-written history, is `TRUE`. Every caller must honour it, because an unreadable history that looks empty is one save away from being destroyed: `import_histories` aborts the migration, and `GPasteHistory` sets its `unreadable` flag so nothing is ever written back over the intact data. That flag is deliberately distinct from the `stopped` one `flush()` sets (below) and tracks *the history currently loaded*, not the process: starting a load clears it and the load's own result sets it, so an unreadable history stops persistence for itself alone and never silently disables it for whichever history is switched to next — and deleting it clears the flag too, since the file it was protecting is the one being unlinked (leaving it set would shut persistence down for the rest of the process). A history whose XML carries an **unknown `<history version=>`** counts as unreadable rather than empty: its items are all skipped (we know neither where their value lives nor how to decode it), so reporting it readable would have the daemon persist that empty model over a file written by a newer GPaste on the very next clipboard change. A favourite is written as a `favourite="true"` attribute, and only when set, so an ordinary history's file is unchanged by its existence. A password's `timeout` rides beside its `name` on the same terms — written only when non-zero, so every password an older GPaste wrote reads back with no timeout, which is what it had. The format version deliberately **stays `2.0`** for it: bumping it would make an older GPaste treat the whole history as unreadable, where leaving it merely has that older GPaste warn about an attribute it does not know and drop the flag. **`2.0` is the only format read.** `1.0` — which held an item's value as text directly inside `<item>` rather than in a `<value>` child — was dropped, and takes exactly that path: an ancient history is refused and left byte-for-byte intact rather than migrated in place, so it can still be converted by loading it once with GPaste 2. It gets its own diagnostic saying so, since "unknown version" would be misleading for a format we ourselves wrote. `list_histories` has a shared default in the base class (enumerate the history dir for files ending in this backend's `get_extension`), so a subclass only overrides it when its listing is not one-file-per-history; **Both capped reads count only the items the cap can evict**: the file backend's parser tallies non-favourites against `max-history-size` and always admits a favourite, and the SQLite read applies its `LIMIT` to a `favourite = 0` subquery. A favourite that has sunk past the cap would otherwise be dropped on load and destroyed by the next save — the one thing pinning exists to prevent. That read therefore hands back more than `max-history-size` once the favourites are counted, which is how the caps themselves count, so **`g_paste_history_on_loaded()` runs both caps on what it just read** rather than leaving the difference to the next clipboard change: the two would otherwise disagree about what the history holds, and the rows over the cap would show until that change came and then vanish all at once. A trim there frees the backing files of what it drops, so it forces the save the load may not have asked for — and is skipped outright for a history that is `unreadable` or `stopped`, neither of which can be saved, where it would be deleting the images a store still points at (a history switch can land inside that flushed window). A truncated enumeration returns `NULL` + `GError` rather than a partial list, since a migration would otherwise import — and its cleanup delete — only the histories it happened to reach. **Every directory listing in this library goes through `g_paste_util_list_directory()`** (`gpaste-daemon-util.{c,h}`), which is where that rule and its companion ("a directory that is not there lists nothing, and is not a failure") are decided once rather than at each of the four places that enumerate one — as is the third rule they all depend on: an entry the enumerator did not answer with the requested attribute fails the listing rather than being added as a `NULL` that every reader takes for its end. It is asked for `G_FILE_ATTRIBUTE_STANDARD_NAME` everywhere, the display name being a UTF-8 *rendering* of those bytes: a history listed under a name that names no file would have `read`/`delete`/`rekey` all act on nothing and report that they acted. `g_paste_storage_backend_new (GPasteStorage kind, settings)` is the factory; `GPasteStorage` enumerates `NOOP` (`GPasteNoopBackend`, "no storage" — reads empty, drops writes, lists nothing, so the history lives only in memory for the session), `FILE` (the XML on-disk backend, `GPasteFileBackend`), `ENCRYPTED_FILE` (the same `GPasteFileBackend` created via `g_paste_file_backend_new_encrypted (settings, passphrase)` — an encrypted ".xmls" history; only offered when the encryption feature is built), `SQLITE` (`GPasteSqliteBackend`, below; only offered when the `sqlite` feature is built) and `ENCRYPTED_SQLITE` (the same `GPasteSqliteBackend` created via `g_paste_sqlite_backend_new_encrypted (settings, passphrase)`; only offered when both features are built). The *kind→flavor* logic is centralized: `g_paste_storage_is_encrypted (kind)` classifies the two encrypted kinds independently of the built features (a build unable to construct one degrades it to `NOOP`, never plaintext), and `g_paste_storage_passphrase_can_decrypt (kind, settings, passphrase)` verifies one, so the factory, keyring fallback, unlock prompts and migration dialog all work per-flavor. It scans **every** history and refuses if any data-holding one fails to open, rather than accepting on the first that does: histories can be keyed differently (a re-key that fails partway leaves exactly that, and `rekey_histories()` warns about it by name), and accepting then would load the others empty and let their next save destroy the real content. The per-history verdict is the `history_refutes_passphrase` vfunc -- only encrypted data the backend cannot open refutes a passphrase; a corrupt or foreign file says nothing either way, since telling the user their correct passphrase is wrong is worse than refusing the read. `GPasteHistory` picks its backend from the `storage-backend` GSettings key (a gschema `<enum>` of string nicks, read via `g_paste_settings_get_storage_backend`). The encrypted backend needs a passphrase, which the factory takes from a process-wide gcr-secure global (`g_paste_storage_backend_set_passphrase`/`get_passphrase`) set once at startup, so no constructor signature has to thread the secret; with no passphrase set it degrades to `NOOP` rather than writing plaintext. **A backend answers which flavour it is, and everything else follows.** `get_kind` is the only vfunc about its identity: `g_paste_storage_backend_get_extension()`, `..._is_encrypted()` and the rule that only an encrypted flavour keeps password items all derive from it in the base class, so a backend never spells out its own extension. The kinds themselves live in one `storage_flavours[]` table in `gpaste-storage-backend.c`, indexed by `GPasteStorage`, carrying the on-disk extension (`xml`/`xmls`/`db`/`dbs`, and the never-matching `noop`) and which class implements it; the shared `list_histories`, the migration's `detect_current_backend()` and the images cleanup's "is this name still stored by some flavour" check all read through it, iterating up to `G_PASTE_N_STORAGE` rather than carrying their own list. To add a backend: add an enum value + nick, a row in that table, and a `GPasteStorageBackend` subclass; implement the incremental vfuncs to persist single changes (the saver already feeds them the per-operation add/remove/replace/clear info), or just `write_history_file` to keep rewriting whole snapshots. **The SQLite backend** (`gpaste-sqlite-backend.{c,h}`, gated by the `sqlite` meson feature / `G_PASTE_ENABLE_SQLITE`) is the incremental reference: one database per history (`<name>.db`), an `items` table ordered by a monotonic `rank` (highest = front, so adds/selects never renumber; compacted on open in the astronomically unlikely case it nears overflow) plus a `special_values` child table (raw BLOBs, `ON DELETE CASCADE`), schema versioned through `PRAGMA user_version` (`migrate_schema` upgrades an older database stepwise on open; a database from a newer GPaste is refused and every operation no-ops rather than corrupting it). **Version 2 added the `favourite` column, version 3 the password `timeout`**, which is the mechanism's real use: one `case` per version, falling through to the next. The first two are a single `ALTER TABLE … DEFAULT 0` each, so every item an older GPaste stored comes back unpinned and every password with no timeout — which is what they were. Both new columns stay plaintext in the encrypted flavour, like `rank` and `date`: a pin and a duration are metadata, not content. Only image rows store a date; the column is nullable for the other kinds. An image row with a NULL date is skipped without refusing the whole history. `add_item` is an upsert-and-reconcile, not a bare INSERT: a `SAVE_ADD` also covers selects (move to front) and dedup re-adds, and size/memory evictions ride along without their own remove op, so after the upsert any stored uuid missing from the snapshot is deleted. `write_history_file` (still reached by the migration import and `g_paste_history_save`) rewrites everything inside one transaction, so a crash rolls back instead of losing data. Password items are skipped exactly like the plain XML backend. **Images are stored as blobs** (the `items.image` column, encrypted like any content column in the encrypted flavor — the one place the SQLite flavors beat `.xmls`, whose PNGs sit in plaintext next to it): on write the blob comes from the item's PNG bytes, falling back to reading the file a path-loaded item was read from when it carries none (e.g. a plain file → sqlite import); on read that blob is the only source — it builds the item via `g_paste_image_item_new_from_bytes` (no file, and no cache path on the item — nothing on disk backs a row), and a row holding none is dropped rather than looked for on disk, the import above being what puts the bytes there in the first place. `GPasteImageItem` carries its encoded PNG across IDLE for this (`get_png_bytes`; capture encodes once with `gdk_texture_save_to_png_bytes` and **writes nothing to disk** — persisting the image data is entirely the storage backend's job, so the NOOP backend genuinely stores nothing; the texture is rebuilt from the bytes on activation, and the bytes count towards the item's size for the memory cap). **An image item's value is its checksum**, not a path: what says *which* image it is, the same string whichever backend the bytes came back from (which is also what lets the migration verifier compare items by real value alone). *Where* the bytes were materialized is a separate, **nullable** `get_cache_path()` — set only by the backend that read the item off a file (`new_from_file`, `new_from_bytes_at_path`), `NULL` for a fresh capture and for anything the SQLite backend hands back, so everything reaching for a file (activation, `GetImage`, the blob fallback above) has one thing to check and does nothing when there is nothing to check. The `images/<history_name>/<checksum>.png` layout is the **file backend's own** (`g_paste_file_backend_image_path`, `_images_dir`, `_encrypted_path`, `_delete_image`) — per history so the same image copied in several histories gets one file each and evicting it from one never breaks the others — and it is *derived* at write time from the checksum and the history being written, never remembered by the item. Each backend materializes what it needs on write: SQLite the blob, the plain *file* backend the referenced `.png` (from item bytes, falling back to reading an existing file for path-loaded items), and the **encrypted file backend an encrypted `.pngs` side file** through the same stream converter as the history — its XML parser reads the `.pngs` back into item bytes, falling back to the plaintext path for not-yet-migrated entries, so no pixel reaches the disk in clear on any encrypted flavor. History eviction asks the storage backend to drop what it materialized outside its own store (`drop_item_data`, an optional vfunc): the file flavours sweep both the `.png` and `.pngs` siblings — the canonical one plus the item's own cache path when it sits elsewhere, absent ones being fine — and SQLite implements nothing, a blob going with its row. the base `delete_history` wrapper removes the history's whole `images/<name>/` directory — but only once **no flavor** still stores that name on disk, since a migration's cleanup deletes the source while the destination (same name) still references, or just materialized, images in that directory. That sweep **reports what it could not remove** through `delete_history`'s `GError` (never over the store's own failure, which is the one that says why): on the plain flavours those files are the clipboard's screenshots in cleartext, so "the history is gone" must not be answered while they are still sitting there. It sweeps everything it can regardless, and only the first failure is kept — and `import_histories` verifies by uuid *and content* (kind and real value, an image's being its checksum), not size — a bytes-carrying item legitimately weighs more than its path-based twin. The XML keeps naming those files: an image's item text is the path this backend materializes it in, its checksum riding along as an attribute, so a history file still points at the files beside it and a load hands the path back as the item's cache path. When the file backend writes items under a name that is *not* the one they were read from (`BackupHistory` writes the source's items under the backup's name), that derivation alone puts the references and the materialized copies under the target history without touching the shared items — backups own their images, and legacy shared-directory entries migrate to their history's own directory on their next save the same way. The connection is cached per path and a mutex serializes the vfuncs (a background load can overlap an in-flight write). **The encrypted flavor** (`g_paste_sqlite_backend_new_encrypted`, ".dbs" extension, needs the `encryption` feature too) encrypts the content columns — `items.value`, `items.name`, `special_values.data` — with libsodium's `crypto_secretbox`, each stored blob being nonce ‖ ciphertext; uuid/kind/rank/date/checksum stay plaintext so ordering, the LIMIT read and uuid reconciliation are untouched (an accepted metadata leak, traded for incremental updates; SQLCipher was rejected as an ABI-incompatible sqlite3 fork). The key is derived per database through the shared `g_paste_crypto_derive_key()` (Argon2id, MODERATE — the same entry point the stream converter uses, and the reason the bound below cannot be forgotten); the salt, Argon2 parameters and a key-check secretbox live in a `meta` table, **and both Argon2 parameters are read back from that table, so they are only as trustworthy as the file**: `g_paste_crypto_derive_key()` refuses anything past `SENSITIVE`, because an absurd opslimit would otherwise make the derivation run effectively forever -- a denial of service just from opening a history. A wrong passphrase is detected on open and refused like a newer schema (never given the chance to overwrite real data) — except an *empty* history, which is silently re-keyed for the new passphrase since there is nothing to lose (the shared verification applies the same rule, quietly). The passphrase is a `GPastePassphrase` and the derived key gcr secure memory, both on the instance; unlike the plain flavor it persists password items (real value + name). **Migration** (`gpaste-storage-migration.{c,h}`) is two concerns the standalone daemon runs back-to-back from its `name-acquired` handler (in `gpaste-daemon.c`, after registering the `AdwApplication` and owning the bus name, before the `GPasteDaemon` is built): the *migration* dialog (`g_paste_storage_migration_async()`, shown when the stored `storage-backend-revision` differs from `G_PASTE_STORAGE_BACKEND_REVISION` — `g_paste_storage_migration_needed()`) and the encrypted-history *decryption* (`g_paste_storage_decryption_async()`, below). All three concerns (those two plus the *re-key*) are ordinary `GAsyncResult` operations — `_async()` starts it, `_finish()` reads the outcome — chained migration → decryption → build the daemon; the library never spins a `GMainLoop` of its own and never calls `adw_init()`. They take **no `GCancellable`**: a concern is a dialog the user is looking at, and neither `GPastePrompt` nor the portal underneath it can be told to take it back down, so one could only ever be ignored. `_finish()` returns `%FALSE` when the prompt implementation itself failed — and, for the *re-key* alone, when the histories on disk could not be re-encrypted — the one outcome the user has to be told about (a passphrase change that did not happen must never be reported as one that did), so the re-key **says so itself** through `g_paste_prompt_report()` rather than leaving it to a caller that can only log: both of them do only that, and the `ChangePassphrase` D-Bus call was answered before any of this ran. Which of the two re-key failures it was decides the wording: a run whose rollback also failed left the histories split across both passphrases, and the reassuring "everything still opens with the previous one" is exactly what is untrue there. The migration's cleanup does the same when the old data it was told to delete is still there — it cannot be offered again (the dialog only offers a cleanup for a migration that changes backend, and the backend is now the chosen one), so the revision is bumped and the user is told instead. That outcome is also what the keyring decision reads: leaving encryption behind only drops the remembered passphrase once the encrypted data it opens is **actually gone**, not once its deletion was asked for; every ordinary outcome, dismissal included, is `%TRUE`, because what the user chose has already been applied to the settings and to the process-wide passphrase by the time the callback runs. A prompt that **fails ends its concern** rather than being asked again: a dismissal is a question the user answered, an implementation error is not one they can — re-asking would loop forever against an implementation that fails reliably, and would let a failure recorded on one round be reported over a later round that succeeded. Each executable registers an `AdwApplication` — registering it is what initialises libadwaita — then kicks off the dialog right after (before `run`) and lets its own `g_application_run()` loop drive it; the shared `G_PASTE_GTK_INIT_APPLICATION` macro passes no command line to `g_application_run()` on the remote-instance path, so GApplication does not mistake our flags and subcommands for files to open (none of our executables takes a file argument; the storage helper's subcommand is what used to hit this, before it was retired). The migration prompt (run *before* the `GPasteDaemon` is built so the chosen backend is in effect) lets the user pick a backend, optionally import the current history into it and optionally delete the old on-disk data afterwards (with a warning when cleanup is ticked without import). It is answered once per invocation, so backing out of a passphrase prompt re-asks it rather than leaving a dialog up — the state gathered so far is kept, so the second time round only asks what is still missing. A prompt's answer is **not trusted**: `import`/`cleanup` are clamped against `g_paste_prompt_can_import()`/`g_paste_prompt_backend_changes()` the moment the reply lands (in `on_migration_reply`, *before* `continue_apply()` reads them), not later on when they are acted on — a backend that answers "import and delete" for a migration going nowhere would otherwise make the user unlock the encrypted history for work that is then clamped away, and greying the toggles out is our own backends' courtesy, not a guarantee. The *current* backend is detected from the files on disk, not from the (possibly stale or unset) setting — `detect_current_backend()` walks a single table of the storing flavours in precedence order (`.xmls` encrypted, `.dbs` encrypted sqlite, `.db` sqlite, `.xml` plain), looking for the active history's file first, then falling back to whichever flavour has the most files (that same order breaks ties, so encrypted flavours win), else `none`; a listing it could not read answers *nothing at all* rather than `none`, leaving the stored setting alone, since "nothing is stored" and "we could not look" produce the same zero count and it is that answer which gets written down — and the detected value is both written to `storage-backend` up front (so dismissing the dialog keeps the right backend, and an encrypted history is never silently downgraded to `none`) and used as the import source / cleanup target, so migrating *any* direction works (e.g. encrypted → file). Import is only offered when the current backend stores data and differs from a storing target; importing from (or deleting) an encrypted current first tries the keyring (`g_paste_storage_keyring_apply_verified`, flavour-aware and shared with the startup unlock and the backend factory) and only prompts for its existing passphrase when none is remembered or the remembered one is stale (verified, with re-prompt), just as switching *to* encrypted prompts for a new one. Confirming writes `storage-backend` + bumps the revision; dismissing (which the prompt reports as its answer) leaves the revision so the dialog returns next start (forcing a deliberate choice — the privacy default of #357), keeping the detected current backend for the session. Between the two sits **"Keep as is"** (`G_PASTE_PROMPT_TEXT_MIGRATION_KEEP`, in both prompt backends, where a cancel button would be): an ordinary `reply_migration()` carrying the *current* backend and neither toggle — never what the combo happens to be showing, so it undoes the fiddling too — which settles the question through the confirm path, revision bump and all. The deliberate choice #357 asks for is a choice to leave things alone as much as a choice to move them, and it was already expressible (pick the current backend, both switches off, Apply); what it was not is findable, which is why the description names the button and says that closing the window is the other thing. **Neither the button nor a preselection is offered when the current backend is not one this build can construct** (an `.xmls` or a `.db` opened without encryption or sqlite): keeping a backend that is not on the list is not an answer `reply_migration()` accepts — it validates `chosen` against the offered set and dismisses anything else — so the button would silently become the dismissal it exists to avoid, and preselecting the first row instead would have the dialog claim a backend the user never chose. Nothing is selected until they say so, and Apply stays insensitive (in the shell backend, `_onApply()` also returns early: Enter reaches the default action through a key binding rather than through the greyed-out button). The same dialog is reached **on demand** without racing the running daemon: the preferences button and `gpaste-client migrate` reset `storage-backend-revision` (opening the same `migration_needed` gate) and call the existing `Reexecute` D-Bus method, rather than spawning the helper behind the daemon's back. That whole sequence is `g_paste_util_trigger_storage_migration()`: it opens the gate (reset + `g_paste_settings_sync()`, so the daemon sees the write whichever path lands) and then runs `g_paste_util_reexecute_daemon()` — the *same* re-exec a plain `gpaste-client daemon-reexec` runs, so the two verbs can never drift. A daemon honouring the re-exec tears its D-Bus connection down before replying, so a missing reply (`G_DBUS_ERROR_NO_REPLY`, matched with its domain — a bare code comparison would also match `G_IO_ERROR_NOT_DIRECTORY`) is the expected success and leaves the `GError` unset — read that way by `g_paste_client_reexecute_sync()`/`_finish()` themselves, hand-written rather than generated for exactly that, so an asynchronous caller such as the graphical tool's Restart does not report a failure for every restart that worked; anything else propagates, and `gpaste-client` (only there — it is the one caller that can find the pid file) falls back to `SIGUSR1`-ing the pid the daemon wrote, for a daemon too old for the method. The standalone daemon re-execs and re-runs exactly this startup migration; the gnome-shell-hosted daemon, which cannot re-exec, instead handles `reexecute-self` by flushing, running the `migrate`/`decrypt` concerns and reloading its backend in place (`g_paste_daemon_reload_storage` → `g_paste_history_reload_backend`, guarded by the same `migration_needed` check so a plain `daemon-reexec` stays a no-op there). Both gates and the reload read the keys back with **`g_paste_settings_reload()`** first: `storage-backend-revision` and `storage-backend` are written by *another* process (`gpaste-client`, opening the gate before it asks for the re-exec) and there is no ordering guarantee that dconf's change notification reaches the shell before the `Reexecute` call does, so trusting the cached copy would silently skip the migration or resurrect the flavour just left behind. `reload_backend` also **detaches** the saver it replaces (`g_paste_history_saver_detach`): an in-flight load keeps the old saver alive through its own task reference, and its pre-migration result would otherwise be installed over the freshly loaded one. The reload itself is asynchronous like every other load — reading (and, encrypted, deriving the Argon2id key) inline would freeze the whole compositor. A cancelled on-demand migration leaves the revision reset, so the dialog returns next start — the same deliberate-choice behaviour as an upgrade. When an **encrypted flavour** is chosen, applying first raises the passphrase prompt with `confirm=TRUE` (two fields, a GNOME-style strength meter — `g_paste_prompt_passphrase_strength()` scores it with libpwquality and the Adwaita backend shows a colour-graded `GtkLevelBar` plus libpwquality's hint, gated on the optional `pwquality` feature — and a data-loss warning) and sets the global passphrase before importing/storing; an already-configured encrypted history is unlocked (the *decryption* concern, `g_paste_storage_decryption_async()`) with the same prompt (`confirm=FALSE`) through the shared `unlock_prompt` helper — keyring first, then prompt — which the migrate-from-encrypted import path reuses too. The entered passphrase is *verified* before use (`g_paste_storage_passphrase_can_decrypt`, which asks each flavour per history — the file one decrypts the `.xmls`, the sqlite one opens the key-check secretbox in the `.dbs`): a wrong one re-prompts with an error (the `error_message` argument) instead of being accepted — accepting it would load an empty history and the next save would overwrite, and destroy, the real still-encrypted data. The prompt lives in the daemon, not the UI. When the `libsecret` feature is built (`G_PASTE_ENABLE_LIBSECRET`, which also requires encryption), the prompt grows a "Remember this passphrase" toggle that stores it in the keyring (`gpaste-storage-keyring.{c,h}`, a single attribute-less `SecretSchema`); the decryption concern tries the keyring first (`g_paste_storage_decryption_needed()` → `g_paste_storage_keyring_apply_verified()`) and only prompts if nothing was remembered or the remembered passphrase no longer decrypts the history (a stale entry is discarded, not used). The same verification guards the in-process keyring fallback in `g_paste_storage_backend_new` (the gnome-shell daemon path, which never runs the prompt). gnome-shell runs the very same `_async` functions **in process**, passing its own `GPastePrompt` (`src/gnome-shell/prompt.js`) instead of the libadwaita one; `daemon.js` promise-wraps the three `_async`/`_finish` pairs by hand in `callStorageConcern()`, and `_runStorageConcern()` logs a rejection and carries on to the next concern. **`Gio._promisify` cannot be used on them**: they are static functions on the GI *namespace* object rather than methods on a prototype (see the JavaScript conventions in [`src/gnome-shell/AGENTS.md`](../../gnome-shell/AGENTS.md)), so the wrapper would either fail to stick or, called off a plain value in an ES module, throw a `TypeError` out of its own first line — either way every storage concern would silently do nothing, the migration dialog and the unlock prompt would never appear, and the daemon would load an unreadable history. There is no helper process and no passphrase crossing one: whatever a prompt settles on is set process-wide by the storage code itself, in the shell's own process, before `new_meta` loads the history. Only **one settle may be in flight**: a prompt can sit there for minutes, and a bus reconnect during that window runs `_onNameAcquired()` again, so `_settleStorage()` is a thin gate that hands a later caller the promise of the running settle (`_doSettleStorage`) instead of raising a second set of dialogs over the very store the first is rewriting. The standalone daemon guards the same window with a `settling` flag on its `DaemonContext`: its `ctx->daemon` check cannot, since the daemon is only built once the settle is over — precisely the minutes a dialog can be up for. Every other concern gets its own turn on `_serializeStorage()`'s chain instead — and **flushes from inside that turn**, never before queueing: `flush()` stops the history recording and makes every `Delete` over the bus fail with `G_IO_ERROR_BUSY`, so flushing up front would leave it that way for as long as an unrelated concern ahead of it keeps a dialog up, and a flush that ran before a settle the caller merely *joined* would be a flush that settle had already read past. That is why `_migrateInPlace()` runs `_doSettleStorage()` in its own `_serializeStorage()` turn rather than through `_settleStorage()`.

**History encryption** (`gpaste-secret-stream-converter.{c,h}`, optional — built only when the `encryption` meson feature finds libsodium, which also defines `G_PASTE_ENABLE_ENCRYPTION`): a bidirectional `GConverter` (the same final type does both directions via a `GPasteSecretStreamDirection` ctor argument) built on libsodium's `crypto_secretstream` (XChaCha20-Poly1305). The symmetric key is derived from a user passphrase with `crypto_pwhash` (Argon2id, MODERATE limits); the random salt and the Argon2 parameters are written into the stream header (`MAGIC · salt · opslimit · memlimit · secretstream-header`) so decryption reproduces the key. Plaintext is split into ≤4 KiB chunks, each emitted as a `u32` length prefix + ciphertext, the last carrying the secretstream FINAL tag (so truncation is caught). Both directions buffer internally (a `GByteArray` for pending input and one for produced output) to cope with the arbitrary buffer splits `GConverter::convert` hands them; "no progress" maps to `G_IO_ERROR_NO_SPACE`/`PARTIAL_INPUT` like GLib's own converters. The passphrase is a `GPastePassphrase` and the derived key **gcr secure memory** (`gcr_secure_memory_*`, non-swappable, wiped on free); the passphrase is retained for the converter's lifetime because the key is salt-dependent and `reset()` must re-derive it for a fresh stream. `GPasteFileBackend` uses it for the `ENCRYPTED_FILE` backend: it wraps its read/write file streams with the converter, uses the ".xmls" extension, and (unlike the plain backend) persists password entries — writing their real value (`g_paste_item_get_real_value`) plus the `name` attribute, since the file is unreadable without the passphrase.

**`GPasteGlobalShortcutClient`** wraps the XDG GlobalShortcuts portal (`org.freedesktop.portal.Desktop`) as a `GDBusProxy` subclass. It is the daemon's only keybinding mechanism: `g_paste_global_shortcut_client_grab_all(accels[])` / `_ungrab_all()` register and release shortcuts, and the `keybinding-activated(const gchar *id)` signal fires when one is pressed. The `GPasteKeybindingAccelerator` struct `{ const gchar *id; const gchar *accelerator; const gchar *description; }` is the transfer type between keybinder and client; arrays are null-terminated by `.id = NULL`, and `description` is the translated label the portal shows in its permission dialog. The array the keybinder hands over is the caller's and lives only for the call, so the client copies it (`accelerators_copy()`, freed with `accelerators_free()`) and asks `accelerators_match()` whether a new set is the one it already holds. The three are static: the client is the only thing that holds a set, and a `g_autoptr` cleanup for the struct would be wrong for the borrowed-string arrays the keybinder builds, which nothing distinguishes from the owned ones. The owned array is also the disposal flag: `NULL` means the client has been disposed of, an empty array that it is still usable and holds no shortcuts, and both methods tolerate a disposed client.

A portal session permits only one `BindShortcuts` attempt, so a session is spent as soon as its shortcuts are not the ones we want any more: changing the set, ungrabbing and disposing all close it, and a non-empty new set creates a fresh one with a `session_handle_token` of its own, the old session's path not being free yet. Handing the client the set it already holds, while a session or a live request exists, is a no-op — `GPasteSettings` emits a rebind for any write to an accelerator key, a write of the value already stored included, and going through with it would put the portal's permission dialog back in front of the user over a set nothing has changed. That is why the keybinder hands its whole set over without ungrabbing first. A successful bind may come back with a subset, including none: that is a valid user choice, not a reason to ask again for the ones left out, and the *requested* set stays the comparison key.

Each portal method answers a Request path, not an outcome. Both calls subscribe to `Request::Response` **before** making the method call, predicting the path from the connection's unique name and a random-plus-counter `handle_token`; a connection with no unique name has no path to predict, so the call is failed rather than made. If the method answers another path, the subscription follows it. Only `(ua{sv})` responses are decoded — a malformed signature is treated as failure (response 2) rather than left to `g_variant_get()`, which logs a critical and leaves the response untouched. A create handle must be a string or an object path and pass `g_variant_is_object_path()` before use, since it is handed to `g_variant_new_object_path()`, which aborts on anything else.

`awaiting_response` means the method callback has completed; `responded` means the Response callback came first. Whichever arrives last frees the request. Every task answer goes through `portal_request_take_error()` or `portal_request_return_boolean()`, because a failed CreateSession method may still receive a later Response after its task has been answered, and answering a task twice is a critical.

Requests are tracked in a non-owning list and hold the client through a `GWeakRef`. Their `GTask` has no source object and owns a `PortalBindData` carrying another weak reference and the generation the request was made for. D-Bus calls go through `g_dbus_connection_call()` rather than the proxy, since a proxy call would retain the client until its method reply. Every callback opens the weak reference and checks the generation; the task completion callback checks its *saved* generation before touching retry state, a task being dispatchable after the request that answered it was superseded.

Closing or replacing a session increments `generation` and retires the requests in flight. Binds are cancelled or completed as superseded; an unanswered create is instead kept for the session handle it may still be answered with, which has to be closed even after disposal. A create whose method call failed reports that failure at once but stays under the same retirement deadline, and its later Response can only close a session — never bind, never change revocation state. Retired creates expire after ten minutes, and also end when their unique owner disconnects. `dispose()` steals the whole request list before retiring it: weak locations are cleared before it runs, so a request freed there cannot unlink itself. Ordinary retirements walk a copy, freeing being what mutates the list.

`has_live_request()` counts only current-generation requests that are neither responded, retired nor cancelled: a cleanup-only create must never stand in the way of a new bind. The retry source holds the client weakly, is cleared on supersede, ungrab, disposal and portal loss, and re-checks the session and request state when it runs. A general failure (2) or a method error is retried up to ten times at one-second intervals — a backend that was still starting answers with exactly that, and nothing else would ever ask again, a portal that stayed up sending no owner change to recover on. Exhaustion stays exhausted until the user writes an accelerator again, a bind succeeds, or the owner changes; an obsolete task can neither reset nor consume that budget.

Well-known name loss is **not** unique-owner death. `portal_owner` records the last observed well-known owner independently of retired requests, seeded from the proxy on the first request since construction need not notify its initial owner. A change closes the known session on its *old* unique owner and retires outstanding creates without abandoning their responses — a replaced portal can stay alive and go on holding grabs. Each request watches its own unique owner's death; only that makes its remaining responses impossible. Recovery binds the retained set when an owner appears and there is neither a live request nor a session — the name appearing because our own CreateSession D-Bus-activated the portal is not a restart, and starting over there would close the session that request is about to be answered with, taking the permission dialog the user is looking at down with it.

A request made while the name is owned subscribes to that unique sender. One issued while unowned uses the well-known sender and owns an activation watch of its own, so disposal before activation completes does not lose the cleanup path; once activation supplies an owner it adds a unique-sender subscription **without** dropping the first, a Response possibly being queued on it already. Completion removes both, discarding any duplicate delivery. Response handlers also check the recorded owner, so a replacement cannot answer an old request through the retained well-known subscription.

`Session::Closed` is subscribed to **before CreateSession**, across all paths and senders, and kept until disposal: subscribing from the create Response handler is too late when Closed is already queued behind that Response. The handler matches both the stored handle and its unique sender before changing anything. A remote close clears the session, retires pending binds, cancels retries and records `session_revoked`; a response of 1 from a current, non-retired request records the same user decision. That suppresses both the retries and the restart recovery — a portal restarting is not the user changing their mind. An explicit `grab_all()` clears it, an unchanged accelerator written again included, which is GPaste's retry affordance after a denial.

Session closes always target the unique owner that supplied the handle, and own their connection, owner and handle independently of the client, so a failed close can retry after disposal or replacement. They share the one-second, ten-retry budget; a disconnected owner, a closed connection or an already removed object ends the cleanup at once, and any other failure is warned about within that budget. No close may activate or reach a replacement portal.

Portal trigger strings use `CTRL`, `ALT`, `SHIFT` and `LOGO` (GTK's Super), and keep GDK's keysym names as they are: uppercasing `Return`, or spelling Super as `SUPER`, breaks the backend's parser. The keyval is canonicalised first (`g_paste_keyval_canonicalize()`, shared with the capture side) so a keypad alias goes out under the primary spelling of its group. An unsupported modifier — Meta, Hyper — produces no `preferred_trigger` at all: dropping it silently would ask for a different chord altogether, possibly a plain letter. With no preferred trigger, the portal asks the user for one.

**A password does not sit on the clipboard forever.** The countdown belongs to the *selection*, not to the manager: it lives on `GPasteClipboardsManager`'s per-provider `_Clipboard` record, one deadline each. A password on the primary and a password on the clipboard are two separate exposures, and none of the routes that put an item on a selection reaches every one of them — `select()` gives up on the first provider to refuse, `ensure_not_empty()` is one provider acting alone — so a single shared countdown could be cancelled for a selection its password had never left, which is that cleartext sitting there for the rest of the session with nothing to take it off. Per selection there is nothing to guard against: a route arms and retires the countdown of the selection it just wrote, and has nothing to say about any other's. Arming is `g_paste_clipboards_manager_arm_password()`, which every route that *publishes an item* ends in: `g_paste_clipboards_manager_select()` for the history's `selected` signal and the add path alike, the manager's own `ensure_not_empty()` wrapper for a provider re-owning a selection it found empty, and `rearm_password()` for a timeout written under a countdown already running. The two writes that skip it are the ones taking a password back *off*: `deselect_password()` putting the replacement or the empty string there, and `notify_finish()` copying one selection's text onto the other. Neither can be publishing a password — the first picks the first item that is not one, the second carries the text a provider just read — so neither has a countdown to arm. That last one is why `g_paste_clipboard_provider_ensure_not_empty()` hands back what it put there: it selects the history's head without going through `select()`, so a password bootstrapped onto a fresh daemon's empty selection would otherwise carry no countdown at all. `select()` arms **inside** its loop, as each provider accepts, which is where the item reaching a selection is known: a provider refusing it never took it and needs no countdown, and a refusal does not leave what the providers before it accepted sitting on their selections with nothing to take it off. **What the countdown is armed for is the item, held by reference, and what makes a firing act is a selection still carrying it** — `g_paste_clipboards_manager_selection_holds()`, comparing `g_paste_item_get_real_value()` against what the provider reports it holds. The history's head is not that question: an add can change the head without touching a selection (a tracked copy inserts at index 0 and emits no `selected`), and a selection can change without touching the head (tracking off, or a copy the size caps refused), so a head-as-proxy test both leaves passwords published forever and clears selections it never put one on. The reference is what keeps the item readable after the history has dropped it, and the value is what a provider can be asked about at all. Selecting the same password again does not restart its countdown: a selection re-taken every few seconds would otherwise push the exposure back for as long as that kept happening. The record therefore keeps the *duration* it armed for beside the item, since that is the one thing about an already-armed item `MakePassword` can change under it: same item and same seconds is the exposure already running out, a different number is a countdown to start over. **Expiring acts per selection.** Expiry first moves a non-password successor to the history's head without emitting `selected`, so a flush or a later empty selection cannot restore the expired head. Each provider is then written only after its current read identifies the password; an unrelated selection keeps its own contents. Moving an existing history item uses an extra reference with the transfer-full `g_paste_history_add()` API. **An emptied history is not a stale firing**: an `Empty` removes every item without emitting `selected`, so the password is still on the selection with nothing having replaced it, and with no item left to put there the empty string goes on through `select_text()` rather than the content being dropped — a provider reports emptiness by the *kind* it holds, so `""` still counts as something and `ensure_not_empty()` leaves it alone, where a genuinely empty selection would have it re-select the history's head, the very password just taken off. **An update in flight owns what its reply reads.** A provider refs itself for the whole read (`gpaste-clipboard-gdk.c`, `gpaste-clipboard-meta.c`) because the read spans main-loop iterations; the manager's side of it holds a `_Clipboard` record the manager owns, so `bootstrap_ready`/`update_ready` are handed a struct carrying a **ref on the manager** rather than the bare record, the records are freed in `finalize` rather than `dispose`, and both callbacks bail (releasing the item they were handed) when `history` is already `NULL` — a `g_object_run_dispose()` during a pending read is dispose running while such a ref is out. **`g_paste_clipboards_manager_expire_password()` runs it early**, from `dispose` and through `g_paste_daemon_expire_password()`, and `g_paste_clipboards_manager_expire_password_async()` does the same for `g_paste_daemon_reexecute()`, which must not hand the successor a selection still being classified: a daemon standing down leaves the selection behind it, and `store()` hands it to the clipboard manager to survive the exec while the successor arms nothing for an item it merely loaded — either way a password left there would outlive its timeout by the whole session. **The `Reexecute` invocation is held through expiry and completion revalidation.** A standalone exec closes the connection on success and reports an error if both `execl()` attempts fail. The `reexecute-self` host signal returns a boolean: the Shell host returns true after scheduling its in-process migration. Deadline and host failures remain errors in the CLI; only `UnknownMethod` permits its legacy SIGUSR1 fallback. **Every way into a re-exec takes that wait.** SIGUSR1 goes through `g_paste_daemon_reexecute()`, and the preferences migration button uses the asynchronous client method. The pending request holds the daemon through a `GWeakRef`: its task sits in the list of the daemon's own clipboards manager. The task that wait hangs on carries **no source object**: the manager's own `expiry_tasks` list holds it, and `g_task_new()` would have the manager reference itself (the rule above), so the callback opens its weak daemon reference and obtains the manager only if that daemon is still live, `expire_password_finish()` validates against `NULL`, and `dispose` returns whatever is still queued — the last answer a read with no manager left to land on can be given. **`dispose` is not enough where the process outlives the daemon.** The gnome-shell host stands its daemon down (an extension disable, a takeover) by dropping its reference, which only hands the wrapper to GJS' garbage collector — and mutter, which took a reference of its own when we published our `GPasteClipboardMetaSource`, goes on serving that source's bytes until the manager behind it is actually disposed. For a password those bytes are its cleartext, so `_releaseDaemon()` calls `g_paste_daemon_expire_password()` before its flush, where the selection it changes is still recorded. That is a method of its own rather than part of `g_paste_daemon_flush()`, which a live daemon also calls mid-life to persist before re-reading its store (a passphrase change, an on-demand migration): expiring there would be expiring for something that is not an exit. The standalone daemon needs neither — its selections die with the process — which is why only its re-exec ever did this.

**Expiry waits for a read to identify the selection.** Password expiry keeps its item and an overdue flag while a provider reports `is_reading()`: a hidden cache does not establish that the selection changed. Retiring the history head is independent of that ownership check: `retire_password()` moves the first non-password item with a transfer-full `g_paste_history_add(g_object_ref(item))`, which moves the existing identity without emitting `selected`. It happens before returning from forced expiry, so the Shell host can flush the replacement head immediately, while each selection is cleared only once its read identifies it. A selection that copied unrelated content must not be overwritten merely to move the history head. Timeout edits retain each candidate and its deadline until the current read identifies it; an unchanged duration preserves its running countdown. An intentional selection after that countdown has expired starts a fresh exposure, even if the old read has yet to conclude. Automatic restoration and timeout edits do not renew an elapsed deadline. Forced expiry survives explicit disposal, clearing the selection without consulting a released history.

**Restart completion is revalidated.** `expire_password_finish()` expires any password published after the task completed but before its callback ran. `G_IO_ERROR_PENDING` means another read needs classification; the daemon retries for at most thirty seconds. Each async wait has a sixty-second absolute deadline, independent of the read guards being restarted by new owners, so even the final retry ends inside the client's two-minute allowance. Each waiter owns its timeout source. A deadline failure answers only that caller and releases forced-expiry flags only when no other waiter remains. A PENDING finish likewise preserves another waiter's cleanup. Completion is dispatched from a separate idle: GTask can otherwise run the restart callback inline before the triggering update is added to history or a mutation replies over D-Bus. The CLI refusal/UnknownMethod regression intercepts signals to verify that only an unsupported method permits SIGUSR1. Only a successful finish permits an immediate store/re-exec, without yielding the main context.

**A pending strip belongs to one copy.** Another external ownership event or a successful independent publication retires its queued refreshes, even when the new text is equal. The provider's `published` signal reports the latter. The internal provider `select_item_full`/`select_text_full` helpers carry an explicit `independent` flag in the `published` signal. Automatic trim/image reselect and empty restoration pass false; public selection calls pass true, even if a rejected restoration synchronously selects the next history item. A same-copy reselect preserves queued strips; manager replacements clear their snapshots explicitly. Manager update data captures the copy serial when the read starts; synchronization cannot overwrite a selection with a later serial, regardless of which read replies first. Maintenance publications preserve the originating copy’s serial; external copies and explicit selections advance it. A newer synchronized copy supersedes an unfinished older read on the other selection: completed copies are retained, but capturing every transient owner is not guaranteed. The sync tests assert this history length as well as the final contents. The provider dispatchers alone hide cache getters while `is_reading()` is true; backend getters return their committed content.

**Every read an update fires is on one `GCancellable`, under one guard timeout** — a `GPasteClipboardReadGuard`, which is the pair of them (`G_PASTE_CLIPBOARD_READ_TIMEOUT`, 30s, in `gpaste-clipboard-content.h` so a stuck owner is given the same rope by either backend; armed before the first read goes out and dropped when the update concludes). **What that deadline measures is silence, not how long the batch has taken**: every read that reports goes through `g_paste_clipboard_update_maybe_done()`, which calls `g_paste_clipboard_read_guard_touch()` and starts the deadline over, so a transfer that is arriving slowly — a large image or a long file list over a forwarded or remote display, serving its INCR chunks at whatever pace it manages — is never cut off for being big, while an owner that has genuinely stopped runs out exactly as before. **Starting it over is a timestamp, not a new source**: `touch()` writes `last_read` and the timer, when it fires, re-arms itself for what is left of `timeout` since — so a text update firing eight reads keeps the one source it was armed with, rather than tearing one down and building another per read and re-arming, on the last of them, a deadline the conclusion cancels two lines later. `touch()` is a no-op on a guard already disarmed, that being a batch already concluded, which it would otherwise conclude a second time. The mutter backend's content read touches the guard by hand before `gdk_content_deserialize_async()`, that being the one read whose slot is chained into something else rather than counted out — without it the deserialisation would run on whatever was left of the deadline when the transfer started. The 30s is then for the one read that cannot report progress at all: a single big transfer is the only thing its batch is waiting on, so nothing lands to say it is moving — and the cost of waiting is a late item where the cost of giving up early is no item at all. A selection transfer has no deadline of its own: an owner that dies between advertising its targets and servicing the request, or an INCR transfer that stops halfway, would otherwise leave `pending` above zero for the rest of the session — and with it the item being built and the re-own a trimmed text is waiting for. **Cancelling is not what unblocks it**: `gdk_x11_clipboard_read_async()` and the selection input stream behind it hand the cancellable to their `GTask` and never connect to it, so those reads stay exactly where they were whatever is asked of them. So the guard *concludes the update itself* — which is why building the item, re-owning the selection and calling the caller back live in `g_paste_clipboard_update_conclude()`, separate from the `g_paste_clipboard_update_maybe_done()` that frees the update once `pending` reaches zero. **That whole lifecycle is one shared `GPasteClipboardUpdate`** (`gpaste-clipboard-content.{c,h}`): the guard, `pending`, `concluded`, `superseded`, the backend slot it is the in-flight update of, the content mimetype, the content-kind union, `reselect`, the mime results, and a ref on the provider — everything concluding an update reaches for, which is what lets the guard conclude one with no backend hook to call. `g_paste_clipboard_update_new()` hands it back armed and with one read outstanding (the caller's own, counted out at the end of `update()` so a batch whose reads all answered synchronously still concludes exactly once), and each backend adds only the calls that fetch the bytes. **One update at a time per selection.** Each backend hands `g_paste_clipboard_update_new()` its update slot and committed content cache. A successor supersedes the update in that slot. Reads write only the update's owned content; its conclusion commits the cache before invoking the callback. This keeps a partly read copy from entering the deduplication cache and suppressing the same text in its successor when the first update is abandoned. While an update is pending, provider getters expose neither the cached text nor its image checksum, and `is_empty()` answers false: the committed value is useful for deduplication but cannot establish what the new owner holds. Local publication also supersedes an outstanding update, so a late read cannot overwrite a user selection. **A change that starts no update supersedes just the same.** What makes the one in flight stale is the change, not the update replacing it, so the two paths where `update()` answers its caller and returns — the selection released, and an owner offering only types this build does not handle — call `g_paste_clipboard_update_supersede()` on their own slot, which is the same call `update_new()` makes and all that is left of it there. Left out, they are the one shape the slot does not cover: the previous owner's text lands with nothing marking it stale, so the older copy is added as the newest entry and written into the provider's cache — and on the ignored path that cache has just been set to `CLIPBOARD_CONTENT_IGNORED`, which is what a text read compares against for dedup, so it is not even recognised as the copy already sitting at the head. `superseded` is a flag of its own rather than an early `concluded` because the callback is still owed — it is what releases whatever the caller put behind the update — so a superseded update still concludes, with no item and no re-own, once its reads are in or its own deadline runs out — a deadline brought forward to the next turn of the main loop, since the callers that supersede without starting a successor leave nothing else to bound it, and an update that says nothing landing 30s later reaches a manager whose cache has moved on twice over, having held the provider (and on X11 the requestor window behind it) all that while. Marked and not concluded on the spot: concluding calls back into the clipboards manager, and doing that from inside `update_new()` would re-enter the very `notify()` that has not returned yet. What does happen on the spot is `g_paste_clipboard_update_release_content()`, which calls nobody back and lets go of everything of any size — a superseded texture is one nothing will ever be built from, and a superseded text can be a password's cleartext. The two used to keep a copy of that struct, of `conclude` and of the union teardown each, and had already drifted apart on how a late read was recognised. The cancel is still asked for, since a read that does honour it fails and counts itself out — *after* the conclusion, and that order is why the guard's timeout lives in `gpaste-clipboard-content.c` rather than in each backend: `g_cancellable_cancel()` runs the handlers connected to it in the calling thread, so a read failing from one of them would count itself out and free the very update being concluded. **A conclusion is finished with the update before it publishes anything**, for the same reason from the other end: re-owning the selection drops its previous owner — which on the mutter backend fails a transfer this update is still waiting on, synchronously — and the callback reaches the history, which publishes too, so the last read to count itself out under either of those frees the update. The mime results and the guard are therefore cleared, and the callback, `reselect` flag and `sensitive` answer taken into locals — with the provider's only ref, the update's, **taken over** into one of them — *before* the `select_item()` and the callback; and `g_paste_clipboard_read_guard_timed_out()` holds its own ref on the cancellable across `expired()` rather than reading it back off a guard that may be gone. What that leaves is the update struct outliving the update, freed only if those reads ever land. Nothing can be done about the struct itself — they hold the pointer — but everything of any size is let go of at the conclusion instead of at the teardown: `g_paste_clipboard_update_release_content()` drops the mime results and the union member, and the provider ref is taken over by the conclusion rather than held alongside it, that ref being what keeps a backend's requestor window and its interned properties on the X server. So an owner that stops answering leaves a counter behind rather than a whole texture and a live provider, and the update still finishes: the item is built, the caller is called back and its own bookkeeping is released. The teardown runs the same release a second time, which is what catches whatever a read landing afterwards stored on its way in — and it is also where the content mimetype goes, that one being what a read was fired *with* rather than what one brought back: the mutter backend hands that very pointer to `meta_selection_transfer_async()`, which reads it after the call returns, so freeing it at the conclusion would free it under a transfer the guard left running. **A read landing after the guard writes nothing anyone reads again**: what it stores in the update data is cleared a second time on the way out (hence the `g_set_str()` and the second `mime_results_clear()`), and it must not reach the *provider's cache* either — the item it describes never got to the history, and a cache holding it dedups it out of every later update, so re-copying that very text is rejected until something else is copied first. What says so is `g_paste_clipboard_update_is_expired()`, the one predicate both backends put that question through, and it asks the *update* and nothing else — `concluded || superseded`. `g_paste_clipboard_update_on_mime_read()` asks it too, so a mime landing late stores nothing: the second clear only comes once the update's last read reports, which a read that never does puts off for the session (`/clipboard/late_mime_read`). The cancel cannot answer it: `concluded` is set where the conclusion starts and the cancel is only asked for once it has finished, so a cancelled guard says nothing `concluded` has not already said, and in between there sits a guard that has not expired on an update that has already handed its provider on. The cancellable is then worth exactly one thing, which is not this: cancelling cannot fail the conversion request an X11 read starts with, but the transfer through the stream that request returns is `gdk_content_deserialize_async()` and, for a mime read, `g_output_stream_splice_async()` — both of which honour it, so a transfer that stalls partway is failed and counts itself out instead of holding the update for the session. Those take a `GCancellable` and nothing else, which is why it is one rather than a flag. A read landing there and reading `update->provider` before asking would cast a `NULL` — which is why both backends take the provider off the update *after* the question and not in the line that declares it. **`sync_text()` is guarded the same way**, being a read reachable straight from D-Bus (`SyncClipboardToPrimary`/`SyncPrimaryToClipboard`): concluding a sync is letting go of the ref it holds on the target selection, there being no text to publish, so a hung read costs a struct rather than a whole provider for the session. What it keeps alive is a `GPasteClipboardSyncData` — that ref and a guard — built and freed in `gpaste-clipboard-content.c`, so the two backends' syncs differ only in the read they fire. **A superseded callback is cleanup only (including resolving any expiry awaiting an independent publication).** `GPasteClipboardProviderUpdateCallback` receives an explicit `superseded` boolean beside the nullable item. Both manager callbacks release their state and return when it is true, without restoring an empty cache or synchronizing another selection. An ordinary callback with no item still performs the usual empty-selection handling. **The item the update built is `(transfer full)` to the callback and the update's own to release when there is none** — an update fired with no callback is part of the contract, what `update()` checks on each of its early returns — so it is held in a `g_autoptr` and stolen into the call. **What the update builds from is its own — text, texture, file list and colour alike — and not a pointer into the provider's cache**: the reads still running leave every route that publishes content free to overwrite it — a password countdown expiring, a `Select`, a `SyncClipboardToPrimary` — and each of those frees what the cache was holding, while the update outlives its content callback whenever anything else is still being read. All four live in one union tagged by `content_kind` — in the shared update, as in the provider's cache itself: a kind's read fills its member, the builder is handed that member and no other, and the teardown releases that one, reading or freeing another reinterpreting unrelated bytes. A `produced` flag says that read landed with something, a colour having no value that stands for none. **A re-owned selection waits for the whole update.** A text read that needs trimming and a GDK image capture set `reselect`. The conclusion publishes the complete item after the remaining MIME reads finish, so replacing the owner cannot abort those transfers.

**A rich-text refresh waits for the read.** A refresh requested while a selection is being classified keeps the stripped item until the read completes, is published only if the selection matches and the history still holds that snapshot, and replaces the incoming item before it is added to the history. An explicit selection or disposal drops pending refreshes.

**Clipboard backends.** `GPasteClipboardProvider` (`gpaste-clipboard-provider.{c,h}`) is a GObject *interface* that abstracts a single selection (clipboard or primary): it caches the current content, exposes `update`/`select_text`/`select_item`/`sync_text`/`ensure_not_empty`/`store`/`get_text`/`get_image_checksum`/`is_reading`/`is_clipboard` as vfuncs, and declares the `changed` signal (emitted by implementations via `g_paste_clipboard_provider_emit_changed`). Crucially, none of its method signatures expose toolkit types, so the `GPasteClipboardsManager` drives every backend through this one contract. Both concrete backends hold their current selection in a shared `GPasteClipboardContent` (`gpaste-clipboard-content.{c,h}`): a content-kind enum plus a tagged union (text/image-checksum string, file list, or RGBA) with shared `clear`/`get_text`/`get_image_checksum` helpers, so only the field matching the kind is ever live. The same module owns the cross-backend policy helpers — `g_paste_clipboard_content_classify_text` (the trim/min-max/dedup decision both backends apply to incoming text), `g_paste_clipboard_file_list_equal` (file-list dedup), `g_paste_clipboard_content_to_item` (what a finished read builds), `G_PASTE_CLIPBOARD_READ_TIMEOUT` with `GPasteClipboardReadGuard`, `GPasteClipboardUpdate` (a whole update in flight, above), `GPasteClipboardSyncData`, `GPasteClipboardMimeCtx`, the `add_read`/`add_mime_read`/`on_mime_read` an update counts its reads in and out through, and `GPasteClipboardMimeResults` with its `store`/`clear` (what the mime reads gathered, and what each list means). A read is counted in beside the call that fires it, never before the choice of whether to fire one: an arm that fires nothing would leave the update pending on a read that does not exist, and the guard only *concludes* such an update — it never frees it. The ten interface thunks each backend needs are generated by the `G_PASTE_CLIPBOARD_PROVIDER_DEFINE_VFUNCS (lc, UC)` macro; `ensure_not_empty` is a concrete method on the interface itself (driven by a per-backend `is_empty` vfunc), not reimplemented in each backend; it answers the item it put on the selection, or `NULL` when it left the selection as it found it, so a caller can act on a selection it did not perform itself. The daemon stays backend-agnostic: `g_paste_daemon_new (GPasteSettings *settings, GPasteClipboardProvider *clipboard, GPasteClipboardProvider *primary)` feeds the two providers the caller built to the manager, so the choice of backend lives entirely in the caller. A single `GPasteSettings` is threaded all the way through — the caller creates it once and the daemon (history, clipboards manager) and both providers share that instance rather than each making their own. The library ships one convenience wrapper, `g_paste_daemon_new_meta (settings, selection)` (mutter backend, used by the in-shell `daemon.js`, built only with `gnome-shell`); the standalone daemon builds its two GDK providers in `on_storage_ready` and calls `g_paste_daemon_new` itself, since that backend is not part of the library. `GPasteClipboardContent`'s helpers are marked `G_PASTE_VISIBLE` for exactly that reason — a provider living outside libgpaste-daemon still needs them. `new_meta`'s `selection` is the `MetaSelection`, typed `GObject *` so the introspected header needs no libmutter; GJS passes a `Meta.Selection` straight in. `GPasteClipboardGdk` (`src/daemon/gpaste-clipboard-gdk.{c,h}`) is the GDK implementation (the former `GPasteClipboard`), built on `GdkClipboard`; it requires the X11/XWayland backend because only X11 delivers *global* selection-ownership notifications. Construct it with `g_paste_clipboard_gdk_new_clipboard()` / `_new_primary()` (both returning a `GPasteClipboardProvider *`). A colour item is published as both `application/x-color` and a `text/plain` fallback (its `gdk_rgba_to_string()` form) so it can also be pasted into plain-text targets; the meta backend does the same. Text is published through `GPasteTextContentProvider` (`src/daemon/gpaste-text-content-provider.{c,h}`) rather than `gdk_content_provider_new_typed (G_TYPE_STRING, …)`, everywhere text is offered (`select_text`, `select_item`, and the colour item's textual half), and for one reason: **bare `text/plain` would otherwise be served as ASCII**. GTK registers the `text/plain` serializer for a `G_TYPE_STRING` with `ASCII` as its target charset and a `?` fallback (`string_serializer()`, `gdk/gdkcontentserializer.c`), so a client that asks for `text/plain` rather than for `text/plain;charset=utf-8` gets a `?` for every character outside ASCII. The class claims exactly two things — `G_TYPE_STRING`, so our own selections still answer `gdk_content_formats_contain_gtype()` and a local reader (one clipboard syncing into the other) gets the value straight from `get_value()` with no serialize/deserialize round trip, and `text/plain`, which it writes as utf-8 bytes into the stream GDK owns. Everything else stays GTK's: `gdk_clipboard_set_content()` unions that gtype with the mime types the serializers provide, so `text/plain;charset=utf-8` and the locale spelling are still advertised and still served by them, and `gdk_clipboard_write_async()` is what routes the two apart, handing a provider only the mime types it claims itself.

`GPasteClipboardMeta` (`gpaste-clipboard-meta.{c,h}`) is the experimental mutter implementation, built on `MetaSelection`. Unlike the GDK backend it is not a display client: it talks to mutter's server-side selection tracker, so it sees *every* selection ownership change globally (no keyboard-focus gating) — but that object is only reachable from inside the gnome-shell process, so the constructors (`g_paste_clipboard_meta_new_clipboard()` / `_new_primary()`) take the `MetaSelection` handed in by the shell glue (`global.display.get_selection()`). Reads go through `meta_selection_transfer_async()` into an in-memory stream; writes publish a source we keep a ref to so the resulting `owner-changed` is recognised as ours and skipped. Since mutter's `MetaSelectionSourceMemory` only ever advertises a single mimetype, writes use a file-local `GPasteClipboardMetaSource` (a `MetaSelectionSource` subclass holding an ordered mimetype list, a mimetype→`GBytes` map for byte payloads, and an optional typed `GValue` for GDK-serialised payloads). Plain text is stored as bytes under both `text/plain;charset=utf-8` and `text/plain`, and a text/uris item's special values (rich-text/HTML/XML, `x-special/gnome-copied-files`) are appended via `g_paste_special_mime_get()`, matching the `GdkContentProvider` union the GDK backend builds. Everything else is bridged through GDK rather than hardcoded mimetypes/byte formats: images (`GDK_TYPE_TEXTURE`), colors (`GDK_TYPE_RGBA`) and file lists (`GDK_TYPE_FILE_LIST`) are held as a `GValue`, the source advertises every format `gdk_content_formats_union_serialize_mime_types(type)` lists, and `read_async` lazily serialises the value (via `gdk_content_serialize_async`, closing the memory stream before `steal_as_bytes`) only for the format actually requested. Everything that source holds goes in **`dispose`** — the two tables, the `GValue`, and the mimetype list along with them — so `read_async` opens by refusing with `G_IO_ERROR_CLOSED` when they are gone: mutter can still be holding a source that has been disposed, and one that has must answer that it has nothing rather than look in tables that are no longer there. On read, `g_paste_clipboard_meta_pick_mime()` matches the offered mimetypes against the cached `gdk_content_formats_union_deserialize_mime_types(type)` set (preferring the canonical `image/png` / `text/uri-list`) and one `update_on_value`/`on_value_deserialized` pair decodes through `gdk_content_deserialize_async(.., type)`. So format coverage tracks GDK's installed loaders automatically, colors and uris are byte-identical to the GDK backend (fixing an `application/x-color` endianness mismatch the old hand-rolled ICCCM codec had, and gaining the `application/vnd.portal.filetransfer`/`files` mimetypes sandboxed apps need for file paste), and `images-support` gates capture in `update()` exactly as in the GDK backend. Only the text path keeps literal mimetypes (its GDK set is already exactly those two, and it needs the backend's own trim/length/dedup logic); `image/png`/`text/uri-list` survive solely as read-preference hints. It is gated on the `gnome-shell` build option and pulls `libmutter-51`; when that option is on it is compiled into `libgpaste-daemon` (which then links libmutter). The in-shell glue is `src/gnome-shell/daemon.js` (`GPasteDaemonRunner`): it runs the daemon inside gnome-shell — `g_paste_daemon_new_meta (settings, global.display.get_selection ())`, plus a `GPasteBus`/`GPasteSearchProvider` — with none of the standalone daemon's GApplication, signal handling or re-exec (its lifetime is the extension's; it owns the name first and always with replacement, builds the daemon from `name-acquired`, and exposes a `ready` promise the indicator awaits — see the ownership/handover notes above). gnome-shell cannot reload an extension's code from disk on wayland, so a plain `reexecute-self` is still a no-op; the exception is an **on-demand storage migration** (flagged by the client resetting `storage-backend-revision`), which is handled in place — deferred to an idle so the `Reexecute` dispatch unwinds first, it flushes, runs the `migrate`/`decrypt` concerns against its own prompt and calls `reload_storage` on the live daemon rather than recreating it (the daemon's self-referential D-Bus registration on gnome-shell's persistent connection makes a clean rebuild impractical). On a takeover (`name-lost` with `was_owned`, e.g. a manual `gpaste-daemon --replace`) it flushes, releases the lock and stands down for good until the next enable. The storage-migration dialog and encrypted-history unlock run in process, against `GPasteShellPrompt` (see Migration and Prompts). Note the `StorageBackend` static functions are introspected as `GPasteDaemon.StorageBackend.lock/unlock/set_passphrase` (class statics), not namespace-level functions. The same `MetaSelection` is used for both the clipboard and the primary provider: there is one per display and the two constructors select the `MetaSelectionType` (`CLIPBOARD` vs `PRIMARY`) internally.

To define a GObject that implements an interface, use `G_PASTE_DEFINE_TYPE_WITH_INTERFACE (TypeName, type_name, ParentType, IFACE_TYPE, iface_init)` (in `gpaste-macros.h`), as both clipboard implementations do.

The D-Bus method surface lives in `gpaste-daemon-methods.{c,h}`: free functions that take a small `GPasteDaemonMethods` context `{ skeleton, history, settings, clipboards_manager }` rather than the daemon's instance-private struct. **Errors are plain `GError`s in the `G_PASTE_ERROR` domain** (`gpaste-3/gpaste-error.{c,h}`, in *libgpaste* rather than the daemon library): a handler bails out with `G_PASTE_DBUS_ASSERT (cond, code, msg)` and the dispatcher has a single out-param to check. The domain is registered with `g_dbus_error_register_error_domain()` (from `g_paste_error_quark()`, which `g_paste_client_class_init()` calls so a client has it registered before any reply can carry one), which is what makes the mapping work both ways — the daemon's code picks the error name on the wire (`org.gnome.GPaste.Error.NotFound` and friends), and a client gets a `GError` back in the same domain instead of an opaque `G_DBUS_ERROR_REMOTE_EXCEPTION` string, so it can switch on the code rather than match on the message. That is also why the domain lives in libgpaste: both sides link it, so neither can drift. Adding a code means adding it to the enum *and* to the `GDBusErrorEntry` table beside it (a `G_STATIC_ASSERT` catches forgetting the second half); the names in that table are API. Image items are handed to clients as PNG bytes (`GetImage(uuid) → ay`) rather than through their file path, so where and how the daemon stores images stays its own business (which is what lets the SQLite backend keep them as database blobs); the toolkit-free `GPasteClient` exposes it as `GBytes` (`g_paste_client_get_image{,_sync,_finish}`) and libgpaste-gtk4's `g_paste_gtk_util_get_image_finish` is the GTK-side conversion to a ready-to-display `GdkTexture` (used by gpaste-ui for its thumbnails). **A colour needs no method of its own**, because the value on the wire *is* the colour: the daemon no longer decorates it (below), so a client drawing a swatch parses what it already has. **`GetUris(uuid) → as` stays** where that leaves nothing to ask for, because what it answers is an *array* and an item's value is one string: shipping the uris joined and having every client split them back apart is the parsing this whole arrangement exists to avoid. It answers uris rather than paths because any scheme reaches a uris item (what makes one is GDK deserialising the offer into `GdkFileList`, and `text/uri-list` carries `smb://` and `trash://` just as happily as `file://`), and `g_file_get_path()` has no answer for those. `GPasteUrisItem` reads them off its own `GdkFileList` (`g_paste_uris_item_get_uris()`) rather than splitting its value back apart, and the reply is a plain `GStrv`: `GPasteClient` lives in the toolkit-free libgpaste-3, so a `GdkFileList` would belong in libgpaste-gtk4 beside `g_paste_gtk_util_get_image_finish()`, the day a front end wants one. A password item still has no such method, deliberately: what it holds is the password. **The decoration itself is the client's**, which is what leaves only those two: the daemon sends an item's own content — a colour's colour, a files item's uris newline-joined, an image's dimensions and date, a password's *name* (never the password, which `get_value()` masks as `"******"`) — and each front end renders it, translating only the bare words `Files`, `Color`, `Image` and `Password` in its own catalogue. A files item is where rendering is more than a prefix: its uris are split, a local one is shown as its percent-decoded path with `$HOME` written `~` (a whole leading component only, so `/home/joe` never shortens `/home/joey`), anything else is left as the uri it is, and the lot is joined by spaces. That ran in the daemon once and got it wrong — a blind substitution over the uri spelled a home file `file://~/a`. The decoration itself is written once, in `g_paste_util_display_string (value, kind)` (`gpaste-3/gpaste-util.c`): `g_paste_client_item_get_display_string()` is that call cached per item, the daemon's search provider describes its results with it (the shell's interface takes finished strings, so those are the daemon's locale — nothing else can be done there), and the gnome-shell extension calls it straight through introspection (`GPaste.util_display_string()`), which is what keeps the extension from carrying a JavaScript copy of the same rules. It translates through the `GPaste` domain, which is also the extension's own (`metadata.json`), so the words come out in the locale of whichever process draws the row. `gpaste-client` deliberately decorates nothing: it is the scripting surface. The brackets are punctuation rather than language, so they are spelled in code — and the image is the one whose payload goes *inside* them, after a comma, because it reads as a description of the image rather than a name in front of one. The daemon still formats an image's dimensions and date, so those come out in *its* locale rather than the client's; structuring them would mean a field on the wire, and the divergence needs a daemon and a client running under different locales to show at all. `gpaste-daemon.c` keeps the object lifecycle, the signal emitters, the controller actions that need the GObject (`upload`, `reexecute`, `show_history`), and a dispatcher that builds the context and forwards. Everything but the `gpaste-daemon.c` entry point is compiled into the installed `libgpaste-daemon` shared library (exposed to in-tree consumers as `gpaste_daemon_internal_dep`), which both the `gpaste-daemon` executable and the test suite link.
