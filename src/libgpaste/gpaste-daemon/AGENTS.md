# `src/daemon/` — `gpaste-daemon` + **libgpaste-daemon**

This file covers both the library under `src/libgpaste/gpaste-daemon/` and the executable under `src/daemon/`. The D-Bus interface rules it implements are in [`src/libgpaste/AGENTS.md`](../AGENTS.md).

Most of the rationale behind what is described here is written as comments beside the code it explains; this file says what exists, where it lives, and the invariants that span several files. Read the comments of a function before changing it.

## Layout

The background service owns the clipboard history and exposes it over D-Bus (`org.gnome.GPaste`).

- Almost all of its objects live in the installed, introspectable **libgpaste-daemon** library: sources under `src/libgpaste/gpaste-daemon/`, umbrella header `src/libgpaste/gpaste-daemon.h`, `GPasteDaemon-1` GIR/typelib. Its types keep the `GPaste`/`g_paste_` prefix, so the GIR passes an explicit `identifier_prefix: 'GPaste'` / `symbol_prefix: 'g_paste'` to place them in the `GPasteDaemon` namespace.
- `src/daemon/gpaste-daemon.c` is the thin executable entry point that links it. What stays in `src/daemon/` is what only that executable uses: the **GDK clipboard backend** (`gpaste-clipboard-gdk.{c,h}` and its `gpaste-text-content-provider.{c,h}`) — which is why `gtk4-x11` is a dependency of the executable and not of the library — and the Adwaita prompt (below). They are compiled straight into the binary, include each other with quoted local includes, and carry no `G_PASTE_VISIBLE`: nothing exports them.

## Items, keybindings and the history model

- **Clipboard watching** (primary + clipboard selections) goes through the backend-agnostic `GPasteClipboardProvider` interface (see Clipboard backends).
- **Items**: the abstract `GPasteItem` base and the five kinds deriving from it directly — `GPasteTextItem`, `GPastePasswordItem`, `GPasteColorItem`, `GPasteImageItem`, `GPasteUrisItem` — plus the `GPasteSpecialMime`/`GPasteBinaryData` helpers. The UI and client use libgpaste's lightweight `GPasteClientItem` instead. **The hierarchy is flat on purpose**: a kind deriving from `GPasteTextItem` without inheriting anything from it would make `G_PASTE_IS_TEXT_ITEM()` true for something that is not text, and would force `g_paste_item_equals()` to dispatch both ways. The base's `equals` compares kind and value, which is symmetric; only the image (checksum) and the password (a named one never matches, a nameless one matches by value) override it.
- **Keyboard shortcuts** are registered through the XDG GlobalShortcuts portal alone (`GPasteGlobalShortcutClient`, used directly by `GPasteKeybinder`); when the portal is unavailable, they are disabled. The keybinder, whose comments carry the reasons (`gpaste-keybinder.c`):
  - honours the `keybindings-enabled` master switch by handing the client an empty set, caching in `self->enabled` the value it last applied (seeded in `g_paste_keybinder_new()`), and rebinding only when the setting no longer matches it;
  - debounces rebinds on a 250 ms timeout re-armed by every write, the source holding the keybinder weakly;
  - deactivates every keybinding before activating them (edited accelerators are only re-parsed that way), but never ungrabs: `grab_all()` replaces the client's whole set in one call, which is what lets it recognise an unchanged set and stay put. That is also why a switch flipped and flipped back, or an accelerator written back to its own value, needs no special case — and why there is no public `deactivate_all()` counterpart to `g_paste_keybinder_activate_all()`.
- **History persistence**: `GPasteHistory` owns the in-memory model and the dedup/size policy, and delegates the asynchronous I/O to `GPasteHistorySaver` (`gpaste-history-saver.c` documents its threading and ownership). Each mutation records a `GPasteHistorySaveOp` — add/remove/replace/clear/full — with the item/uuid involved; a snapshot of the items rides along only when the backend will consume it (a non-incremental backend always, an incremental one only on *add*, where it is reconciled against). An incremental backend applies the queue in order; for a non-incremental one it collapses to the latest snapshot. A load's `save_after` flag is dropped for incremental backends, which normalize on open. A load reads at most `max-history-size` rows and the next add reconciles the store down to the loaded snapshot, so rows beyond the cap survive only until then.
- **The history lock** is a non-recursive `GMutex` taken through `G_PASTE_DO_LOCK_HISTORY` (lock for the rest of the scope) or `G_PASTE_LOCK_HISTORY` (what public entry points use: it also emits the pending `SELECTED` signal once the lock is released, since emitting under it would queue every other caller, D-Bus methods included, behind the clipboards manager and deadlock a handler calling back in — see the comments in `gpaste-history.c`). The signal is still emitted before the caller regains control, so ordering towards clients is unchanged. Any new code path emitting a signal that can re-enter the history must go through the same mechanism.

## Bus-name ownership & handover

Two daemons can serve the bus: the standalone `gpaste-daemon`, and the one hosted in the gnome-shell extension (`GPasteDaemonRunner` in `daemon.js`). Both own the single well-known name `org.gnome.GPaste`, and hand it over through D-Bus name replacement rather than any stop/proxy protocol. The mechanics are documented on `GPasteBus` (`gpaste-bus.c`), in `src/daemon/gpaste-daemon.c` and at the top of `daemon.js`; the rules they follow:

- **Always replaceable, replacing only when asked.** The name is always owned with `ALLOW_REPLACEMENT` through `g_paste_bus_own_name_full (self, replace)`, the only entry point. The extension always replaces; the standalone daemon only with `--replace` (a bare argv flag stripped before GApplication sees it) — never from D-Bus activation or the systemd unit, so those automated paths cannot ping-pong with the extension. The GApplication singleton (`org.gnome.GPaste.Daemon`, distinct from the owned bus name) still dedups two standalone daemons, so `--replace` only ever targets the in-shell one.
- **Own first, then build.** Both daemons own the name before building the daemon, and do the storage work (migration, unlock) from `name-acquired`, so a daemon that is going to lose never pops a dialog.
- **Three outcomes, three answers.** `name-lost` with `was_owned == FALSE` is a startup failure; with `TRUE` it is a takeover, on which the evicted daemon flushes, releases the storage lock and exits `0` (so the systemd unit does not land in `failed`). A failure to export an object is neither and has its own **`export-failed`** signal; both daemons treat it as fatal, since a name owned but not served also stops D-Bus from activating a daemon that would work. The in-shell runner tells a takeover from a dropped connection with `g_paste_bus_is_connected()`: it stands down for good on the first, and re-owns the name on a fresh connection a second later on the second.
- **`g_paste_bus_unown_name()` also unexports every object it registered**, since gnome-shell's session connection outlives the daemon; re-owning the name re-exports them.
- The activation, desktop and systemd files remain the fallback for sessions without the extension. The daemon's systemd unit is **`Type=exec` with no `BusName=`**, and spells out `Requires=`/`After=dbus.socket` itself — the unit file's comments say why. The two `--gapplication-service` units (Ui, Preferences) stay `Type=dbus`: neither re-executes, and there the readiness handshake is worth having.

## History flush & the storage lock

Handover is race-free because **history loads are gated on a process-wide advisory lock** (`g_paste_storage_backend_lock`/`_unlock`, a `flock` on `<history-dir>/lock`), taken in the saver's load worker before the first read and held for the process lifetime. `gpaste-storage-backend.c` documents the wait, why it runs outside the mutex, and the two ways out of it (the released flag, and the load's `GCancellable`); `gpaste-history-saver.c` documents why neither holds the lock and so why the load then reads nothing and answers **unreadable**, and why the load task sets `g_task_set_check_cancellable (task, FALSE)`. The load's cancellable goes on down into `g_paste_storage_backend_read_history()`: the file backend asks it once before the read, the sqlite backend before its first step and then per row, and a read a cancel got in front of answers unreadable, exactly as a corrupt row does.

- **Every exit or handover path flushes first**: `g_paste_daemon_flush` → `g_paste_history_flush` sets `stopped` (nothing more is recorded) and `g_paste_history_saver_drain`s the saver, waiting for the in-flight write through a `GMutex`/`GCond` handshake and applying the queue synchronously, so the on-disk history is complete without pumping the main loop. The lock is released only afterwards. `drain()` leaves `write_in_progress` set on purpose (see its comment).
- **`DeleteHistory` is ordered against all of this** (`g_paste_history_delete`): refused with `G_IO_ERROR_BUSY` while `stopped` (the D-Bus method answers that and skips the deleted/switch signals); for the current history it abandons a load in flight, empties, then drains before unlinking.
- The standalone daemon flushes and unlocks on `SIGTERM`/`SIGINT` and on a takeover.
- **Re-exec must not lose the daemon** (`reexec()` in `src/daemon/gpaste-daemon.c`): flush the D-Bus replies, flush the history, keep the lock (its `O_CLOEXEC` fd goes with a successful exec), then `execl` the installed `PKGLIBEXECDIR/gpaste-daemon` and fall back to `/proc/self/exe`. It never quits before the exec; if every exec fails the daemon warns and `g_paste_daemon_resume`s.

## Prompts

Everything the storage layer asks the user goes through **`GPastePrompt`** (`gpaste-prompt.{c,h}`), a GObject interface with no toolkit type in any signature, so the migration/unlock/re-key logic lives in one place while its UI does not. The interface documentation in `gpaste-prompt.h` is the contract: the `passphrase` and `migration` concerns and the `report` that asks nothing, vfuncs taking a `GPastePromptRequest` because GJS cannot implement a vfunc taking a callback, defaults that dismiss, and no `GCancellable`. The rules a backend has to keep:

- **The first answer wins**, and later ones are no-ops, so a dialog that both replies and reports its own destruction is harmless.
- **Every way of losing the window must answer, from its `destroy`** — never from a `g_object_set_data_full()` destroy notify alone, which runs at finalize (see `gpaste-prompt-adw.c`). The whole daemon startup is waiting on that answer.
- **Anything both backends would otherwise duplicate is exported next to the interface** — what counts as an answer, the strength scale and rating, the offered backends and their labels, the migration toggles' sensitivity, the remember-switch state and every word (`GPastePromptText`) — so neither prompt can come to disagree with the other. `g_paste_prompt_passphrase_strength()` is the only way a JS prompt reaches libpwquality, which is not introspectable; it forwards to `g_paste_util_password_strength()`, so a passphrase and a password item are rated by the same rules.
- `passphrase_finish()` hands back a **`GPastePassphrase`** (`gpaste-passphrase.{c,h}`), an opaque boxed type holding the cleartext in gcr secure memory — never a `gchar *` — so `g_autoptr()` enforces `g_paste_passphrase_free()` and introspected callers cannot `g_free()` gcr memory. `g_paste_passphrase_new()` gives `NULL` for `NULL` and for the empty string; `g_paste_passphrase_peek()` reads it.

The libadwaita backend is `GPastePromptAdw` (`src/daemon/gpaste-prompt-adw.{c,h}`), executable-only like the GDK clipboard; the shell's is `prompt.js`. That is why **libgpaste-daemon links neither libadwaita nor libgpaste-gtk4** (nor carries `Adw-1` or `GPasteGtk-4` in its GIR), which matters for a library gnome-shell hosts: its image checksum is `g_paste_image_item_compute_checksum()`, pure GDK, and `gtk4` stays only for `GdkTexture`, `GdkRGBA` and `gtk_accelerator_parse`.

## Storage backends

*Where* the history is persisted is abstracted behind **`GPasteStorageBackend`** (`gpaste-storage-backend.{c,h}`), a derivable GObject. The header documents each vfunc; in outline:

- `read_history_file`/`write_history_file`/`get_kind`, optional `delete_history`/`list_histories`/`count_history`/`rekey`/`drop_item_data`/`history_refutes_passphrase`, and optional incremental `add_item`/`remove_item`/`replace_item`/`clear_history`. A backend implementing **all** of the incremental ones is `g_paste_storage_backend_is_incremental()`; a partial set counts as non-incremental, and the public wrappers fall back to a full write (the file backend relies on that). Every vfunc takes the history's **name**, never a path.
- **`read_history_file` answering %FALSE means the history is on disk but could not be read back**, as opposed to empty or absent — and every caller must honour it, since an unreadable history that looks empty is one save away from being destroyed: `import_histories` aborts the migration, and `GPasteHistory` sets its `unreadable` flag so nothing is written back. What counts as unreadable is in the comments of each backend's read: a read that stopped short (SQLite before `SQLITE_DONE`, the file parser before its `END` state), a cancelled one, a row the SQLite read could make nothing of (`g_paste_sqlite_backend_read_item()`'s `unreadable` out-parameter, as opposed to rows dropped on purpose), and an unknown `<history version=>`. The SQLite read is deliberately stricter than the file backend, which reads around an `<item>` it cannot make sense of; a *special value* the read cannot use (an unknown mime, a value that does not decrypt) is dropped in both, the item around it still being read (`g_paste_sqlite_backend_read_special_values()` answers %FALSE only for its own scan stopping short). An empty file — the placeholder the file backend creates for a never-written history — is readable.
- **`unreadable` belongs to the loaded history, `stopped` to the process**: starting a load clears the first and its result sets it, and deleting the history clears it too.
- **Both capped reads count only what the cap can evict** — favourites are always admitted — so a read can hand back more than `max-history-size`, and **`g_paste_history_on_loaded()` runs both caps on what it read** (forcing the save its trim needs, and skipping it for a history that is `unreadable` or `stopped`).
- **Every directory listing goes through `g_paste_util_list_directory()`** (`gpaste-daemon-util.c`), which decides once that a truncated listing fails rather than coming back partial, that a missing directory lists nothing, and that an entry without the requested name attribute fails the listing. It is asked for `G_FILE_ATTRIBUTE_STANDARD_NAME` everywhere: the display name is a rendering and may name no file.

**Flavours.** `g_paste_storage_backend_new (GPasteStorage kind, settings)` is the factory, and `GPasteHistory` picks the kind from the `storage-backend` key (a gschema `<enum>` read via `g_paste_settings_get_storage_backend`):

| Kind | Class | Extension | Built when |
|---|---|---|---|
| `NOOP` | `GPasteNoopBackend` — reads empty, drops writes, lists nothing | `noop` (never matches) | always |
| `FILE` | `GPasteFileBackend` | `xml` | always |
| `ENCRYPTED_FILE` | `GPasteFileBackend` via `g_paste_file_backend_new_encrypted (settings, passphrase)` | `xmls` | `encryption` |
| `SQLITE` | `GPasteSqliteBackend` | `db` | `sqlite` |
| `ENCRYPTED_SQLITE` | `GPasteSqliteBackend` via `g_paste_sqlite_backend_new_encrypted (settings, passphrase)` | `dbs` | both |

- **A backend answers which flavour it is, and everything else follows**: `get_kind` is its only identity vfunc, and the extension, `is_encrypted()` and "only an encrypted flavour keeps password items" derive from it. The kinds live in one `storage_flavours[]` table in `gpaste-storage-backend.c`, which the shared `list_histories`, the migration's `detect_current_backend()` and the images cleanup all iterate up to `G_PASTE_N_STORAGE`. **To add a backend**: an enum value and nick, a row in that table, and a subclass implementing either the incremental vfuncs (the saver already feeds them per-operation changes) or just `write_history_file`.
- `g_paste_storage_is_encrypted (kind)` classifies the encrypted kinds independently of the built features; a build unable to construct one degrades it to `NOOP`, never to plaintext. The encrypted backends take their passphrase from a process-wide gcr-secure global (`g_paste_storage_backend_set_passphrase`/`get_passphrase`) set once at startup, and also degrade to `NOOP` without one.
- `g_paste_storage_passphrase_can_decrypt (kind, settings, passphrase)` verifies a passphrase against **every** history, refusing if any data-holding one fails to open (histories can be keyed differently after a failed re-key); the per-history verdict is `history_refutes_passphrase`, where only encrypted data the backend cannot open refutes anything.

**The file backend** (`gpaste-file-backend.c`) writes XML format `2.0`, the only one read: `1.0` is refused and left intact, with its own diagnostic, so it can still be converted by loading it once with GPaste 2. A favourite is a `favourite="true"` attribute and a password's `timeout` rides beside its `name`, each written only when set, so the version **stays `2.0`**: bumping it would have an older GPaste refuse the whole history, where leaving it only has it drop what it does not know.

**The SQLite backend** (`gpaste-sqlite-backend.c`, whose header comment describes the schema, ranking and encrypted flavour) is the incremental reference. What its comments do not say:

- The schema is versioned through `PRAGMA user_version`, one `case` per version in `migrate_schema`, falling through: **version 2 added `favourite`, version 3 the password `timeout`**, each a single `ALTER TABLE … DEFAULT 0` so older rows come back unpinned and without a timeout. Both stay plaintext in the encrypted flavour, like `rank` and `date`: metadata, not content.
- Only image rows store a date (the column is nullable), and an image row with a NULL date is skipped without refusing the history.
- `add_item` is an upsert-and-reconcile (see its comment), `write_history_file` (the migration import, `g_paste_history_save`) rewrites everything in one transaction, the connection is cached per path, and a mutex serializes the vfuncs, since a background load can overlap a write.
- The encrypted flavour uses per-column `crypto_secretbox` rather than SQLCipher, which was rejected as an ABI-incompatible sqlite3 fork. Its key comes from the shared `g_paste_crypto_derive_key()` (Argon2id, MODERATE); the salt and both Argon2 parameters are read back from the `meta` table, so they are only as trustworthy as the file, and `g_paste_crypto_derive_key()` refuses anything past `SENSITIVE`. A wrong passphrase is refused on open, except for an empty history, which is silently re-keyed.

**Images.** An image item's **value is its checksum**, and where its bytes were materialized is a separate, nullable `get_cache_path()`, set only by a backend that read it off a file (`gpaste-image-item.c` documents both). Capture encodes the PNG once (`get_png_bytes`, carried across IDLE and counted against the memory cap) and **writes nothing to disk**: persisting it is entirely the backend's job, so `NOOP` genuinely stores nothing.

- SQLite stores the blob in `items.image` (encrypted like any content column in the encrypted flavour), and a row without one is dropped rather than looked for on disk.
- The file backend owns the `images/<history_name>/<checksum>.png` layout (`g_paste_file_backend_image_path`, `_images_dir`, `_encrypted_path`, `_delete_image`): per history, so evicting an image from one never breaks another, and *derived* at write time from the checksum and the history being written — which is what makes a backup own its images, and what moves legacy shared-directory entries on their next save. The encrypted file flavour writes an encrypted `.pngs` side file instead, so no pixel reaches the disk in clear on any encrypted flavour; its parser falls back to the plaintext path for entries not yet migrated.
- Eviction calls `drop_item_data` (the file flavours sweep the `.png` and `.pngs` siblings, SQLite implements nothing). The base `delete_history` removes `images/<name>/` only once **no flavour** still stores that name, and reports the files it could not remove through its `GError` (never over the store's own failure), since on the plain flavours those are screenshots in cleartext.
- `import_histories` verifies by uuid *and content* (kind and real value), never by size: a bytes-carrying item legitimately weighs more than its path-based twin.

**History encryption** of the file flavour is described below.

## Migration, unlock and re-key

`gpaste-storage-migration.{c,h}` holds three **concerns**, each an ordinary `_async()`/`_finish()` pair documented where it is defined: the *migration* dialog (`g_paste_storage_migration_async()`, needed when the stored `storage-backend-revision` differs from `G_PASTE_STORAGE_BACKEND_REVISION`), the encrypted-history *decryption* (`g_paste_storage_decryption_async()`), and the *re-key* (`g_paste_storage_rekey_async()`). Startup chains migration → decryption → build the daemon. The library never spins a `GMainLoop` of its own nor calls `adw_init()`, and the concerns take **no `GCancellable`**, a concern being a dialog nothing can take back down.

- **Outcomes.** `_finish()` is `%FALSE` only when the prompt implementation failed, or when the re-key could not re-encrypt the histories — which the re-key reports to the user itself through `g_paste_prompt_report()`, worded by whether its rollback also failed. The migration's cleanup reports old data it could not delete the same way; every other outcome, a dismissal included, is `%TRUE`. A prompt that **fails ends its concern** rather than being asked again.
- **The migration dialog** picks a backend, optionally imports into it and optionally deletes the old data (warning when deleting without importing). Backing out of a passphrase prompt asks it again, keeping what was gathered. The *current* backend is detected from the files on disk (`detect_current_backend()`), written to `storage-backend` up front, and used as the import source and cleanup target, so migrating in any direction works. Its toggles are **clamped the moment the reply lands** (`on_migration_reply`), not trusted. Confirming bumps the revision; dismissing leaves it, so the dialog comes back next start (the deliberate choice of #357). **"Keep as is"** (`G_PASTE_PROMPT_TEXT_MIGRATION_KEEP`, in both prompt backends) is a reply carrying the current backend and neither toggle; it and any preselection are withheld when the current backend is one this build cannot construct, and Apply then stays insensitive (in the shell, `_onApply()` also returns early, Enter reaching the default action through a key binding).
- **Passphrases** come from the process first, then the keyring (`g_paste_storage_keyring_apply_verified`, flavour-aware and shared with the startup unlock and the backend factory's in-process fallback), and only then from a prompt — `confirm=TRUE` with a strength meter for a new encrypted history, `confirm=FALSE` through the shared `unlock_prompt` helper otherwise. Every passphrase is **verified** with `g_paste_storage_passphrase_can_decrypt` before use and re-prompted on failure. With `libsecret` built (`G_PASTE_ENABLE_LIBSECRET`, which requires encryption) the prompt offers "Remember this passphrase" (`gpaste-storage-keyring.{c,h}`, one attribute-less `SecretSchema`); a stale remembered entry is discarded, never used. The prompt lives in the daemon, not the UI.
- **On demand**, the preferences button and `gpaste-client migrate` reset the revision and re-execute the daemon rather than racing it: `g_paste_util_trigger_storage_migration()` is `g_paste_util_prepare_storage_migration()` (reset and `g_paste_settings_sync()`) followed by the same `g_paste_util_reexecute_daemon()` a plain `daemon-reexec` runs. A missing reply is the expected success of a re-exec, read that way by `g_paste_client_reexecute_sync()`/`_finish()` themselves; only `gpaste-client`, which can find the pid file, falls back to `SIGUSR1`-ing a daemon too old for the method. A cancelled on-demand migration leaves the revision reset.
- **The standalone daemon** re-execs and re-runs the startup migration. **The gnome-shell-hosted one**, which cannot re-exec, handles `reexecute-self` by flushing, running the concerns and reloading its backend in place (`g_paste_daemon_reload_storage` → `g_paste_history_reload_backend`, asynchronous like every load, and guarded by the same `migration_needed` check so a plain `daemon-reexec` is a no-op there). Both gates and the reload call **`g_paste_settings_reload()`** first, since the keys were written by another process; `reload_backend` also **detaches** the saver it replaces.
- Each executable registers an `AdwApplication` (which initialises libadwaita) and lets its own `g_application_run()` drive the dialogs. `G_PASTE_GTK_INIT_APPLICATION` passes no command line to `g_application_run()` on the remote-instance path, so GApplication never takes a flag or subcommand for a file to open.
- **In gnome-shell** the same `_async` functions run in process with `src/gnome-shell/prompt.js` as the `GPastePrompt`, so no passphrase ever crosses a process. `daemon.js` promise-wraps them by hand in `callStorageConcern()` — `Gio._promisify` cannot wrap namespace functions (see the JavaScript conventions in [`src/gnome-shell/AGENTS.md`](../../gnome-shell/AGENTS.md)), and would leave every concern silently doing nothing — and `_runStorageConcern()` logs a rejection and carries on. **One settle at a time** (`_settleStorage()` joins a later caller onto the running `_doSettleStorage`; the standalone daemon's `settling` flag guards the same window), every other concern taking its own turn on `_serializeStorage()` and **flushing from inside that turn**, which is why `_migrateInPlace()` runs `_doSettleStorage()` in a turn of its own.

## History encryption

`GPasteSecretStreamConverter` (`gpaste-secret-stream-converter.{c,h}`, built with the `encryption` feature, which defines `G_PASTE_ENABLE_ENCRYPTION`) is a bidirectional `GConverter` over libsodium's `crypto_secretstream` (XChaCha20-Poly1305), one final type doing both directions through a `GPasteSecretStreamDirection` argument. Its header comment gives the stream layout: the Argon2id salt and parameters in the header, ≤4 KiB length-prefixed chunks, the last carrying the FINAL tag so truncation is caught. Both directions buffer internally to cope with the arbitrary splits `GConverter::convert` hands them, "no progress" mapping to `G_IO_ERROR_NO_SPACE`/`PARTIAL_INPUT` as in GLib's own converters. The passphrase is a `GPastePassphrase` and the key gcr secure memory; the passphrase is kept for the converter's lifetime, `reset()` having to re-derive a salt-dependent key.

`GPasteFileBackend` wraps its streams with it for `ENCRYPTED_FILE` (".xmls"), and, unlike the plain flavour, persists passwords: their real value (`g_paste_item_get_real_value`) and `name`.

## The GlobalShortcuts portal client

**`GPasteGlobalShortcutClient`** wraps the XDG GlobalShortcuts portal (`org.freedesktop.portal.Desktop`) as a `GDBusProxy` subclass and is the daemon's only keybinding mechanism: `g_paste_global_shortcut_client_grab_all (accels[])`/`_ungrab_all()`, and a `keybinding-activated (const gchar *id)` signal. `gpaste-global-shortcut-client.c` is commented throughout; what a change to it has to keep:

- **`GPasteKeybindingAccelerator`** `{ id, accelerator, description }` is the transfer type, arrays terminated by `.id = NULL`, `description` being the label the portal's permission dialog shows. The caller's array lives only for the call, so the client copies it (`accelerators_copy()`/`_free()`) and compares sets with `accelerators_match()`. The three are static, and there is no `g_autoptr` cleanup for the struct: the keybinder's arrays borrow their strings, and nothing tells those from owned ones. The owned array doubles as the disposal flag: `NULL` once disposed, empty while usable with nothing held; both methods tolerate a disposed client.
- **A session is spent once its shortcuts are not the ones wanted** (a session permits one `BindShortcuts`): changing the set, ungrabbing and disposing close it, and a new non-empty set creates a session with its own `session_handle_token`. Handing over the set already held, while a session or live request exists, is a no-op. A bind may come back with a subset, including none: that is the user's choice, and the *requested* set stays the comparison key.
- **Requests** subscribe to `Request::Response` before the call, at a path predicted from the unique name and a random-plus-counter `handle_token` (no unique name: the call fails), and follow the path the method answers. Only `(ua{sv})` responses are decoded, anything else being failure (2); a create handle must be a string or object path passing `g_variant_is_object_path()`. `awaiting_response`/`responded` decide which of the two callbacks frees the request, and every task answer goes through `portal_request_take_error()` or `portal_request_return_boolean()`.
- **Nothing holds the client strongly**: requests sit in a non-owning list with a `GWeakRef`, their `GTask` has no source object and owns a `PortalBindData` with another weak ref and the request's generation, and calls use `g_dbus_connection_call()` rather than the proxy. Every callback opens the weak ref and checks the generation, the completion callback its *saved* one.
- **Generations**: closing or replacing a session bumps `generation` and retires requests in flight. Binds are cancelled or completed as superseded; an unanswered create is kept for the session handle it may still bring, which must be closed even after disposal. A create whose method call failed reports at once but stays under the retirement deadline, and its late Response can only close a session. Retired creates expire after ten minutes, or when their unique owner disconnects. `dispose()` steals the request list before retiring it; ordinary retirements walk a copy. `has_live_request()` ignores cleanup-only requests.
- **Retries**: a general failure (2) or a method error is retried up to ten times a second apart, by a source holding the client weakly and re-checking state when it runs. Exhaustion lasts until an accelerator is written, a bind succeeds or the owner changes; an obsolete task can neither reset nor consume the budget.
- **Owners**: `portal_owner` records the last well-known owner (seeded from the proxy on the first request). Losing the well-known name is not the unique owner dying: a change closes the known session on the *old* unique owner and retires outstanding creates without abandoning their responses, while each request watches its own unique owner. Recovery binds again when an owner appears with neither a live request nor a session — our own CreateSession activating the portal is not a restart. A request made while unowned subscribes to the well-known sender with an activation watch of its own, and adds the unique-sender subscription once the owner is known without dropping the first.
- **Closed and revocation**: `Session::Closed` is subscribed before CreateSession, for every path and sender, until disposal, the handler matching handle and unique sender. A remote close, or a response of 1 from a current request, records `session_revoked`, which suppresses retries and restart recovery; `grab_all()` — even with an unchanged accelerator — clears it.
- **Closes** target the unique owner that supplied the handle, own their connection, owner and handle so they can retry after disposal or replacement, share the retry budget, end at once on a disconnected owner, closed connection or removed object, and never activate or reach a replacement portal.
- **Triggers** use `CTRL`, `ALT`, `SHIFT` and `LOGO` and keep GDK's keysym names as they are (uppercasing `Return` or spelling `SUPER` breaks the backend's parser), after `g_paste_keyval_canonicalize()`, shared with the capture side. An unsupported modifier (Meta, Hyper) produces no `preferred_trigger`, leaving the portal to ask.

## Password expiry

**A password does not sit on the clipboard forever.** `gpaste-clipboards-manager.c` documents every step; the invariants:

- **The countdown belongs to the selection**, on `GPasteClipboardsManager`'s per-provider `_Clipboard` record, one deadline each: no route that puts an item on a selection reaches all of them (`select()` gives up on the first provider refusing, `ensure_not_empty()` is one provider acting alone), so a shared countdown could be cancelled for a selection its password never left.
- **Every route that publishes an item ends in `g_paste_clipboards_manager_arm_password()`**: `select()` (arming inside its loop, as each provider accepts), the manager's `ensure_not_empty()` wrapper — which is why `g_paste_clipboard_provider_ensure_not_empty()` hands back what it put there — and `rearm_password()`. The two writes taking a password *off* (`deselect_password()`, `notify_finish()`) arm nothing.
- **A firing acts only on a selection still carrying the item** it was armed for, held by reference (`g_paste_clipboards_manager_selection_holds()`, comparing real values against the provider's cache) — never on the history's head, which moves independently of the selections. Re-selecting the same password keeps its countdown unless its duration changed, which is why the record keeps the seconds it armed for.
- **Expiry acts per selection**: it first moves a non-password successor to the head without emitting `selected` (`retire_password()`, through a transfer-full `g_paste_history_add (g_object_ref (item))`, so a flush cannot restore the expired head), then writes each provider only once its current read identifies the password. An emptied history gets the empty string through `select_text()`, never an empty selection, which `ensure_not_empty()` would refill with the very password.
- **Expiry waits for a read to identify the selection**: while a provider `is_reading()`, the item stays retained with an overdue flag. Timeout edits keep their candidate and deadline until then; an intentional selection after an expired countdown starts a fresh exposure, while automatic restoration and edits never renew an elapsed deadline. Forced expiry survives explicit disposal.
- **An update in flight owns what its reply reads**: providers ref themselves for the whole read, the manager's callbacks get a struct holding a ref on the manager, the records are freed in `finalize`, and both callbacks bail when `history` is already `NULL`.
- **Running it early**: `g_paste_clipboards_manager_expire_password()` from `dispose` and `g_paste_daemon_expire_password()`, and the `_async` variant for `g_paste_daemon_reexecute()`, which must not hand the successor a selection still being classified. Its task has no source object (the manager's `expiry_tasks` list holds it), its completion is dispatched from a separate idle, and `expire_password_finish()` revalidates — `G_IO_ERROR_PENDING` asks for another wait, retried for at most thirty seconds, each wait bounded at sixty, inside the client's two-minute allowance. A deadline failure answers only its caller and keeps another waiter's cleanup.
- **The `Reexecute` invocation is held through expiry and revalidation**, and every way into a re-exec takes that wait (SIGUSR1 goes through `g_paste_daemon_reexecute()`; the pending request holds the daemon weakly). `reexecute-self` returns a boolean — the Shell host answers true once its in-process migration is scheduled — and only `UnknownMethod` lets the CLI fall back to SIGUSR1.
- **In gnome-shell, `dispose` is not enough**: dropping the daemon leaves it to GJS' collector while mutter keeps serving the published `GPasteClipboardMetaSource`, so `_releaseDaemon()` calls `g_paste_daemon_expire_password()` before its flush. It is kept out of `g_paste_daemon_flush()`, which a live daemon also calls mid-life.

## Clipboard updates

One clipboard change is one **`GPasteClipboardUpdate`** (`gpaste-clipboard-content.{c,h}`), shared by both backends, which only add the calls that fetch bytes. Its header comment and `GPasteClipboardReadGuard`'s are the reference; the rules they spell out:

- **Every read of an update is on one `GCancellable`, under one guard** measuring *silence*, not duration (`G_PASTE_CLIPBOARD_READ_TIMEOUT`, 30 s): every read reporting goes through `g_paste_clipboard_update_maybe_done()`, which touches the guard. Touching writes a timestamp; the single timer re-arms itself for what is left. The mutter backend touches it by hand before `gdk_content_deserialize_async()`.
- **The guard concludes the update itself**, since cancelling cannot fail an X11 conversion request: building the item, re-owning the selection and calling back live in `g_paste_clipboard_update_conclude()`, apart from the teardown that frees the struct once `pending` reaches zero. The cancel is asked for *after* the conclusion, and still fails a stalled stream transfer.
- **One update at a time per selection**: `g_paste_clipboard_update_new()` takes the backend's slot and supersedes what it holds; the two paths answering a change without starting an update (selection released, only unhandled types offered) call `g_paste_clipboard_update_supersede()` themselves. A superseded update releases its content at once and still concludes — with no item and no re-own — on the next main-loop turn, its callback being owed. A superseded callback (`superseded == TRUE`) is cleanup only.
- **Reads write only the update's own content**, a union tagged by `content_kind` with a `produced` flag, and **only the conclusion commits the provider's cache**. While an update is pending, the provider's getters hide the cache and `is_empty()` answers false; `is_reading()` says so.
- **A conclusion is done with the update before it publishes or calls back**, either of which can free it: locals are taken, the provider's ref taken over, and `g_paste_clipboard_update_release_content()` drops everything of size, running again at teardown for anything a late read stored. The content mimetype is freed only at teardown, the mutter backend's transfer holding that pointer.
- **A late read writes nothing anyone reads**: `g_paste_clipboard_update_is_expired()` (`concluded || superseded`, asked of the update and never of the cancellable) gates the content reads and `g_paste_clipboard_update_on_mime_read()`. Both backends take the provider off the update only after asking.
- **`sync_text()`**, reachable from D-Bus, is guarded the same way through `GPasteClipboardSyncData`.
- **The built item is transfer-full** to the callback, and the update's to release when there is none. A trimmed text or GDK image sets `reselect`, re-owning the selection only after every read is in.
- **Copies are ordered by serial**: update data captures the copy serial when the read starts, and synchronization never overwrites a selection holding a later one. Independent publications advance it and retire queued strips; maintenance ones (trim/image reselect, empty restoration, passing `independent = FALSE` to the provider's `select_item_full`/`select_text_full` and its `published` signal) preserve it. A newer synchronized copy supersedes an unfinished older read on the other selection: completed copies are kept, but capturing every transient owner is not guaranteed.
- **A rich-text strip belongs to one copy and waits for its read**: a refresh requested while a selection is classified keeps the stripped item until the read completes, publishes only if the selection matches and the history still holds that snapshot, and replaces the incoming item. An explicit selection or disposal drops pending refreshes.
- **Tests pinning these down**: `/clipboard/late_mime_read` for a mime landing late, the sync tests asserting the history's length as well as the final contents, and a CLI regression intercepting signals to check that only `UnknownMethod` permits SIGUSR1.

## Clipboard backends

**`GPasteClipboardProvider`** (`gpaste-clipboard-provider.{c,h}`) is a GObject interface abstracting one selection (clipboard or primary), with no toolkit type in any signature, so `GPasteClipboardsManager` drives every backend through it. Its vfuncs are `update`/`select_text`/`select_item`/`sync_text`/`ensure_not_empty`/`store`/`get_text`/`get_image_checksum`/`is_reading`/`is_clipboard`, generated per backend by `G_PASTE_CLIPBOARD_PROVIDER_DEFINE_VFUNCS (lc, UC)`; implementations emit `changed` through `g_paste_clipboard_provider_emit_changed`. `ensure_not_empty` is a concrete interface method over a per-backend `is_empty` vfunc, answering the item it put on the selection or `NULL`. A type implementing an interface uses `G_PASTE_DEFINE_TYPE_WITH_INTERFACE (TypeName, type_name, ParentType, IFACE_TYPE, iface_init)` (`gpaste-macros.h`), as both backends do.

- **Shared by both backends** (`gpaste-clipboard-content.{c,h}`): `GPasteClipboardContent`, the kind enum plus a tagged union (text or image-checksum string, file list, RGBA) with `clear`/`get_*` helpers; `g_paste_clipboard_content_classify_text` (trim, min/max and dedup for incoming text); `g_paste_clipboard_file_list_equal`; `g_paste_clipboard_content_to_item`; the read guard, `GPasteClipboardUpdate`, `GPasteClipboardSyncData`, `GPasteClipboardMimeCtx`, `GPasteClipboardMimeResults` and the `add_read`/`add_mime_read`/`on_mime_read` an update counts its reads through. A read is counted in beside the call firing it, never before the choice of whether to fire. These helpers are `G_PASTE_VISIBLE` because the GDK backend lives outside the library.
- **The daemon is backend-agnostic**: `g_paste_daemon_new (settings, clipboard, primary)` takes the two providers its caller built, and one `GPasteSettings` is shared by the daemon, its history, the clipboards manager and both providers. The library's only convenience constructor is `g_paste_daemon_new_meta (settings, selection)` (mutter, used by `daemon.js`, built with `gnome-shell`), `selection` typed `GObject *` so the introspected header needs no libmutter; the standalone daemon builds its GDK providers in `on_storage_ready`.
- **Colours** are published as `application/x-color` and a `text/plain` fallback (`gdk_rgba_to_string()`), by both backends, so they paste into plain-text targets.

**`GPasteClipboardGdk`** (`src/daemon/gpaste-clipboard-gdk.{c,h}`, `g_paste_clipboard_gdk_new_clipboard()`/`_new_primary()`) is built on `GdkClipboard` and requires the X11/XWayland backend, the only one delivering *global* ownership notifications. Text is published everywhere — `select_text`, `select_item`, a colour's textual half — through **`GPasteTextContentProvider`** (`src/daemon/gpaste-text-content-provider.{c,h}`) rather than `gdk_content_provider_new_typed (G_TYPE_STRING, …)`, because GTK's `G_TYPE_STRING` serializer serves bare `text/plain` as ASCII with `?` for the rest (`gpaste-text-content-provider.c` says how the two formats it claims and GTK's own serializers split the work).

**`GPasteClipboardMeta`** (`gpaste-clipboard-meta.{c,h}`, experimental, compiled into libgpaste-daemon with `gnome-shell`, linking `libmutter-51`) is built on `MetaSelection`, mutter's server-side tracker: it sees every ownership change with no focus gating, but only from inside gnome-shell, so `g_paste_clipboard_meta_new_clipboard()`/`_new_primary()` take the `MetaSelection` (`global.display.get_selection()`, one per display, the constructors picking `CLIPBOARD` or `PRIMARY`).

- Reads go through `meta_selection_transfer_async()` into a memory stream; writes publish a source we keep a ref to, so the resulting `owner-changed` is recognised as ours.
- Writes use the file-local **`GPasteClipboardMetaSource`**, since `MetaSelectionSourceMemory` advertises one mimetype: an ordered mimetype list, a mimetype→`GBytes` map and an optional `GValue`. Text is bytes under `text/plain;charset=utf-8` and `text/plain`, plus a text/uris item's special values (`g_paste_special_mime_get()`), matching the GDK backend's union. Images, colours and file lists are held as a `GValue` (`GDK_TYPE_TEXTURE`, `GDK_TYPE_RGBA`, `GDK_TYPE_FILE_LIST`), advertised with every format `gdk_content_formats_union_serialize_mime_types()` lists and serialized lazily in `read_async` (closing the memory stream before `steal_as_bytes`). Everything the source holds goes in **`dispose`**, and `read_async` then refuses with `G_IO_ERROR_CLOSED`, mutter possibly still holding a disposed source.
- On read, `g_paste_clipboard_meta_pick_mime()` matches the offer against the cached `gdk_content_formats_union_deserialize_mime_types()` set, preferring `image/png`/`text/uri-list`, and one `update_on_value`/`on_value_deserialized` pair decodes through `gdk_content_deserialize_async()`. Format coverage therefore follows GDK's loaders, colours and uris are byte-identical to the GDK backend (including `application/x-color`'s endianness and the `application/vnd.portal.filetransfer`/`files` types sandboxed apps need), and `images-support` gates capture in `update()` as in the GDK backend. Only the text path keeps literal mimetypes, needing the shared trim/length/dedup logic.

**The in-shell runner** (`GPasteDaemonRunner`, `src/gnome-shell/daemon.js`) builds `g_paste_daemon_new_meta()` with a `GPasteBus` and `GPasteSearchProvider`, and exposes a `ready` promise the indicator awaits (ownership and takeover above). Its lifetime is the extension's: no GApplication, signals or re-exec. gnome-shell cannot reload extension code on Wayland, so a plain `reexecute-self` is a no-op; an **on-demand storage migration** is handled in place from an idle (so the `Reexecute` dispatch unwinds first) by flushing, running the concerns against its own prompt and calling `reload_storage` on the live daemon, rebuilding it being impractical with its registration on gnome-shell's persistent connection. `StorageBackend`'s statics are introspected as class statics, `GPasteDaemon.StorageBackend.lock/unlock/set_passphrase`, not namespace functions.

## D-Bus methods

The method surface lives in `gpaste-daemon-methods.{c,h}`: free functions taking a small `GPasteDaemonMethods` context `{ skeleton, history, settings, clipboards_manager }`. `gpaste-daemon.c` keeps the object lifecycle, the signal emitters, the actions that need the GObject (`upload`, `reexecute`, `show_history`) and the dispatch. Everything but the `src/daemon/gpaste-daemon.c` entry point is in the installed library (`gpaste_daemon_internal_dep` in-tree), which the executable and the tests link. The interface-level rules are in [`src/libgpaste/AGENTS.md`](../AGENTS.md).

- **Errors are plain `GError`s in `G_PASTE_ERROR`** (`gpaste-3/gpaste-error.{c,h}`, in libgpaste so both sides share it). A handler bails with `G_PASTE_DBUS_ASSERT (cond, code, msg)`. The domain is registered with `g_dbus_error_register_error_domain()` from `g_paste_error_quark()`, which `g_paste_client_class_init()` calls, so errors map both ways (`org.gnome.GPaste.Error.NotFound`…) and a client switches on the code. A new code goes in the enum *and* the `GDBusErrorEntry` table (a `G_STATIC_ASSERT` catches a missing entry); the names are API.
- **Images travel as PNG bytes** (`GetImage(uuid) → ay`), never as paths, so storage stays the daemon's business; `GPasteClient` exposes `GBytes` (`g_paste_client_get_image{,_sync,_finish}`) and libgpaste-gtk4's `g_paste_gtk_util_get_image_finish` makes a `GdkTexture`.
- **A colour needs no method**, its value on the wire being the colour. **`GetUris(uuid) → as`** answers an array rather than a joined string, and uris rather than paths since `smb://` or `trash://` reach a uris item too; `GPasteUrisItem` reads them off its `GdkFileList` (`g_paste_uris_item_get_uris()`), and the reply is a plain `GStrv`, `GdkFileList` belonging in libgpaste-gtk4 if a front end ever wants one. A password has no such method: what it holds is the password.
- **Decoration is the client's**: the daemon sends an item's own content (a colour, uris newline-joined, an image's dimensions and date, a password's *name* — `get_value()` masks the password as `"******"`), and `g_paste_util_display_string (value, kind)` (`gpaste-3/gpaste-util.c`) renders it once for everyone: cached per item by `g_paste_client_item_get_display_string()`, used by the search provider (the shell's interface takes finished strings, so those are in the daemon's locale) and called by the extension through introspection. It translates only `Files`, `Color`, `Image` and `Password`, through the `GPaste` domain the extension shares; brackets are punctuation, spelled in code, an image's description going inside them after a comma. Local uris show as percent-decoded paths with a whole leading `$HOME` component written `~`; others stay uris; all are space-joined. `gpaste-client` decorates nothing, being the scripting surface. An image's dimensions and date are still formatted by the daemon, in its locale: structuring them would take a field on the wire, for a divergence that needs a daemon and a client under different locales to show.
