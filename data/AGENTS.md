# `data/`

Non-code resources: D-Bus service files (`dbus/`), `.desktop` entries, GSettings schemas (`gsettings/`), the application icons (`icons/`), systemd user units, AppStream metadata, shell completions (`completions/`).

A service file names its systemd unit (`SystemdService=`) only in a build that installs the units, a bus activating through a unit that is not there starting nothing. The daemon's `.desktop` entry, which GNOME Shell matches the daemon's own windows (the storage prompts) to, carries the graphical tool's icon and an `Exec=`: no D-Bus service activates `org.gnome.GPaste.Daemon`. The overview's search provider registration is installed whether or not the extension is built, the standalone daemon exporting the provider too.

**The release notes live outside the translated metainfo.** `data/metainfo/org.gnome.GPaste.Ui.metainfo.xml.in` carries `<releases type="external"/>` and the notes themselves sit in `data/metainfo/org.gnome.GPaste.Ui.releases.xml`, installed to `$datadir/metainfo/releases/`, where AppStream looks for `<component-id>.releases.xml`. That file is deliberately absent from `POTFILES.in`: the notes of a version nobody runs are never shown to anyone, yet every one of them sat in the catalog forever and fuzzied across every language the moment an old entry was touched. A new release adds its `<release>` there and nowhere else.

**Shell completions** (`data/completions/gpaste-client` for bash, `_gpaste-client` for zsh, `gpaste-client.fish` for fish — each behind its own `*-completion` meson option) mirror `gpaste-client`'s `commands[]` table, so a new verb or alias has to be added to all three and to `man/1/gpaste-client.1` — `show_help()` is printed from the table itself and needs nothing. Bash offers its options verb by verb, so a verb with a nonzero `item_args` has to offer `--use-index` there too. `meson test -C build completions` fails until they agree. Two rules every one of them follows:

- **Never activate the daemon from the overview either**: the search provider's registration (`search-provider/`) carries `AutoStart=false`, so GNOME Shell asks a daemon that is running and starts none, the standalone daemon recording every copy once it is up (`tests/tools/test-search-provider.py`).
- **Never activate the daemon from a completion, nor wait on one.** Anything that needs the daemon first asks the bus for the name's owner with `gdbus` (`GetNameOwner`), giving up when nothing owns it, then asks that owner by its unique name, which nothing activates, for a property of `org.gnome.GPaste3` — otherwise hitting tab would start a daemon behind the user's back and block the shell while it loads the history, or have `gpaste-client` wait on one still settling its storage, or on a GPaste 45 or 50 an update left running (`/client/presence/completion-serving-daemon` runs bash's against each).
- **History names come off disk**, not from `list-histories`: one file per history, `<name>.{xml,xmls,db,dbs}` under `$XDG_DATA_HOME/GPaste` (falling back to `.../gpaste`, the same `PACKAGE_NAME`/`PACKAGE` rule as `g_paste_util_get_history_dir_path`), so they complete instantly with no daemon at all.

The completions list items with `gpaste-client history`, which reads nothing from stdin, and still redirect `</dev/null`: an older `gpaste-client` first on `PATH` read stdin whenever it was not a tty, and would block where completion runs without a terminal. Item arguments complete to uuids, or to indexes when `--use-index` is in effect. zsh and fish show each item's text beside it, with its control characters as U+FFFD, as `gpaste-client` shows them on a terminal: the history writes an item as it is to a pipe, and a shell lists a description as it is (the completions test checks both, each where its shell is installed).
